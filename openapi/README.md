# The OpenAPI documents the web app is typed from

| file | what | generated by |
|---|---|---|
| `openapi.json` | the local server's (`server-rs`) public API | `pnpm gen:api` (exported by the server's own test/build) |
| `hub.json` | the **hub's** public API at `https://api.droppen.app/openapi.json` | refreshed by hand, see below |

`web/src/api/schema.d.ts` and `web/src/api/hub-schema.d.ts` are generated from
the two documents with `openapi-typescript`; both are committed, and CI
regenerates them and fails if the result differs.

## Refreshing the hub document

The hub generates its document from its handlers (`hub/crates/rh-hub/src/gotcha_app.rs`);
the checked-in copy is the contract of the **deployed** hub:

```sh
curl -fsS https://api.droppen.app/openapi.json > openapi/hub.json
pnpm --filter @remote-hand/web gen:api:hub
```

Do this after a hub release that changes the public API (a new route, a changed
body, a new response schema), in the same change that starts using it.

Known gaps, where the generated type is still `unknown` and the client keeps
a hand-written wire shape for now:

- `GET /v1/me?touch=1`: the query is not in the document yet.
- `me.email`, `me.plan`, `me.rotations`, `me.credentials`,
  `me.sign_in_changes`, `me.relay_prefs`: JSON values in the document.
- the error body: the document's `ApiError` schema has no properties (the
  client reads `{error, message, retry_after_ms, …}` itself).
- passkey WebAuthn options: JSON values (their shape is WebAuthn's).

Each is a hub-side schema improvement; until then those fields are read as
`unknown` at the edge and validated where they enter the app.
