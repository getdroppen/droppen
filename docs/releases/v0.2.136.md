## Droppen App for macOS

`Droppen-0.2.136.dmg` — the desktop app (Apple silicon and Intel), signed with Developer ID and notarised by Apple. It needs macOS 13 or later. Open the DMG, drag Droppen to Applications, open it.

Droppen 0.2.127 to 0.2.135 update themselves to this release: they download it in the background and install it the next time you quit, or at once with *Restart to Update*. 0.2.133 and 0.2.134 freeze after an update check that finds nothing newer, but not after one that finds this release, so they update the same way. If yours is frozen now, force-quit it (Option-Command-Esc) and open it again: its check about 15 seconds later finds this release. Droppen 0.2.125 and 0.2.126 update themselves in two steps: first to 0.2.127, which https://github.com/getdroppen/releases (where they look for updates, now archived) still offers, then from 0.2.127 to this release. Version 0.2.124 and older do not update themselves: download this DMG once and replace the app in Applications.

## macOS 版 Droppen App

`Droppen-0.2.136.dmg` 是桌面 App（Apple 芯片和 Intel 芯片的 Mac 都能用），使用 Developer ID 签名并经过 Apple 公证，需要 macOS 13 或更高版本。打开 DMG，把 Droppen 拖到「应用程序」，然后打开它。

0.2.127 至 0.2.135 会自动更新到这个版本：在后台下载，并在你下次退出时安装；也可以用「重启以更新」立即安装。0.2.133 和 0.2.134 在检查更新、发现没有新版本后会卡死，但发现这个版本时不会，所以同样会正常更新。如果你的 App 现在已经卡住，请强制退出（Option-Command-Esc）后重新打开：约 15 秒后的那次检查就会找到这个版本。0.2.125 和 0.2.126 会分两步自动更新：先更新到 0.2.127（它们检查更新的 https://github.com/getdroppen/releases 已归档，但仍提供 0.2.127），再从 0.2.127 更新到这个版本。0.2.124 及更早的版本不会自动更新：请手动下载一次这个 DMG，替换「应用程序」里的 Droppen。

## What's new in v0.2.136

### Terminals

- **vim works in the terminal again.** In the desktop app, on droppen.app and on a local server's web page, a terminal stopped drawing as soon as vim started. Keys still reached vim (it went into insert mode, and `:wq` saved the file), but the screen showed nothing after vim's first frame. At start, vim asks the terminal which modes it has on, and answering that threw an error in the web app's built copy of the terminal, which stopped the terminal from drawing anything more. The web app is now built so that code stays intact. The development server never had the problem; only the built app did.
- **Coming back to a terminal no longer types stray characters.** When you reopen a terminal, the page draws again what it showed before. The terminal used to answer the questions in that old output a second time (the cursor position, the device attributes, the colours), and the answers reached whatever ran in the terminal as typed text, for example `zsh: command not found: 2RR0`. Nothing is sent while the old output is drawn; keys pressed in those few milliseconds are dropped, as they are while the terminal is reconnecting.
- The web app is now built for browsers with ES2021: Firefox 79 or later, where Firefox 78 was enough before; the other browsers' minimums are unchanged. droppen.app already needs much newer browsers for its encryption (Chrome or Edge 137, Firefox 130, Safari 17).

### Claude Code: models with `[1m]`

- **A model asked for with `[1m]` is measured against its 1M window, and stays chosen.** Claude Code writes the model into a session's transcript without the `[1m]` marker. So a session on `deepseek-v4.1-flash[1m]` (or any other `…[1m]` model) showed its context against 200k, and after each turn the composer switched to the model without the marker, so the next message asked for the 200k variant. Droppen now puts the marker back from what the session asks for: the model its Claude Code process runs; with no process running, the model picked for the session in the composer, or else the `ANTHROPIC_MODEL` of the account it is bound to. The marker is only put back on the same model the transcript names.
- A `/model` sent in a session is followed from the next turn on, and so is a switch back to the model the session started with.
- One case still reads against 200k: a session run only from a terminal, with no model picked for it in Droppen and none in its account, since nothing on the computer knows it asked for `[1m]`. And one case reads too high: if you pick a `[1m]` model in Droppen and then run the same session from a terminal on the model without the marker, that run shows against 1M. This only changes the display.

### Sessions and Stop

- **An ACP session reads as working while its agent starts or switches model.** When a message went to an ACP session whose agent had exited (after its idle exit, a crash or a change to its settings), the session showed as idle with nothing running until the agent had started again, for up to two minutes. The same happened while the agent switched to the model or effort a message asked for, for up to a minute. It now shows as starting, the last turn stays on view, and the session list and the open session are told at once.
- **Stop works while a session starts.** On ACP and Codex sessions, Stop during the agent's start was refused with *no running message to interrupt*. It is now taken, and stops the turn of the message being started.
- **Stop stops the turn you meant.** A Stop that reached a Codex or ACP session just as its turn ended could stop the next queued message's turn instead. A Stop now names the turn or message it is for, and does nothing once that turn is over. A Stop that finds nothing to stop is not kept for a later turn.
- **The working bar no longer shows the previous turn's figures.** While a session's process starts (an ACP or Codex restart, or a Claude Code process starting), the bar under the composer showed the last turn's count and age, such as "3 messages · last activity 120m ago · 121m". Until the turn starts it now reads *agent is working on your message…*.
- **A session's detail matches its transcript.** A turn written while a session was being opened could, for one response, show its items next to the previous turn's model or idle status. Both now come from the same version of the transcript.

### Codex

- **Starting a Codex session no longer holds up the others.** A message to a Codex session whose app server was not running (a resume after a restart, the first message after switching its account, a new thread) held up every other start while codex started: sends to Claude Code, Codex and ACP sessions, archives and agent edits waited, their composers spinning, for up to a minute or more. Now only reserving the session waits; codex starts on its own.
- While a Codex session's app server starts, dropping or steering a message queued for it is refused at once (*Codex is still starting this session; try again once it has answered*), and so is archiving it (*Codex is still starting this session; archive it once it has answered*), instead of waiting for the whole start.

### droppen.app

- **Device-change alerts show in a browser that cannot keep their acknowledgement.** A browser whose storage is full or switched off, or whose stored acknowledgement was lost, never showed a device-change alert for the account, including one for a device someone else added. It now shows every change since this browser joined the account; *that was me* hides one on that page only, since nothing can be kept.

### Relays

- **A stopping relay tells the Hub it is draining.** When a relay stopped, its draining notice never reached the Hub, which learned only when the link closed, and could keep handing out tickets for the relay in the meantime. The relay now sends the notice before it closes the link, and closes it with code 1001 (*the relay is stopping*). Droppen Hub ignores such a notice from a link that a newer instance of the same relay has replaced, so an overlapping restart cannot leave the new instance marked as draining.

### Also new

- The server's split into crates is complete: the server program now only wires them together. No change in behaviour beyond what is listed here.

## v0.2.136 更新内容

### 终端

- **终端里又能正常使用 vim 了。** 在桌面 App、droppen.app 和本地服务端的网页上，终端一启动 vim 就不再刷新画面。按键其实送到了 vim（它进入了插入模式，`:wq` 也能保存文件），但 vim 画出第一屏之后屏幕就不再变化。vim 启动时会询问终端开着哪些模式，而 Web App 打包后的终端代码在回答这个询问时出错，从此不再绘制任何内容。现在 Web App 的打包方式保证这段代码保持原样。开发服务器从来没有这个问题，只有打包后的 App 有。
- **回到一个终端时，不再打出多余的字符。** 重新打开一个终端时，页面会把它之前的内容再画一遍。终端以前会把这些旧内容里的询问再回答一次（光标位置、设备属性、颜色），这些回答被当成键盘输入送进了终端里正在运行的程序，例如出现 `zsh: command not found: 2RR0`。现在重画旧内容的这段时间不再发送任何东西；这几毫秒里按下的键会被丢弃，和终端重新连接时一样。
- Web App 现在面向支持 ES2021 的浏览器打包：Firefox 需要 79 或更高版本（以前 78 即可），其他浏览器的最低版本不变。droppen.app 因为加密功能，本来就要求新得多的浏览器（Chrome 或 Edge 137、Firefox 130、Safari 17）。

### Claude Code：带 `[1m]` 的模型

- **用 `[1m]` 指定的模型按 100 万的上下文窗口计算，而且选择会保留。** Claude Code 写进会话记录的模型名不带 `[1m]` 标记。所以在 `deepseek-v4.1-flash[1m]`（或其他任何 `…[1m]` 模型）上的会话，上下文用量按 20 万计算；而且每一轮之后输入框都会切换到不带标记的模型，下一条消息就请求了 20 万的版本。现在 Droppen 会根据会话实际请求的模型补回这个标记：会话的 Claude Code 进程正在运行的模型；没有进程在运行时，用输入框里为这个会话选的模型，再不然用它绑定的账号的 `ANTHROPIC_MODEL`。只有和会话记录里是同一个模型时，才会补回标记。
- 在会话里发送的 `/model` 从下一轮起生效，切回会话启动时的模型也一样。
- 有一种情况仍按 20 万计算：只在终端里运行、在 Droppen 里没有为它选过模型、账号里也没有配置模型的会话，因为这台电脑上没有任何地方知道它请求了 `[1m]`。还有一种情况会显示偏高：在 Droppen 里选了 `[1m]` 模型，又在终端里用不带标记的模型运行同一个会话，那一次运行会按 100 万显示。这只影响显示。

### 会话与停止

- **ACP 智能体启动或切换模型时，会话显示为正在工作。** 消息发给一个智能体已经退出的 ACP 会话时（空闲退出、崩溃或改了它的设置之后），会话会一直显示为空闲、没有在运行，直到智能体重新启动完成，最长两分钟。智能体切换到消息要求的模型或推理强度时也一样，最长一分钟。现在会话显示为正在启动，上一轮的内容继续显示，会话列表和打开着的会话也会立即更新。
- **会话启动期间也能停止。** 在 ACP 和 Codex 会话上，智能体启动期间按停止会被拒绝（*no running message to interrupt*）。现在会接受，并停止正在启动的那条消息的这一轮。
- **停止只停你想停的那一轮。** 停止指令刚好在 Codex 或 ACP 会话的一轮结束时到达，可能会停掉下一条排队消息的那一轮。现在停止指令会写明它针对哪一轮或哪条消息，那一轮结束后就不再生效。没有可停的东西时，停止也不会留到之后的某一轮。
- **工作状态栏不再显示上一轮的数字。** 会话的进程启动期间（ACP 或 Codex 重启、Claude Code 进程启动），输入框下方的状态栏显示的是上一轮的条数和时间，比如「3 条消息 · 最近活动 120m 前 · 121m」。现在在这一轮开始之前，它显示 *agent 正在处理你的消息…*。
- **会话详情和会话记录保持一致。** 打开会话的同时如果正好写入了新的一轮，返回的内容可能会把新一轮的条目和上一轮的模型或空闲状态放在一起，持续一次。现在两者取自会话记录的同一个版本。

### Codex

- **启动 Codex 会话不再拖住其他会话。** 向 app server 没有在运行的 Codex 会话发消息时（重启后恢复会话、切换账号后的第一条消息、新建对话），codex 启动的这段时间里，其他所有会话的启动都要等着：发给 Claude Code、Codex 和 ACP 会话的消息、归档和智能体的修改都在等，输入框一直转圈，最长一分钟甚至更久。现在只有预留会话这一步需要等，codex 的启动不再占着别人。
- Codex 会话的 app server 启动期间，丢弃或插队一条给它排队的消息会立即被拒绝（*Codex is still starting this session; try again once it has answered*），归档它也一样（*Codex is still starting this session; archive it once it has answered*），不再等整个启动结束。

### droppen.app

- **无法保存确认记录的浏览器也会显示设备变更提醒。** 存储已满或被关闭的浏览器，或者保存的确认记录丢失了的浏览器，从来不会显示账号的设备变更提醒，包括别人加了一台设备的提醒。现在它会显示这个浏览器加入账号以来的每一次变更；「是我操作的」只在当前页面隐藏这一条，因为没有地方可以保存。

### 中继

- **中继停止时会通知 Hub 它正在排空。** 以前中继停止时，「正在排空」的通知从来没有送到 Hub，Hub 要等连接断开才知道，在这之前可能还在给这个中继分配连接。现在中继会先发出通知，再关闭连接，关闭码是 1001（*the relay is stopping*）。如果同一个中继已经由更新的实例接替，Droppen Hub 会忽略旧连接发来的这种通知，所以新旧实例交替重启时，新实例不会被误标为正在排空。

### 其它新内容

- 服务端拆分成多个 crate 的工作已经完成：服务端程序现在只负责把它们组装起来。除了这里列出的内容，行为没有变化。
