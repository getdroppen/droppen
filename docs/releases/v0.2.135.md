## Droppen App for macOS

`Droppen-0.2.135.dmg` — the desktop app (Apple silicon and Intel), signed with Developer ID and notarised by Apple. It needs macOS 13 or later. Open the DMG, drag Droppen to Applications, open it.

Droppen 0.2.127 to 0.2.134 update themselves to this release: they download it in the background and install it the next time you quit, or at once with *Restart to Update*. 0.2.133 and 0.2.134 freeze after an update check that finds nothing newer (see below), but not after one that finds this release, so they update the same way. If yours is frozen now, force-quit it (Option-Command-Esc) and open it again: its check about 15 seconds later finds this release. Droppen 0.2.125 and 0.2.126 update themselves in two steps: first to 0.2.127, which https://github.com/getdroppen/releases (where they look for updates, now archived) still offers, then from 0.2.127 to this release. Version 0.2.124 and older do not update themselves: download this DMG once and replace the app in Applications.

## macOS 版 Droppen App

`Droppen-0.2.135.dmg` 是桌面 App（Apple 芯片和 Intel 芯片的 Mac 都能用），使用 Developer ID 签名并经过 Apple 公证，需要 macOS 13 或更高版本。打开 DMG，把 Droppen 拖到「应用程序」，然后打开它。

0.2.127 至 0.2.134 会自动更新到这个版本：在后台下载，并在你下次退出时安装；也可以用「重启以更新」立即安装。0.2.133 和 0.2.134 在检查更新、发现没有新版本后会卡死（见下文），但发现这个版本时不会，所以同样会正常更新。如果你的 App 现在已经卡住，请强制退出（Option-Command-Esc）后重新打开：约 15 秒后的那次检查就会找到这个版本。0.2.125 和 0.2.126 会分两步自动更新：先更新到 0.2.127（它们检查更新的 https://github.com/getdroppen/releases 已归档，但仍提供 0.2.127），再从 0.2.127 更新到这个版本。0.2.124 及更早的版本不会自动更新：请手动下载一次这个 DMG，替换「应用程序」里的 Droppen。

## What's new in v0.2.135

### The desktop app no longer freezes

- **Droppen 0.2.133 and 0.2.134 froze after checking for updates.** Whenever a check found the app up to date (about 15 seconds after every launch, and at any later check), the app stopped responding and could not be quit, only force-quit. This release fixes it. It also fixes a rarer hang, when the app's server exited just as *Try again* was restarting it.
- **Updates never travel over plain http.** The app's update checks and downloads, and its reads of the release notes, refuse a redirect to an `http://` address. The first address was already checked to be https, but a redirect from it was followed wherever it led. An update's signature already refused a changed archive; now neither the update manifest nor the archive travels unencrypted. A refused redirect, or too many of them, shows as *Update Service Unavailable*, not as no network.
- The app's updater is now tauri-plugin-updater 2.14.1, which checks an update's signature once more as it installs it (the app has already checked it just before).
- Dependency updates clear three security advisories, none of which reached what Droppen ships: `zip`, which the updater uses only on Windows and the macOS app never included; a second copy of `katex`, which the web app never included; and `vite`, whose advisory concerns its development server only.

### Old environment names no longer work

- **The server reads only the `DROPPEN_*` names.** As v0.2.134 announced, the server no longer reads its pre-rename environment names. If a launchd plist, a systemd unit or a shell profile still sets one, set the `DROPPEN_*` name with the same value instead. Only `REMOTE_HAND_DATA_DIR` and `REMOTE_HAND_CONFIG_DIR` are still mentioned, once each at start when set without their new name, because ignoring them in silence would move the server to the default install's files. The names no longer read, by group:
  - Files and configuration: `REMOTE_HAND_DATA_DIR`, `REMOTE_HAND_CONFIG_DIR`, `REMOTE_HAND_CLAUDE_LOCAL_ROOT`, `REMOTE_HAND_CLAUDE_MANAGED_ROOT`, `REMOTE_HAND_SHIM_BIN`.
  - Push and notifications: `REMOTE_HAND_PUSH_CONTACT`, `RH_PUSH_ALLOW_INSECURE_ENDPOINT`, `RH_NOTIFY_ALLOW_INSECURE_ENDPOINT`.
  - Requests and recordings: `RH_ALLOWED_ORIGINS`, `RH_SESSION_LOG`, `RH_SESSION_LOG_MAX_MB`.
  - Running the CLIs and accounts: `RH_IDLE_TIMEOUT_MS`, `RH_STALL_MS`, `RH_INTERRUPT_STEP_MS`, `RH_WATCHDOG_INTERVAL_MS`, `RH_AWAIT_BACKGROUND_MS`, `RH_RESIDENT_IDLE_MS`, `RH_STEER_SETTLE_MS`, `RH_TASK_ROOT`, `RH_ROTATE_AHEAD_PERCENT`, `RH_USAGE_FALLBACK_MS`.
  - The cloud agent and the hub it signs in to: `RH_HUB_DEFAULT`, `RH_HUB_API_TRAFFIC`, `RH_AGENT_CONTROL`, `RH_AGENT_LINK`, `RH_AGENT_DIRECT`, `RH_AGENT_DIRECT_STUN`, `RH_AGENT_RELAYS`, `RH_AGENT_RELAY_INSECURE`, `RH_AGENT_MIGRATE_WITHIN_SECS`, `RH_AGENT_STATUS_CLI`, `RH_AGENT_SYNC_DAYS`, `RH_AGENT_SYNC_EXTERNAL`, `RH_AGENT_COMPACT_RECORDS`, `RH_AGENT_COMPACT_EVERY_SECS`, `RH_AGENT_COMPACT_IDLE_SECS`, `RH_AGENT_COMPACT_OLDEST_SECS`.
  - Names Droppen sets for the programs it starts: `RH_SUPERVISED`, `RH_DESKTOP_APP`, `RH_NOTIFY_URL`, `RH_NOTIFY_TOKEN`. The server that `droppen up` or the desktop app runs, a session's `droppen-notify`, and the command Droppen shows for a second install get only the `DROPPEN_*` names.
- **The relay reads only the `DROPPEN_RELAY_*` names.** As v0.2.134 announced, the relay no longer reads `RH_RELAY_HUB`, `RH_RELAY_ORIGIN`, `RH_RELAY_KEY`, `RH_RELAY_STATE_DIR`, `RH_RELAY_REGISTRATION_TOKEN`, `RH_RELAY_ID`, `RH_RELAY_TICKET_KEYS`, `RH_RELAY_BIND`, `RH_RELAY_TRUST_PROXY`, `RH_RELAY_MAX_CONNS` or `RH_RELAY_DRAIN_SECS`, and says nothing about them. A relay still configured under them stops at start with `DROPPEN_RELAY_ORIGIN is required`: set each `DROPPEN_RELAY_*` name with the same value. Move the key first: a relay that starts with its key only in `RH_RELAY_KEY` finds no key, makes a new one in its state directory, and so becomes a new relay. (The relay no longer reads `RH_HUB_API_TRAFFIC` either: the hub-API traffic capture is `DROPPEN_HUB_API_TRAFFIC` only.)

### ACP agents

- **A terminal an agent kills takes all its processes with it.** On macOS, a process the terminal's shell was starting at the moment of the kill could survive it, keep the terminal open, and hold up the agent until that process ended. Droppen now signals the terminal's processes again until none is alive, for at most a second, so `terminal/kill` and `terminal/release` answer once they are gone, a few milliseconds later than before. The same goes for the terminals of an agent whose process ends.
- **A failed session says why at once.** When a session on an ACP agent fails, the line saying why is in its transcript by the time the session shows as failed. Before, the session could already show as failed while that line was not yet written.
- **For authors of ACP agents: the client uses the protocol's official schema.** What Droppen sends an agent, and its answers to the agent's requests, are now built with the official `agent-client-protocol-schema` crate (1.13). An agent that follows the specification reads them as before, and what an agent says is read as before. What changes on the wire:
  - `initialize`'s `clientCapabilities` carry `"auth":{"terminal":false}`, the specification's default for a client that offers no terminal login.
  - `session/load` sends the same members in another order.
  - A request from the agent whose id is a boolean, an object or an array is not run, and is answered `{"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Invalid request"}}`, as JSON-RPC 2.0 asks. One whose id is a string, a number (a fraction or a very large integer included) or `null` is still run, and answered under its id as it came.
  - A terminal's exit status leaves out what it does not know instead of writing `null`: `{"exitCode":3}`, `{"signal":"SIGKILL"}`, and no `exitStatus` in `terminal/output` while the command runs. A negative exit code, which the protocol's unsigned field cannot hold, is left out; the signal, if there is one, is kept.
  - A message that cannot be encoded, such as one with a working directory that is not UTF-8, is not sent: the call fails with *a message to the agent would not encode*.

### The command line

- **A command line that cannot be parsed exits with status 2.** An unknown command or option, or a missing value, now exits 2, clap's status for a usage error, instead of 1. A command that refuses after reading its arguments still exits 1. The same holds for `droppen-relay` and `droppen-update-manifest`.
- `--name=value` and short options with their value attached are accepted.
- **`droppen-relay` checks its command line.** A word its command does not read is refused (`serve junk`), and `--help` after a command prints the help: `keygen --help` used to print a key, and `serve --help` started the relay. `--reason=x` gives `deregister` its reason.

### Also new

- **A server started inside a session keeps that session's notification channel to itself.** Droppen started from a Droppen session (another instance run in a session's terminal, say) inherited that session's notification address and token, and passed them on to every program it started except a Claude session with notifications on: those programs could notify as the outer session, and carried its token in their environment. Now none of them inherits it; a Claude session with notifications on gets a channel of its own, as before.
- **Tool details shown as JSON keep the CLI's order.** The input and output of tools without a view of their own (MCP tools among them), Codex function calls, and ACP tool input and output list their keys in the order the CLI wrote them, instead of sorted. After the update, a computer linked to droppen.app uploads its copy of each session that shows such JSON once more, open pages reload those sessions once, and it sends its status and session list once more; what they say is unchanged.
- On droppen.app, the download buttons show the latest version and its size and download the file itself, where they fell back to the release page, and the waitlist on the pricing page goes through. Those pages asked their own host instead of the hub, or were not allowed to reach it.
- The server's code is split into separate crates internally; no change in behaviour beyond what is listed here.

## v0.2.135 更新内容

### 桌面 App 不再卡死

- **0.2.133 和 0.2.134 检查更新后会卡死。** 只要检查发现已是最新版本（每次启动后约 15 秒，以及之后的每一次检查），App 就会停止响应，也无法退出，只能强制退出。这个版本修复了这个问题。另外还修复了一个更少见的卡死：App 的服务端恰好在「重试」重启它时退出。
- **更新不再经过明文 http。** App 检查和下载更新、读取更新说明时，会拒绝跳转到 `http://` 地址。以前只检查第一个地址是不是 https，它跳转到哪里都会跟过去。更新的签名本来就会拒绝被改动过的安装包；现在更新清单和安装包也都不会以明文传输。被拒绝的跳转、或跳转次数过多，会显示为「更新服务暂时不可用」，而不是网络不可用。
- App 的更新组件升级到 tauri-plugin-updater 2.14.1，安装更新时会再校验一次签名（App 在安装前已经校验过）。
- 依赖更新消除了三条安全公告，但它们都没有影响到 Droppen 实际发布的内容：`zip` 只在 Windows 上被更新组件使用，macOS App 从未包含它；另一份 `katex` 副本从未打包进 Web App；`vite` 的公告只涉及它的开发服务器。

### 旧的环境变量名不再生效

- **服务端只读 `DROPPEN_*` 名字。** 如 v0.2.134 预告的那样，服务端不再读取改名前的环境变量名。如果 launchd plist、systemd unit 或 shell 配置里还设着旧名字，请改设同值的 `DROPPEN_*` 名字。只有 `REMOTE_HAND_DATA_DIR` 和 `REMOTE_HAND_CONFIG_DIR` 还会提示：设了旧名字而没设新名字时，服务端启动时各提示一次，因为悄悄忽略它们会让服务端改用默认安装的文件。下面按用途分组列出不再读取的名字：
  - 文件与配置：`REMOTE_HAND_DATA_DIR`、`REMOTE_HAND_CONFIG_DIR`、`REMOTE_HAND_CLAUDE_LOCAL_ROOT`、`REMOTE_HAND_CLAUDE_MANAGED_ROOT`、`REMOTE_HAND_SHIM_BIN`。
  - 推送与通知：`REMOTE_HAND_PUSH_CONTACT`、`RH_PUSH_ALLOW_INSECURE_ENDPOINT`、`RH_NOTIFY_ALLOW_INSECURE_ENDPOINT`。
  - 请求与会话记录：`RH_ALLOWED_ORIGINS`、`RH_SESSION_LOG`、`RH_SESSION_LOG_MAX_MB`。
  - 驱动 CLI 与账号：`RH_IDLE_TIMEOUT_MS`、`RH_STALL_MS`、`RH_INTERRUPT_STEP_MS`、`RH_WATCHDOG_INTERVAL_MS`、`RH_AWAIT_BACKGROUND_MS`、`RH_RESIDENT_IDLE_MS`、`RH_STEER_SETTLE_MS`、`RH_TASK_ROOT`、`RH_ROTATE_AHEAD_PERCENT`、`RH_USAGE_FALLBACK_MS`。
  - 云端 agent 与它登录的 hub：`RH_HUB_DEFAULT`、`RH_HUB_API_TRAFFIC`、`RH_AGENT_CONTROL`、`RH_AGENT_LINK`、`RH_AGENT_DIRECT`、`RH_AGENT_DIRECT_STUN`、`RH_AGENT_RELAYS`、`RH_AGENT_RELAY_INSECURE`、`RH_AGENT_MIGRATE_WITHIN_SECS`、`RH_AGENT_STATUS_CLI`、`RH_AGENT_SYNC_DAYS`、`RH_AGENT_SYNC_EXTERNAL`、`RH_AGENT_COMPACT_RECORDS`、`RH_AGENT_COMPACT_EVERY_SECS`、`RH_AGENT_COMPACT_IDLE_SECS`、`RH_AGENT_COMPACT_OLDEST_SECS`。
  - Droppen 为它启动的程序设置的名字：`RH_SUPERVISED`、`RH_DESKTOP_APP`、`RH_NOTIFY_URL`、`RH_NOTIFY_TOKEN`。`droppen up` 或桌面 App 运行的服务端、会话里的 `droppen-notify`，以及 Droppen 为第二套安装显示的命令，都只拿到 `DROPPEN_*` 名字。
- **中继只读 `DROPPEN_RELAY_*` 名字。** 如 v0.2.134 预告的那样，中继不再读取 `RH_RELAY_HUB`、`RH_RELAY_ORIGIN`、`RH_RELAY_KEY`、`RH_RELAY_STATE_DIR`、`RH_RELAY_REGISTRATION_TOKEN`、`RH_RELAY_ID`、`RH_RELAY_TICKET_KEYS`、`RH_RELAY_BIND`、`RH_RELAY_TRUST_PROXY`、`RH_RELAY_MAX_CONNS` 和 `RH_RELAY_DRAIN_SECS`，也不再提示。仍用旧名字配置的中继会在启动时停下（`DROPPEN_RELAY_ORIGIN is required`）：请逐个改设同值的 `DROPPEN_RELAY_*` 名字。先迁移密钥：密钥只设在 `RH_RELAY_KEY` 里的中继启动时找不到密钥，会在状态目录里生成一把新的，也就成了另一个中继。（中继也不再读 `RH_HUB_API_TRAFFIC`：hub-API 流量捕获只认 `DROPPEN_HUB_API_TRAFFIC`。）

### ACP 智能体

- **智能体结束一个终端时，终端里的所有进程都会一起结束。** 在 macOS 上，如果结束终端的那一刻终端里的 shell 正在启动进程，这个进程可能躲过结束信号，让终端一直开着，智能体也要一直等到它退出。现在 Droppen 会反复发信号，直到终端里没有存活的进程为止（最多一秒），所以 `terminal/kill` 和 `terminal/release` 会在进程都结束后才应答，比以前晚几毫秒。智能体进程退出时，它的终端也一样处理。
- **会话失败时立即说明原因。** ACP 智能体上的会话失败时，会话显示为失败之前，说明原因的那一行已经写进会话记录。以前会话可能已经显示失败，那一行却还没写进去。
- **致 ACP 智能体的作者：客户端改用协议的官方 schema。** Droppen 发给智能体的消息，以及它对智能体请求的应答，现在都用官方的 `agent-client-protocol-schema` crate（1.13）构建。遵循规范的智能体读到的内容和以前一样；Droppen 读取智能体消息的方式也没有变。线上格式的变化如下：
  - `initialize` 的 `clientCapabilities` 多了 `"auth":{"terminal":false}`，这是规范对不提供终端登录的客户端的默认值。
  - `session/load` 发送的字段不变，只是顺序不同。
  - 智能体发来的请求如果 id 是布尔值、对象或数组，不会执行，应答为 `{"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Invalid request"}}`，这是 JSON-RPC 2.0 的要求。id 是字符串、数字（包括小数和非常大的整数）或 `null` 的请求照常执行，并按原样带回它的 id。
  - 终端的退出状态省略未知的字段，而不是写 `null`：`{"exitCode":3}`、`{"signal":"SIGKILL"}`；命令还在运行时，`terminal/output` 里没有 `exitStatus`。负的退出码超出协议里无符号字段的范围，会被省略；如果有信号，信号保留。
  - 无法编码的消息（比如工作目录不是 UTF-8）不会发送，这次调用会失败并提示 *a message to the agent would not encode*。

### 命令行

- **无法解析的命令行以状态码 2 退出。** 未知的命令或选项、缺少的值，现在按 clap 的惯例以 2 退出，而不是 1。命令读完参数之后才拒绝的情况仍然以 1 退出。`droppen-relay` 和 `droppen-update-manifest` 也一样。
- 现在可以写 `--name=value`，短选项也可以直接接值。
- **`droppen-relay` 会检查命令行。** 命令不读取的多余参数会被拒绝（`serve junk`）；命令后面的 `--help` 会显示帮助，以前 `keygen --help` 会生成一把密钥，`serve --help` 会直接启动中继。`--reason=x` 可以作为 `deregister` 的原因。

### 其它新内容

- **在会话里启动的服务端，不再把这个会话的通知通道传下去。** 在 Droppen 会话里启动的 Droppen（比如在会话的终端里运行另一个实例）会继承这个会话的通知地址和令牌，并传给它启动的所有程序，只有开了通知的 Claude 会话除外：这些程序能以外层会话的身份发通知，环境变量里也带着它的令牌。现在它们都不再继承；开了通知的 Claude 会话仍然有自己的通道。
- **以 JSON 显示的工具详情保持 CLI 的顺序。** 没有专门视图的工具（包括 MCP 工具）的输入输出、Codex 的函数调用，以及 ACP 工具的输入输出，按 CLI 写出的顺序列出字段，不再排序。更新之后，连接到 droppen.app 的电脑会把含有这类 JSON 的会话副本重新上传一次，打开着的页面会重新加载这些会话一次，电脑还会再发送一次状态和会话列表；内容都没有变化。
- 在 droppen.app 上，下载按钮会显示最新版本和文件大小，并直接下载文件，以前会退回到发布页面；定价页的候补名单也能正常提交了。这些页面以前向自己的域名请求、而不是向 hub 请求，或者不被允许访问 hub。
- 服务端的代码在内部拆分成了多个 crate；除了这里列出的内容，行为没有变化。
