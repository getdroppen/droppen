## Droppen App for macOS

`Droppen-0.2.140.dmg` — the desktop app (Apple silicon and Intel), signed with Developer ID and notarised by Apple. It needs macOS 13 or later. Open the DMG, drag Droppen to Applications, open it.

Droppen 0.2.129 to 0.2.139 update themselves to this release: they download it in the background and install it the next time you quit, or at once with *Restart to update*. 0.2.133 and 0.2.134 freeze after an update check that finds nothing newer, but not after one that finds this release, so they update the same way; if yours is frozen now, force-quit it (Option-Command-Esc) and open it again. Version 0.2.128 and older are not guaranteed to upgrade themselves: install this release once by hand — download this DMG and replace the app in Applications, or run the install script again (`curl -fsSL https://droppen.app/install.sh | sh`) — and later releases update themselves as before.

## Droppen App for Linux

The desktop app for Linux, the same app as on the Mac. It needs glibc 2.35 or later (Ubuntu 22.04, Debian 12 and newer), on x86_64 (`x86_64`, `amd64`) or 64-bit Arm (`aarch64`, `arm64`). The AppImage, `Droppen-0.2.140-x86_64.AppImage` or `Droppen-0.2.140-aarch64.AppImage`, is one file that carries its own libraries and updates itself; the .deb, `droppen_0.2.140_amd64.deb` or `droppen_0.2.140_arm64.deb`, is for Debian and Ubuntu. To install it the first time, keep the AppImage in a folder you can write to, make it executable (`chmod +x Droppen-0.2.140-x86_64.AppImage`) and open it; or install the .deb with `sudo apt install ./droppen_0.2.140_amd64.deb` and open Droppen from your app launcher.

Droppen 0.2.139's AppImage updates itself to this release: it downloads this release's AppImage for its architecture in the background (it waits while NetworkManager says the connection is metered), checks its signature, and writes it over the old file, under the same name, the next time you quit, or at once with *Restart to update*. It does not update where you cannot replace the file (the menu says *Move Droppen to a Folder You Can Write to Update*), nor when it runs unpacked (`--appimage-extract-and-run`). The .deb does not update itself: install this release's .deb the same way, `sudo apt install ./droppen_0.2.140_amd64.deb` (`droppen_0.2.140_arm64.deb` on Arm). `Droppen-0.2.140-linux-sources.tar` holds the source of the libraries the AppImages carry and of the AppImage runtime; `LIBRARIES-x86_64.txt` and `LIBRARIES-aarch64.txt` list each library with its Ubuntu package and version.

## What's new in v0.2.140

### Long sessions

- **Long, busy sessions are much faster.** Opening a long session, jumping to its first unread message, searching it and paging back through its history are all much faster, most of all while an agent is writing to it. Droppen used to read a session's whole transcript again every time it changed. On a 480 MiB Claude Code transcript that was about a second of work for every change the agent wrote: once for the open session, once for its offline copy, and again for a history page, the first-unread lookup or a search that came in between, which had to wait for it. Droppen now reads on from where it last stopped, so the same change takes about a millisecond; on a 100 MiB Codex session, under a millisecond where it took about 0.35 s. While an agent works in a long session, the server (and the one inside the desktop app) now spends far less CPU.
- **Jumping to the first unread message takes milliseconds.** In a long session an agent was writing to, *jump to the first* could spin for seconds: the lookup and each page of history it fetched read the whole transcript again, since the agent had changed it since the last read. They are now answered from the version the server read last whenever it still holds the messages you are looking at, and otherwise read on from it. In our measurements on a transcript of about 500 MB, with an agent adding to it every second or faster, the whole jump went from 0.3–1.4 s to about 3 ms, and a history page or first-unread lookup that does have to read the file went from about 1.1 s to under a millisecond.
- **A jump fetches its history in one request, and lands with context above it.** *jump to the first* and a jump to a search hit used to fetch history 200 items at a time, each request only once the one before had come back, so a jump far back waited for a round trip per page, which adds up over a relay. Now a jump asks for everything back to just above its target in one request. A request carries up to 2000 items or 1 MiB, so only a jump further back than that takes a few, with a count of them while it goes. The jump also brings a page of earlier items above the target, so the view can centre the target instead of leaving it at the top edge, and a search hit in a tool's output lands on that tool's card, opened, instead of on a row the card folds away a moment later. Scrolling back still fetches a page at a time. A device on an older release answers a page at a time, as before.
- **A long session opens faster, and is read once however many ask.** A transcript is now read 1 MiB at a time instead of 8 KiB, which takes a whole read of a 480 MiB transcript from about 0.9 s to about 0.6 s. When several parts of Droppen want the same version at once (the open session, its history, the unread count, search, the offline copy), it is read once and shared: in our test, six readers at once took about 3 s each, 15 s of CPU and over 200 MB of memory between them, and now take 0.6 s each, 0.6 s of CPU and under 50 MB.

### Fixes

- **A session no longer starts over when a file it mentions appears or disappears.** When a message names a file that exists, Droppen shows a file chip you can download it from. When such a file was created or deleted, the server took the transcript for a changed one from that message on, though nothing in it had changed: scrolling back past the message reloaded the session from its newest messages instead of adding the older ones, a session reopened or reconnected was sent again whole instead of only what was new, and the session's offline copy was uploaded again. Now only what the transcript says counts, and the chip still comes and goes with the file. Once, after this update, the offline copy of most sessions updated in the last 30 days that mention a file that exists is uploaded again; after that, not again for this reason.
- **An open session no longer stays on old content after a read that failed.** When Droppen could not read a transcript for a moment (a file being replaced, a disk error), the open session took the change as seen and kept showing what it had before until the file changed again, which in an idle session could be never. It now tries again 2 s later, then less often while the read keeps failing (after 4, 8 and 16 s, then every 30 s), and shows the new content as soon as a read works, even if the file has not changed since. The offline copy had the same problem and is fixed the same way: it now backs off from a session it cannot read, where it tried again every 3 s.

### For developers

- The server's API: `GET /api/sessions/{source}/{id}/history` takes an optional `from`, the index the page should reach back to. The answer is `[from, before)` as one page, never less than the page a request without `from` gets, and at most 2000 items and 1 MiB of item JSON; past either, it is the newest part of the range, with `hasMoreBefore` and the `startIndex` to go on from. A `from` that is not an index is a 400. `GET /api/sessions/{source}/{id}/first-unread` takes the client's resume marker as two optional fields, `since` and `fp`. Both routes may answer from the newest parse the server holds when the client's fingerprint holds in it, so a page's `sig` and `totalItems` can be a little behind the file. A server from before this ignores the new fields.
- **`DROPPEN_PARSE_ORACLE=1`** in the server's environment is an opt-in diagnostic. After a parse that read on from the last one, the server parses the whole file again and compares the two, at most one check per transcript at a time; if they differ, it logs an error and reads that file whole the next time. Each check costs a whole parse (on a 480 MiB transcript about 0.5–1 s, and about 170 MB of memory while it runs), so it is off by default and not for everyday use.
- Inside: a version of a transcript is parsed once however many ask. A Claude Code or Codex transcript of 8 MiB or more that only grew (by up to 32 MiB) is read on from its last parse, and read whole again after 64 such reads in a row or 10 minutes after its last whole read. A transcript's items are each shared, so a version read on from the last one, or a prefix of it, copies none of them. Each parse logs its `mode` (`full`, `resume` or `fallback`) at debug level. A transcript's fingerprints leave out the file chips, so a session's fingerprint chain changes once, from its first item with a chip.

## v0.2.140 更新内容

### 长会话

- **又长又忙的会话快多了。** 打开长会话、跳到第一条未读消息、在会话中搜索、往回翻历史记录都快多了，agent 正往会话里写的时候尤其明显。以前会话的对话记录每变一次，Droppen 都要把整份文件重新读一遍。一份 480 MiB 的 Claude Code 对话记录，agent 每写一点就要花大约一秒：打开的会话读一遍，它的离线副本读一遍，中间请求的历史记录页、第一条未读或搜索还要再读一遍，而且得等它读完。现在 Droppen 从上次读到的地方接着读，同样的改动只要大约一毫秒；100 MiB 的 Codex 会话，从大约 0.35 秒降到不到一毫秒。agent 在长会话里工作时，服务端（以及桌面 App 内置的服务端）占用的 CPU 少得多。
- **跳到第一条未读消息只要几毫秒。** 在 agent 正在写的长会话里，「跳到第一条」以前可能要转好几秒：查找第一条未读，以及它取回的每一页历史，都因为 agent 刚改过文件而把整份对话记录重新读一遍。现在只要服务端上次读到的版本里还有你正在看的消息，就直接用它回答，否则从它接着读。我们在一份约 500 MB、agent 每秒或更快地往里追加的对话记录上测量：整个跳转从 0.3–1.4 秒降到大约 3 毫秒；确实需要读文件的历史页或第一条未读查询，从大约 1.1 秒降到不到一毫秒。
- **跳转一次请求取回历史，落点上方留有上下文。** 「跳到第一条」和跳到搜索结果以前每次取 200 条历史，等上一次回来才发下一次，所以跳得越远，要等的往返越多，经过中继时更明显。现在跳转一次请求取回直到目标上方的全部内容。每次请求最多 2000 条或 1 MiB，只有更远的跳转才需要几次请求，期间会显示请求的计数。跳转还会在目标上方多取一页，这样视图能把目标放在中间，而不是贴在顶边；工具输出里的搜索结果会落在这个工具的卡片上并展开，而不是落在随后被卡片折叠掉的那一行。往上滚动仍然一次取一页。运行旧版本的设备仍是一次回答一页，和以前一样。
- **长会话打开得更快，同一版本不管多少地方要都只读一次。** 对话记录现在每次读 1 MiB，而不是 8 KiB，整份读一遍 480 MiB 的对话记录从大约 0.9 秒降到大约 0.6 秒。Droppen 的几个部分（打开的会话、它的历史、未读计数、搜索、离线副本）同时要同一个版本时，只读一次，大家共用：我们测量六个同时读，以前每个大约 3 秒，合计 15 秒 CPU、200 MB 以上内存；现在每个 0.6 秒，合计 0.6 秒 CPU、不到 50 MB。

### 修复

- **会话提到的文件出现或消失时，会话不再从头来过。** 消息里提到的文件存在时，Droppen 会显示一个可以下载它的文件条。以前这样的文件被创建或删除时，服务端会把对话记录从那条消息起当成改过了，尽管里面什么都没变：往回滚过这条消息时，会话会从最新的消息重新加载，而不是加上更早的消息；重新打开或重连的会话会整份重发，而不是只发新内容；会话的离线副本也会重新上传。现在只看对话记录本身写了什么，文件条照样随文件出现和消失。更新后会有一次：最近 30 天更新过、提到了存在的文件的会话，大多会把离线副本重新上传一次；之后不会再因为这个原因上传。
- **读取失败后，打开的会话不再停在旧内容上。** 以前 Droppen 一时读不了对话记录时（文件正在被替换、磁盘出错），打开的会话会把这次改动当成已经看过，继续显示原来的内容，直到文件再次改变；闲置的会话可能一直停在那里。现在它 2 秒后再试，读取一直失败时间隔逐渐拉长（4、8、16 秒，之后每 30 秒一次），一旦读成功就显示新内容，即使文件之后没再变过。离线副本也有同样的问题，现在也一样修好了：读不了的会话，它会退避重试，不再每 3 秒重读一次。

### 面向开发者

- 服务端 API：`GET /api/sessions/{source}/{id}/history` 新增可选的 `from`，即这一页要往回取到的序号。返回 `[from, before)` 一整页，至少和不带 `from` 时的一页一样多，最多 2000 条、条目 JSON 共 1 MiB；超过任一上限时返回这段范围里最新的部分，并带上 `hasMoreBefore` 和接着取用的 `startIndex`。不是序号的 `from` 返回 400。`GET /api/sessions/{source}/{id}/first-unread` 新增两个可选字段 `since` 和 `fp`，即客户端的续接标记。只要客户端的指纹在服务端手里最新的解析结果里成立，这两个路由都可能直接用它回答，所以一页的 `sig` 和 `totalItems` 可能比文件稍旧。旧版本的服务端会忽略这些新字段。
- **`DROPPEN_PARSE_ORACLE=1`**（设在服务端的环境里）是可选的诊断开关。每次接着上次读的解析之后，服务端把整份文件再解析一遍并比较两者，同一份对话记录同时最多查一次；不一致时记一条错误日志，下次整份读这个文件。每次检查都要整份解析一遍（480 MiB 的对话记录大约 0.5–1 秒，运行时约多占 170 MB 内存），所以默认关闭，不适合日常开着。
- 内部变化：同一版本的对话记录不管多少地方要，只解析一次。8 MiB 及以上、只是变长了（最多 32 MiB）的 Claude Code 或 Codex 对话记录，会从上次解析的地方接着读；连续这样读 64 次，或距上次整份读满 10 分钟后，再整份读一次。对话记录的每个条目都是共享的，接着读出的新版本或它的前缀都不复制条目。每次解析都会在 debug 级别记下 `mode`（`full`、`resume` 或 `fallback`）。对话记录的指纹不再包含文件条，所以每个会话的指纹链会从它第一个带文件条的条目起变一次。
