## Droppen App for macOS

`Droppen-0.2.127.dmg` — the desktop app (Apple silicon and Intel), signed with Developer ID and notarised by Apple. It needs macOS 13 or later. Open the DMG, drag Droppen to Applications, open it.

Droppen 0.2.125 and 0.2.126 update themselves to this release: they download it in the background and install it the next time you quit, or at once with *Restart to Update*. From this release on, releases are published at https://github.com/getdroppen/droppen/releases, and the app looks for its updates there. Version 0.2.124 and older do not update themselves: download this DMG once and replace the app in Applications.

## macOS 版 Droppen App

`Droppen-0.2.127.dmg` 是桌面 App（Apple 芯片和 Intel 芯片的 Mac 都能用），使用 Developer ID 签名并经过 Apple 公证，需要 macOS 13 或更高版本。打开 DMG，把 Droppen 拖到「应用程序」，然后打开它。

0.2.125 和 0.2.126 会自动更新到这个版本：在后台下载，并在你下次退出时安装；也可以用「重启以更新」立即安装。从这个版本起，新版本发布在 https://github.com/getdroppen/droppen/releases，App 也到那里检查更新。0.2.124 及更早的版本不会自动更新：请手动下载一次这个 DMG，替换「应用程序」里的 Droppen。

## What's new in v0.2.127

### How releases are made

- **Built, signed and published by GitHub Actions, from the public source.** This is the first release made entirely by this repository's release workflow, on GitHub's runners: the server for every platform and the desktop app were built there, and the app was signed with Developer ID and notarised by Apple there too. Nothing was built or signed on anyone's own computer. Every file of the release has a build provenance attestation: a statement, signed through Sigstore and recorded by GitHub, that this repository's release workflow made exactly that file for this tag. With the [GitHub CLI](https://cli.github.com) (logged in), check a file you downloaded, for example:

  ```sh
  gh attestation verify droppen-v0.2.127-macos-aarch64.tar.gz --repo getdroppen/droppen \
    --signer-workflow getdroppen/droppen/.github/workflows/release.yml \
    --source-ref refs/tags/v0.2.127
  ```

  `SHA256SUMS` is attested too, so checking it once and then the files against it (`shasum -a 256 -c --ignore-missing SHA256SUMS`) is the same. More in [Verifying a download](https://github.com/getdroppen/droppen/blob/v0.2.127/docs/releasing.md#verifying-a-download).
- **Releases have moved here from getdroppen/releases.** The releases up to v0.2.126 stay there, and this one is also published there once, for the apps that still look for their updates there. The install command, `curl -fsSL https://droppen.app/install.sh | sh`, keeps working: https://droppen.app/install.sh now redirects to the installer of this repository's latest release.

### Web app (droppen.app and the page on your device)

- **A browser that cannot run Droppen's encryption is told so.** A browser without WebCrypto's Ed25519 or X25519, such as an older Chromium on an Android phone, signed in to droppen.app and then showed "this browser could not open its device keys", with a *try again* that could never work. droppen.app now checks the browser first, before it reads or makes any key. It says what is missing and which browsers are new enough, and in a browser built into an app (WeChat, QQ, Alipay, Douyin, Weibo, or an Android web view) it suggests opening the page in the system browser.
- **Compatibility mode**, for a browser that lacks only Ed25519, X25519 or both: the same keys and the same encryption, with those two done in JavaScript (the noble-curves library). The screen explains the choice and says what it changes: while the page is open, this device's private keys are plain bytes in the page's memory instead of keys the browser holds; the JavaScript arithmetic is not hardened against side channels as the browser's own is; and one more library runs in the page. Nothing is made until you tick *I understand the risk* and press *trust this browser*. The choice is kept for this browser only, which then shows "compatibility mode" in the bar and on its row in My devices. Tap that label to read what it means, or to stop using compatibility mode: the device keys stay stored, and the page asks again before it uses them. droppen.app/security describes it too.
- **droppen.app/security explains itself.** Point at, focus or tap any part of a formula: a short card says what it is, why it is there, what makes it and what takes it, and who can know it, and the same value lights up in every formula on the page. A card can be pinned, and *View as* (your device, the other device, Droppen Hub, a relay) hatches every value that party cannot know. The page now starts by defining the two kinds of device it speaks of, devices that run AI and your browsers and phones, and every later mention shows that definition the same way. Long enumerations are now lists with their key terms in bold, and the repository paths it names link to the source on GitHub.
- When you start a new session, files pasted or attached just after you press Send could still count the attachments that had just been sent, leaving less room than the 20 a message can carry. They now count only what is still in the box.

### Devices that run AI (the server `droppen`, and the one inside the Droppen App)

- **Closing a terminal now tells every pane still showing it.** Each one, on any of your devices, shows `[process exited]`. Before, a pane could miss that note and freeze on a terminal that was already gone.
- More terminal fixes:
  - A pane that opens a terminal while it is printing gets that output exactly once: it could lose some, or show some twice.
  - A pane that cannot keep up with a terminal's output is cut off cleanly and shows `[client too slow]`, instead of a reset connection that lost the note. One that stops reading altogether is let go after 90 seconds, instead of holding on to the terminal's connection for good. A burst of output after the computer was busy for a moment no longer cuts off one that keeps up.
  - Closing a terminal whose shell had just exited no longer sends any signal. It used to signal the process ids the shell had, which by then could belong to other programs.
- **A relay ticket that Droppen Hub revoked is replaced at once.** The device kept trying the revoked ticket and asked for a new one only as it neared its expiry, so it could stay off its relays for up to ten minutes. It now asks Droppen Hub for a fresh ticket straight away.
- The server holds the lock on its instance for as long as its process runs. If serving stopped on an error, the lock could go while the rest of the process still ran, and a second server could then start on the same instance.

### Renewing a device's identity key, in testing

- **A device's identity key can now be renewed without enrolling the device again, while this is tested.** The 0.2.126 notes said renewal stayed switched off. Droppen Hub has since switched it on for early testing: the switch is the hub's, not part of this release. In My devices, a device that runs AI has *renew identity key* in its ⋯ menu. The account's setting *Always confirm on the device when renewing an identity key* decides whether each renewal waits for the code that device shows, or a device renews on its own once a device that could control it is removed. Until someone chooses, none renews on its own.
- Fixes found in that testing:
  - Notifications from a renewed device keep coming: the page follows the device's new notification key, and the device no longer hands out its old one while it makes the new one.
  - A device that cannot save its state as it takes its new key takes the key once saving works again, instead of reporting at its next start that its identity key was replaced elsewhere. Copies kept of a renewed device's sessions carry on from where they were, instead of reading everything again from the start.
  - If Droppen Hub switches renewals off, a page undoes what it had begun for them: no device's keys stay withheld, and a pause of control that can safely end is ended. A device waiting for Droppen to be updated on other devices is renewed once they are. Two pages no longer withdraw each other's renewal. The note shown when someone changes the renewal setting now says renewals "may now be automatic", not "again", which was wrong for an account's first choice.

## v0.2.127 更新内容

### 发布方式

- **由 GitHub Actions 从公开源码构建、签名并发布。** 这是第一个完全由本仓库的发布工作流在 GitHub 的运行器上做出的版本：各平台的服务端和桌面 App 都在那里构建，App 也在那里使用 Developer ID 签名并经过 Apple 公证。没有任何文件是在某个人自己的电脑上构建或签名的。这个版本的每个文件都附有构建来源证明（build provenance attestation）：一份经 Sigstore 签名、由 GitHub 记录的声明，说明正是本仓库的发布工作流为这个标签做出了这个文件，一字节不差。装好 [GitHub CLI](https://cli.github.com) 并登录后，可以这样核对下载的文件，例如：

  ```sh
  gh attestation verify droppen-v0.2.127-macos-aarch64.tar.gz --repo getdroppen/droppen \
    --signer-workflow getdroppen/droppen/.github/workflows/release.yml \
    --source-ref refs/tags/v0.2.127
  ```

  `SHA256SUMS` 本身也有证明，所以核对它一次、再用它核对各个文件（`shasum -a 256 -c --ignore-missing SHA256SUMS`）效果相同。详见 [Verifying a download](https://github.com/getdroppen/droppen/blob/v0.2.127/docs/releasing.md#verifying-a-download)。
- **发布地址从 getdroppen/releases 搬到了这里。** v0.2.126 及更早的版本仍留在那里；这个版本也会在那里发布一次，供仍到那里检查更新的 App 使用。安装命令 `curl -fsSL https://droppen.app/install.sh | sh` 照常可用：https://droppen.app/install.sh 现在会跳转到本仓库最新版本的安装脚本。

### 网页（droppen.app 和设备上的本地页面）

- **浏览器运行不了 Droppen 的加密时，会直接说明。** 不支持 WebCrypto Ed25519 或 X25519 的浏览器（例如 Android 手机上较旧的 Chromium）以前能登录 droppen.app，随后却显示「这个浏览器打不开它的设备钥匙」，附带一个永远不会成功的「重试」。现在 droppen.app 在读取或生成任何钥匙之前，会先检查浏览器。它会说明缺少什么、哪些浏览器版本够新；在应用内置的浏览器里（微信、QQ、支付宝、抖音、微博，或 Android 的 WebView），会建议改用系统浏览器打开本页。
- **兼容模式**，用于只缺 Ed25519、X25519 或两者都缺的浏览器：钥匙和加密方式不变，只是这两项改用 JavaScript 完成（noble-curves 库）。页面会解释这个选择，并说明有什么不同：页面打开期间，这台设备的私钥是页面内存里的明文字节，而不是由浏览器保管的钥匙；JavaScript 的曲线运算不像浏览器自带的那样针对侧信道做过加固；页面里还会多运行一个库。在你勾选「我了解这个风险」并按下「信任这个浏览器」之前，什么都不会生成。这个选择只对这个浏览器有效，之后顶栏和「我的设备」里它的那一行会显示「兼容模式」。点一下这个标记，可以查看它的含义，或者停用兼容模式：设备钥匙仍保存在浏览器里，再次使用前页面会重新询问。droppen.app/security 也写到了它。
- **droppen.app/security 处处有解释。** 指向、聚焦或点按公式里的任何部分，都会出现一张小卡片，说明它是什么、为什么在那里、由什么生成、被什么使用，以及谁能知道它；同一个值在页面所有公式里一起高亮。卡片可以固定；「视角」（你的设备、另一台设备、Droppen Hub、中继）会把那一方无法知道的每个值打上斜线。页面开头现在先定义它所说的两类设备：可运行 AI 的设备，以及你的浏览器和手机；之后每次提到它们，都能用同样的方式看到定义。长串的列举改成了列表，关键词加粗；页面提到的仓库路径都链接到 GitHub 上的源码。
- 新建会话时，按下发送之后紧接着粘贴或添加的文件，可能仍把刚随消息发出的附件算在内，可用的名额少于一条消息最多能带的 20 个。现在只算输入框里实际还有的附件。

### 可运行 AI 的设备（服务端 `droppen`，以及 Droppen App 内置的服务）

- **关闭终端时，所有还在显示它的窗格都会收到通知。** 你任何设备上的这些窗格都会显示 `[process exited]`。以前窗格可能收不到这条提示，停在一个已经不存在的终端上不动。
- 其它终端修复：
  - 在终端正在输出时打开它的窗格，每段输出恰好收到一次：以前可能丢掉一部分，或者重复显示一部分。
  - 跟不上终端输出的窗格会被干净地断开，并显示 `[client too slow]`，而不是连接被重置、提示也随之丢失。完全不再读取的窗格会在 90 秒后被放开，不会一直占着终端的连接。电脑短暂忙碌之后的一阵输出，不会再把跟得上的窗格断开。
  - 关闭一个 shell 刚退出的终端，不再发送任何信号。以前它会向那个 shell 用过的进程号发信号，而那时这些进程号可能已经属于别的程序。
- **被 Droppen Hub 撤销的中继票据会立即换新。** 以前设备会一直重试被撤销的票据，快到期时才申请新的，因此可能长达十分钟连不上中继。现在它会马上向 Droppen Hub 申请一张新票据。
- 服务端在进程运行期间一直持有它实例的锁。以前服务因出错停止时，锁可能在进程其余部分仍在运行时就被释放，另一个服务端随后可能在同一个实例上启动。

### 更换设备身份密钥（测试中）

- **现在可以更换设备的身份密钥，不必重新加入设备；这项功能仍在测试。** 0.2.126 的说明写的是它仍处于关闭状态。此后 Droppen Hub 已把它打开，供早期测试使用：开关在 Hub 那边，不属于这个版本。在「我的设备」里，可运行 AI 的设备的 ⋯ 菜单中有「更换身份密钥」。账户设置「更换身份密钥时总在设备上确认」决定每次更换是等你输入那台设备显示的代码，还是在能控制它的设备被移除后由它自动更换。在有人做出选择之前，任何设备都不会自动更换。
- 测试中发现并修复的问题：
  - 更换过身份密钥的设备，通知会继续送达：页面会跟上设备新的通知密钥，设备在生成新密钥期间也不再把旧的交出去。
  - 设备在换上新密钥时如果没能保存状态，会等保存恢复正常后再换上，而不是在下次启动时报告它的身份密钥「已在别处更换」。为更换过密钥的设备保留的会话副本会从原来的位置继续，而不是从头重新读取。
  - Droppen Hub 关闭更换功能时，页面会撤回它为此开始的操作：不再有设备的钥匙被扣着，能安全结束的控制暂停会结束。等待其它设备更新 Droppen 的设备，会在它们更新后完成更换。两个页面不再互相撤回对方的更换。有人修改更换设置时显示的提示，现在写的是「更换身份密钥现在可以自动进行」，而不是「又可以自动进行了」：账户第一次做选择时，「又」是不对的。
