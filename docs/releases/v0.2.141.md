## Droppen App for macOS

`Droppen-0.2.141.dmg` — the desktop app (Apple silicon and Intel), signed with Developer ID and notarised by Apple. It needs macOS 13 or later. Open the DMG, drag Droppen to Applications, open it.

Droppen 0.2.129 to 0.2.140 update themselves to this release: they download it in the background and install it the next time you quit, or at once with *Restart to update*. 0.2.133 and 0.2.134 freeze after an update check that finds nothing newer, but not after one that finds this release, so they update the same way; if yours is frozen now, force-quit it (Option-Command-Esc) and open it again. Version 0.2.128 and older are not guaranteed to upgrade themselves: install this release once by hand — download this DMG and replace the app in Applications, or run the install script again (`curl -fsSL https://droppen.app/install.sh | sh`) — and later releases update themselves as before.

## Droppen App for Linux

The desktop app for Linux, the same app as on the Mac. It needs glibc 2.35 or later (Ubuntu 22.04, Debian 12 and newer), on x86_64 (`x86_64`, `amd64`) or 64-bit Arm (`aarch64`, `arm64`). The AppImage, `Droppen-0.2.141-x86_64.AppImage` or `Droppen-0.2.141-aarch64.AppImage`, is one file that carries its own libraries and updates itself; the .deb, `droppen_0.2.141_amd64.deb` or `droppen_0.2.141_arm64.deb`, is for Debian and Ubuntu. To install it the first time, keep the AppImage in a folder you can write to, make it executable (`chmod +x Droppen-0.2.141-x86_64.AppImage`) and open it; or install the .deb with `sudo apt install ./droppen_0.2.141_amd64.deb` and open Droppen from your app launcher.

The AppImages of Droppen 0.2.139 and 0.2.140 update themselves to this release: they download this release's AppImage for their architecture in the background (they wait while NetworkManager says the connection is metered), check its signature, and write it over the old file, under the same name, the next time you quit, or at once with *Restart to update*. They do not update where you cannot replace the file (the menu says *Move Droppen to a Folder You Can Write to Update*), nor when they run unpacked (`--appimage-extract-and-run`). The .deb does not update itself: install this release's .deb the same way, `sudo apt install ./droppen_0.2.141_amd64.deb` (`droppen_0.2.141_arm64.deb` on Arm). `Droppen-0.2.141-linux-sources.tar` holds the source of the libraries the AppImages carry and of the AppImage runtime; `LIBRARIES-x86_64.txt` and `LIBRARIES-aarch64.txt` list each library with its Ubuntu package and version.

`Droppen-0.2.141.dmg` 是桌面 App（Apple 芯片和 Intel 芯片的 Mac 都能用），使用 Developer ID 签名并经过 Apple 公证，需要 macOS 13 或更高版本。打开 DMG，把 Droppen 拖到「应用程序」，然后打开它。

Linux 版桌面 App，和 Mac 版是同一个 App。需要 glibc 2.35 或更高版本（Ubuntu 22.04、Debian 12 及更新的版本），支持 x86_64（`x86_64`、`amd64`）和 64 位 Arm（`aarch64`、`arm64`）。AppImage（`Droppen-0.2.141-x86_64.AppImage` 或 `Droppen-0.2.141-aarch64.AppImage`）只有一个文件，自带所需的库，会自动更新；.deb（`droppen_0.2.141_amd64.deb` 或 `droppen_0.2.141_arm64.deb`）适用于 Debian 和 Ubuntu。第一次安装：把 AppImage 放在你可写入的文件夹里，设为可执行（`chmod +x Droppen-0.2.141-x86_64.AppImage`），然后打开它；或者用 `sudo apt install ./droppen_0.2.141_amd64.deb` 安装 .deb，然后从应用启动器打开 Droppen。

## What's new in v0.2.141

### On droppen.app

- **A slow connection no longer drops while data is still arriving.** On a slow link (around 1 Mbps or less, as on a weak mobile connection), the connection to a device through droppen.app could drop every few seconds and connect again, over and over. The page checks the path through the relay every 5 s with a small probe, and it closed the connection when a probe had gone unanswered for 10 s, even though data was arriving the whole time: on a slow link, the probe's answer waits behind the data already on its way. Each new connection then asked for the same data again, which filled the link again. Now the page closes the connection only when a probe has gone unanswered for 10 s and nothing at all has arrived for 10 s either. A path that has died is still replaced, within 15 s of the last data it brought, and a pause of a few seconds on a mobile link is not taken for one. One limit is known: an upload slower than about 100 kbps can go more than 10 s with nothing coming back from the device, so its connection can still be taken for a dead one and closed.
- **The bar says "slow" instead of a round trip it never measured.** On such a link the bar often showed the relay's round trip as *5001 ms*: that was how long the oldest probe had gone unanswered, not a round trip. Now, while a probe has gone unanswered for 5 s or more, and for longer than the last round trip measured, the bar reads *slow · ≥5 s* in red (*≥10 s* and so on, in whole seconds), and its hover card and screen-reader label say the same. As soon as an answer comes, the measured round trip shows again.
- **A connection log, to read and to send.** droppen.app now keeps a log of what this browser's connections to your devices did, to read on screen and to send along when you report a connection problem. Open it from the pulse icon in the bar, before *devices* (in a window 640 px wide or more); from *Connection log…* under *Change relay…* in the path's hover card, while connected; or from *my devices → This device → Connection log → open*, at any width. It records the link to the Hub; which relay was chosen, and why; each device's end-to-end channel and its paths (a relay, the Hub, or direct); when a connection opened and closed, and which side or timer closed it; probes and their answers; the requests over the connection (their route, status, time and size); what the bar said; and, once a second while data moves, how much is queued and in flight. It keeps the last 30 minutes, in memory in this tab, and the newest of it across a reload. It opens on *events*, which leaves out the once-a-second samples and the probes; *all* has them, and *problems* shows only warnings and errors. *copy* puts the newest of the view on the clipboard, up to 60,000 characters (it fits in a GitHub issue), under a header that names the web build, the version of Droppen on the device, the browser and the network; *download* saves all of it as a `.txt` file; *clear* empties it. The log leaves out tokens, keys and cookies, what a session or message says, file and folder names and paths, device and account names, email addresses, IP addresses and host names, and full URLs; device and account ids are masked with a hash salted for this browser, and text that is not Droppen's own words is withheld. Nothing is sent anywhere: the log leaves the browser only when you copy or download it.

### Sessions

- **A Claude Code session shows its agent name.** Other agent sessions message a running Claude Code session by its agent name (with `ListAgents` and `SendMessage`), not by the session id that *copy session id* copies, so with several sessions in one project it was hard to tell which one to address. While a Claude Code session's CLI runs, the session header now shows that name on a chip with an @ icon; click it to copy the name. The session list's menu has *copy agent name*, after *copy session id*. On droppen.app the name shows only once the device itself has answered, never from the offline copy, which can hold the name of a CLI that has exited since. Codex and ACP sessions have no agent name.
- **On a Mac, a crashed Claude Code CLI no longer counts as live.** A Claude Code CLI that crashes leaves its registration behind, and once another process got its process id, Droppen took the session for one still attached to a live CLI: its status said so, and Droppen would not send to it. On a Mac, Droppen now also checks that the process at that id is the one that registered; on Linux it goes by the process id alone, as before.

### Security fixes

- The server (and the one inside the desktop app) and the desktop app itself use url 2.5.9, which fixes RUSTSEC-2026-0592: the url before it could overflow its stack when asked for the origin of a `blob:` URL nested in another (`Url::origin()`).
- The desktop app uses cookie 0.18.3, which fixes RUSTSEC-2026-0594: the cookie before it could repeat the nonce of an encrypted (private) cookie in a process that forks.

### For developers

- The server's API: in `GET /api/sessions` and `GET /api/sessions/{source}/{id}`, a Claude Code session's summary has an optional `agentName` while its CLI runs, read from `name` in the CLI's registration (`sessions/<pid>.json` in its config folder) on every read and never cached. A server from before this sends none. On a Mac, a registration counts as live only while the process at its pid started no more than 5 s after its `startedAt`; on Linux, where a clock step can move a process's start time, the pid alone decides.
- `docs/relay-and-plans.md` §2.14 has the slow state and the bounds of the relay path's new rule. The connection log's events and its privacy rules are at the top of `web/src/lib/connection-log.ts`, and `docs/manual.zh-CN.md` has an entry for it.

## v0.2.141 更新内容

### droppen.app 上

- **慢速连接在数据还在到达时不再断开。** 在慢速链路上（大约 1 Mbps 或更慢，比如信号差的手机网络），经 droppen.app 到设备的连接以前可能每隔几秒就断开、重连，反复如此。页面每 5 秒用一个小探测检查一次经中继的路径，一个探测 10 秒没有回答就关闭连接，尽管数据一直在到达：在慢速链路上，探测的回答排在已经在路上的数据后面。每次新的连接又把同样的数据重新要一遍，链路又被占满。现在，只有一个探测 10 秒没有回答、而且 10 秒里什么都没收到时，页面才关闭连接。真正断掉的路径仍会被替换，在它送来最后一点数据后 15 秒内；手机网络上几秒的停顿不会被当成断开。有一个已知的限制：慢于约 100 kbps 的上传可能超过 10 秒收不到设备的任何回应，所以它的连接仍可能被当成断开而关闭。
- **连接条显示「慢」，不再显示一个没测到的往返。** 在这样的链路上，连接条以前常把中继的往返显示成 *5001 ms*：那其实是最早一个探测等了多久还没有回答，不是往返时间。现在，一个探测 5 秒及以上、并且比上次测得的往返还久没有回答时，连接条用红色显示「慢 · ≥5 秒」（之后是「≥10 秒」等，按整秒），悬停卡片和读屏标签也这样说。回答一到，就又显示测得的往返。
- **可以查看、也可以发送的连接日志。** droppen.app 现在会记下这个浏览器与你的设备之间的连接做了什么，可以在页面上看，也可以在报告连接问题时附上发送。打开方式：顶栏里「设备」前面的脉搏图标（窗口宽度 640 px 及以上）；连接时路径悬停卡片里「更换中继…」下面的「连接日志…」；或者「我的设备 → 这台设备 → 连接日志 → 打开」，任何宽度都可以。它记下：到 Hub 的连接；选了哪个中继、为什么；每个设备的端到端通道和它的路径（中继、Hub 或直连）；连接何时打开、何时关闭，由哪一方或哪个计时器关闭；探测和它们的回答；经这个连接的请求（路由、状态、耗时和大小）；连接条显示过的文字；以及传输数据期间，每秒一次的排队量和在途量。它在这个标签页的内存里保留最近 30 分钟，刷新页面后最近的部分也还在。默认打开「事件」，不含每秒的采样和探测；「全部」包含它们，「问题」只显示警告和错误。「复制」把当前视图最新的部分放到剪贴板，最多 60,000 个字符（放得进一个 GitHub issue），开头写明网页构建、设备上 Droppen 的版本、浏览器和网络；「下载」把整份存成 `.txt` 文件；「清除」清空它。日志不含令牌、密钥和 cookie，不含会话或消息的内容、文件和文件夹的名称与路径、设备和账户的名称、邮箱地址、IP 地址和主机名，也不含完整的 URL；设备和账户的 ID 换成用本浏览器的随机盐算出的哈希，不是 Droppen 自己说的文字一律不记。它不会发到任何地方：只有你复制或下载时，日志才离开浏览器。

### 会话

- **Claude Code 会话显示它的 agent 名称。** 其他 agent 会话给一个正在运行的 Claude Code 会话发消息时，用的是它的 agent 名称（通过 `ListAgents` 和 `SendMessage`），而不是「复制会话 ID」复制的会话 ID，所以一个项目里有几个会话时，很难分清该发给哪一个。现在 Claude Code 会话的 CLI 运行时，会话标题栏会在一个带 @ 图标的标签里显示这个名称，点一下就复制。会话列表的菜单在「复制会话 ID」后面多了「复制 agent 名称」。在 droppen.app 上，名称只在设备本身回应之后才显示，不会来自离线副本：离线副本里可能还留着一个已经退出的 CLI 的名称。Codex 和 ACP 会话没有 agent 名称。
- **在 Mac 上，崩溃的 Claude Code CLI 不再被当成还活着。** 崩溃的 Claude Code CLI 会留下它的登记文件，一旦另一个进程用上了它的进程号，Droppen 就把这个会话当成仍连着一个活着的 CLI：会话的状态这样显示，Droppen 也不给它发消息。现在在 Mac 上，Droppen 还会检查这个进程号上的进程是不是登记的那一个；在 Linux 上仍只看进程号，和以前一样。

### 安全修复

- 服务端（以及桌面 App 内置的服务端）和桌面 App 本身使用的 url 升级到 2.5.9，修复了 RUSTSEC-2026-0592：之前的 url 在求一个嵌套在另一个 URL 里的 `blob:` URL 的源（`Url::origin()`）时可能栈溢出。
- 桌面 App 使用的 cookie 升级到 0.18.3，修复了 RUSTSEC-2026-0594：之前的 cookie 在会 fork 的进程里，加密（private）cookie 的随机数（nonce）可能重复。

### 面向开发者

- 服务端 API：在 `GET /api/sessions` 和 `GET /api/sessions/{source}/{id}` 里，Claude Code 会话的摘要在它的 CLI 运行时带一个可选的 `agentName`，每次读取时从 CLI 的登记文件（它配置目录下的 `sessions/<pid>.json`）里的 `name` 读出，从不缓存。旧版本的服务端不发这个字段。在 Mac 上，一份登记只有在它进程号上的进程启动时间不比登记里的 `startedAt` 晚 5 秒以上时才算活着；在 Linux 上，时钟跳变可能改变进程的启动时间，所以仍只看进程号。
- `docs/relay-and-plans.md` 2.14 节写了「慢」的状态和中继路径新规则的界限。连接日志的事件和隐私规则写在 `web/src/lib/connection-log.ts` 的开头，`docs/manual.zh-CN.md` 也有它的条目。
