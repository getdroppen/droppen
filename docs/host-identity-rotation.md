## 0. 结论

- **能做成自动的，但要把它挡住谁、挡不住谁说清楚。**
  - **挡住**拿着旧身份钥、但在换钥那一刻没有冒充这台 host 的人。这是常见情形：丢了的手机、换掉的旧浏览器、拷走了 0600 文件的脚本。换完之后，旧钥登录不了 Hub，拿不到任何新的内容密钥，接不了任何设备的握手，写出的流头也没人认。
  - **分不出**在换钥那一刻也在线、冒充这台 host 的人。他和真电脑握着完全相同的秘密，任何不经过那台电脑本身的协议都分不出两者。
    - 设计保证这种情况**不会悄无声息**：真电脑在线时，换钥自动作废，并告警。
    - 真电脑离线时，攻击者可以赢。真电脑一上线就会被发现，这台设备被隔离，转为「在那台设备上确认」。
    - 结果都不比今天差：今天这个人能一直冒充下去，直到你重新注册。
  - **「在那台设备上确认」（高保障档）**：设备本机显示一串代码，你在管理设备上输入。它保证换到的一定是真电脑，与重新注册同等。但它保留 id 和一切，也不用输注册码。
  - **都挡不住后门**：攻击者能控制期间改过的程序、加的开机任务、加进去的 SSH 公钥。这时重新注册同样没用，只能排查或重装。
- **协议（每步一行）**
  1. admin 设备在 Hub 登记一次换钥请求（只交 nonce 的哈希）。Hub 把这台 host 标为「待换」，暂停它的设备角色。
  2. admin 经端到端通道调用 host 的 `POST /rh/rotate {nonce, eph, 链视图, 保障档}`。它属于 Posture 路由：只给 admin，要求 12 小时新鲜度。
  3. host 生成新种子，暂存为 `machine-key.next.json`，然后回答：新签名钥、新 DH 钥、旧钥签名、新钥签名、DH 确认 MAC。两把钥签的是同一份 `rh/v1 host-rotate` 证明体，内容是账户、host、新旧四把公钥、链视图、nonce 和保障档。
  4. host 用**以旧钥登录着的 Hub 连接**把证明交给 Hub 暂存。之后的窗口 T（默认 2 分钟）里，每个以旧钥登录为这台 host 的连接都必须用新钥确认，否则暂存作废。
  5. 窗口过后，admin 写 `[RotateHostKey{host, 新钥, 证明…}, KeyEpochs{host: 下一轮}]`。`RotateHostKey` 是链 v3 的新动作，20 号；Rust 与 TS 两份验证者都要验那两把签名。
  6. Hub 存下条目的同时：把这台 host 登记的钥（agent 角色与设备角色两处）换成新钥，把旧钥记进历史，删掉给它的信，吊销它的设备会话。之后吊销它的中继票据，用 4005 关掉旧钥的连接。
  7. host 在链上看到条目与自己暂存的一致，就原子地换上新种子、删掉旧种子，并在进程内重启链接。各设备按链上的新 DH 钥重新握手。
  8. 新一轮 `MK` 只封给新 DH 钥，并且带重加密：流按新纪元改名重建，新流头只用新钥签。读者从网络上只认链上当前那把钥签的流头。
  9. 换完之后谁再用旧钥登录，Hub 都会拒绝，并把带签名、可验证的证据发给每台设备。页面随即隔离这台 host，直到在那台设备上确认、再换一次。
- **什么时候跑**：移除、降权或收窄「谁可以控制它」之后立刻跑，对象是每台受影响的 host，包括经别的 host 间接够得着的（§4.1）。
  - 在线的 host 约 2 分钟换完。
  - 离线的排队，上线后由任一 admin 页面自动完成。
  - 「先移除，再重新添加」退到「更多」里，只留给旧版 agent 和 v2 账户。
- **兼容**：新动作会让不认识它的验证者验链失败。所以采用与链 v3 相同的门槛：账户里每台 host 都声明了 `rotate/1`，并且 Hub 打开了 `DROPPEN_HUB_HOST_ROTATION`，才收这种条目。
  - 读的一侧先全部发版，写的一侧后发版。
  - 没有回头路：一个账户写下第一条换钥条目后，读者就不能退到不认识它的版本以下。
- **实现**：分 R1–R6 六个阶段（§6）。§7 的问题已定。

| 按纪元命名的流 | 一次轮换立刻给索引与状态改名，会话按新名字重建（带重加密时立即），旧名字确认被取代后才删 | `S/agent/streams/naming.rs` | 换钥沿用它，新流头只用新钥签 |
| 心跳流头 | 每条流每 5 分钟重签一次流头（`HEARTBEAT_EVERY`，每轮至多 20 条） | `S/agent/streams/mod.rs` | 换钥后几分钟内，每条流都有新钥签的头 |

**今天的「重新注册」丢掉什么**（自动换钥都留着）：

- **id**：从 `m-…` 变成新的 `d-…`。所有按 id 记的东西都失效：
  - 它自己的接受策略、别的 host 名单里的它（`SetAccept`）；
  - `/v1/main-device`、屏幕里带 `machine` 的格子；
  - 钥环 `mk/<host>/…`、通行密钥包 `pk/m/<host>/…`；
  - 设备名。
- **云端数据**：旧 id 下的流。会话能从本机 transcript 重建，只在云端的会丢。
- **一次告警与名额**：每台设备都收到一条「新 host 加入」要确认，替换期间还占一个 `hosts.max` 名额。
- **一次到场**：必须到那台电脑上输入注册码。

## 2. 威胁模型

### 2.1 攻击者

- **A 持有一份 host H 的旧种子 S0**，也就是旧签名钥 `sig0` 与旧 DH 钥 `dh0`。
- **D3 之下，A 往往还有 H 上能读到的一切**：
  - `state.json`、`machine-keys.json`（H 各轮旧 `MK`）、`streams.db`；
  - `aggregator/keys.json`（放行 H 的别的 host 的旧轮 `MK`）、`copies.db`；
  - Bark 设置、`~/.claude/.credentials.json`、SSH 钥。
  - 所以「H 有、A 没有」的秘密不存在。
- **两种 A**：
  - **被动**：拿着，换钥那一刻不动。
  - **主动**：在线，以 H 的身份登录 Hub 或中继，抢着回答发给 H 的通道。
- **两种 Hub**：诚实；或恶意（与 A 串通，可以扣消息、乱排、对谁撒谎，但伪造不了签名，也解不开密文）。
- **前提**：A 失去控制之后，H 本身是干净的，没有留下后门。不满足这一条时，什么协议都没用，见 §2.3。

### 2.2 换钥必须保证的

下表说的是换钥条目提交之后，旧钥还能做什么。

| 旧钥想做的事 | 诚实 Hub | 恶意 Hub | 靠什么 |
|---|---|---|---|
| 以 agent 角色登录 Hub（在线态、收信、写流、领 agent 票据） | 拒绝：Hub 登记的这台 host 的签名钥在存条目的同时换掉，已连着的用 4005 关掉 | Hub 可以放它进来，但它在那里拿到、写出的东西没人认（下面几行） | Hub 登记的公钥；`HubLogin` |
| 以设备角色（设备会话、信箱、订阅、设备票据） | 拒绝：它作为设备登记的钥同时换掉，旧会话吊销；「待换」期间就已暂停（§4.3） | 能给它旧纪元的密文，那些钥它本来就有 | 同上 |
| 拿到新的内容密钥 | 拿不到：新一轮 `MK` 在链上提交，只封给新 DH 钥；给 H 的旧信全部删掉 | 同左（密码学保证） | `KeyEpochs` 提交，带发送方认证的封装，只封给链上当前的钥 |
| 接设备的握手（冒充 H，收你的输入） | 接不了：设备按链上的新 DH 钥做 IK | Hub 对某台设备扣住换钥条目时，那台设备仍连旧钥，直到它从别处拿到链（别的 host 的握手回复带着链后缀）。与「扣住移除」同类 | 链；握手回复带链后缀 |
| 以 H 的身份控制别的 host | 不行：别的 agent 按链上 H 的新钥准入（H 自己的 hello 会把条目带过去） | Hub 扣住条目时，别的 host 最多再信旧钥 7 天（控制类新鲜度，聚合器文档 §3.4） | 链与新鲜度 |
| 写 H 的流（状态、索引、会话） | Hub 拒收旧钥签的流头 | 读者照样拒收：网络上来的流头只认当前钥 | 流头签名；按纪元改名重建 |
| 中继 | 提交时吊销 H 的旧票，新票绑新签名钥 | 票据只是准入，通道两端仍是端到端的 Noise | 票据的 `sign_key` |
| 推送 | 提升时 agent 换一把新的 VAPID 钥、忘掉旧订阅（新钥做好之前，经通道来的 `GET /api/push/vapid`、`POST /api/push/subscriptions` 回 503 `push_renewing`，页面稍后再取）；页面看到换钥条目就退订旧订阅（推送服务随即作废旧端点），按新 VAPID 钥重订 | 同左；没打开过页面的设备在下次打开前，旧端点仍可能收到伪造的提醒（只有提醒，读不到内容） | 推送服务按订阅绑定 VAPID 钥 |

### 2.3 换钥保证不了的

- **H 本机的告警靠收到那一条**：真 H 要判定「身份已在别处更换」，得先收到并验过那条换钥条目。只经 Hub 同步链时，与 A 串通的 Hub 可以一直扣住它。那样 H 只会停在「登录被拒，等待同步」，不告警，也不签争议声明。别的 host 的握手回复带着链，是另一条来路。
- **复制当时已有的一切**：
  - H 上的 transcript、文件、凭据（Claude 登录、SSH 钥、云凭据）；
  - H 各轮旧 `MK`，以及 Hub 上用它们加密的旧密文；
  - `aggregator/keys.json` 里别的 host 的旧轮 `MK`、`copies.db` 里的明文。
  - 换钥只保护以后。别的凭据要你自己去对应的地方换，换完时界面会提一句（§7 问题 9，已定）。
- **后门**：A 能控制期间改过的二进制、开机任务、`authorized_keys`。新种子一生成就会被拷走。重新注册也一样没用。
- **换钥那一刻的抢答**（§3.6）：A 在线、真 H 离线（或 Hub 与 A 串通）时，A 可以把 H 的 id 换到自己的钥上。自动档保证的只是「不悄无声息、可恢复」。高保障档能防。
- **元数据**：Hub 看得到哪台 host、什么时候换了钥。没有新增的内容泄露。

### 2.4 与重新注册对比

| | 重新注册（今天） | 自动换钥 | 在那台设备上确认 |
|---|---|---|---|
| 要到那台电脑前 | 要，输注册码 | 不要 | 要，看一串代码，在手机或浏览器上输入 |
| id 与按 id 记的一切 | 全丢 | 留着 | 留着 |
| A 被动 | 挡住 | 挡住 | 挡住 |
| A 在线，真 H 在线，Hub 诚实 | 挡住 | 自动作废并告警，转确认 | 挡住 |
| A 在线，真 H 离线 | 挡住 | A 可能赢；真 H 上线即发现、隔离 | 挡住 |
| A 与 Hub 串通 | 挡住 | A 可能赢，Hub 能压下证据，只剩 H 本机的告警 | 挡住 |
| 后门 | 挡不住 | 挡不住 | 挡不住 |
| 对用户的影响 | 繁琐 | 无感（约 2 分钟） | 一次十秒的核对 |

## 3. 协议

### 3.1 参与者与总流程

参与者：

- **D**：admin 设备，即浏览器或手机上的 droppen.app。
- **H**：要换钥的 host。它的 agent 与本机控制端共用一个身份（聚合器文档 §3.3）。
- **Hub**、**中继**。
- **A**：见 §2.1。

```
D (admin)                         Hub                                 H（旧钥 K0）
 │ PUT /v1/rotations/H {nonce_hash} ▶│ 记请求；H 标为「待换」，暂停其设备角色
 │═══ E2E 通道（经中继，Noise IK → H 的 dh0）══════════════════════════════════▶│
 │    POST /rh/rotate {nonce, eph, chainSeq, chainHead, assurance}              │ 生成 S1 → machine-key.next.json
 │◀══ {signKey, dhKey, oldSig, newSig, mac} ═══════════════════════════════════│
 │ 验两把签名与 mac                  │◀── rotation_stage {…}（旧钥登录着的 agent 连接）│
 │                                   │ 验证、记 staged，开窗口 T
 │          …… 窗口内，每个以 K0 登录为 H 的连接都要用 K1 确认 ……
 │ POST /v1/chain [RotateHostKey, KeyEpochs] ▶│ 一并生效：换钥、旧钥进历史、删信、吊销会话
 │                                   │── 链条目 ───────────────────────────────▶│ 与暂存一致 → 换上 S1、删 S0
 │                                   │── 关闭 4005 rotated {fp} ──────────────▶│ 用 K1 重新登录；进程内重启链接
 │═══ 新通道（Noise IK → dh1）═════════════════════════════════════════════════▶│
 │    POST /rh/machine-key {新一轮, reencrypt: true}                             │ 按新纪元改名重建流
```

### 3.2 请求、证明与 DH 确认

**请求** `POST /rh/rotate`

- 这是 agent 自己的路由，在 `S/agent/bridge.rs` 的 `ROUTES` 里归 `Posture`：只给 admin，并要求 12 小时新鲜度，与 `/rh/machine-key` 同档。
- 请求体：`{nonce: 16 字节, eph: X25519 公钥, chainSeq, chainHead, assurance: 0 | 1}`。

**agent 先检查**

- 自己是链上当前的 host。
- `(chainSeq, chainHead)` 在自己的链上。通道 hello 已带条目，通常已经补齐；不在就回 409，让设备先同步。
- 同一 nonce 的重复请求回同一份应答（幂等）；新 nonce 顶替旧的暂存。
- 声明了 `rotate/1`。旧 agent 没有这条路由，回 404，页面据此显示「版本过旧」。

**生成新种子**

- 用 OsRng 生成新的 32 字节种子 S1，写进 `agent/machine-key.next.json`。
- 0600，与 `KeyFile` 同格式，另带 `{nonce, chainSeq, assurance, createdMs}`。
- 绝不动 `machine-key.json`。

**证明体**（Rust 与 TS 逐字节相同，进互通向量）

```
标签 "rh/v1 host-rotate\0"
str16 account | str16 host | u64 staged_seq | staged_head 32
| old_sign 32 | old_dh 32 | new_sign 32 | new_dh 32 | nonce 16 | u8 assurance
```

- `old_sig`：旧签名钥（链上当前的 `sig0`）对证明体的签名。
- `new_sig`：新签名钥对证明体的签名。
- `mac = HMAC-SHA256(DH(new_dh 私钥, eph), "rh/v1 rotate-confirm\0" ‖ 证明体)`：证明它握有新 DH 私钥。签名证明不了这一点：两把钥由同一颗种子各自展开，外人验不了它们的关系。

**应答** `{signKey, dhKey, oldSig, newSig, mac}`。`assurance = 1` 时，agent 同时在本机显示代码（§3.7）。

**D 再检查**

- 两把签名、`mac` 都成立；
- 新钥从没在链上出现过；
- `assurance` 与请求一致。
- 有一项不过就放弃，并记下「这台设备的应答不对」（§4.2）。

**为什么链上还要旧钥签名**

- 通道本身已经证明应答来自 `dh0` 的持有者。旧钥签名写进链，是给**第三方**验的：其它设备、各 agent、Hub。
- 有了它，一个 host 的 id 只能在两方都同意时改绑：一台 admin 签条目，**再加上**当前身份钥的持有者同意。
- 只偷到一台 admin 设备的人因此只能移除 H，不能把 H 的 id 连同它的接受策略、主设备地位一起绑到自己的钥上。今天他能做到的，是移除 H 再加一台自己的机器，而那会是一台新 id、对所有设备告警的新 host。

### 3.3 Hub 暂存与窗口

**登记**：`PUT /v1/rotations/{host} {nonce_hash?, assurance}`

- 需要 admin 的设备会话。
- 带 `nonce_hash` 是一次尝试，有效 10 分钟。不带只把 H 标成「待换」，用于离线的 host。
- 检查：H 是本账户当前的 host、声明了 `rotate/1`；同一 host 同时只有一次尝试，另一个页面的尝试还在跑时回 409 `rotation_in_progress`。
- 限流：每台 host 每小时 6 次、每天 20 次。
- Hub 记下这次请求，向账户的设备推 `rotation {host, state}`。
- `DELETE /v1/rotations/{host}` 撤回。`GET /v1/rotations` 列出状态、原因、`ready_ms` 与争议（§3.8）。
- 这些接口、状态与错误码的细节见 `docs/hub-api/http.md` 的 Identity key renewals 一节。

**暂存**：H 在自己以旧钥登录着的 agent 连接上发 `rotation_stage {nonce, staged_seq, staged_head, sign_key, dh_key, assurance, old_sig, new_sig}`。只在这条连接的 `welcome` 带了 `rotate/1` 时才发（§5.6「线上兼容」）。Hub 检查：

- `SHA-256(nonce)` 对得上一次开着的尝试；
- `(staged_seq, staged_head)` 在 Hub 的链上；
- `old_sig` 按 Hub 登记的这台 host 的当前签名钥成立，`new_sig` 按新钥成立；
- 新钥从没在链上出现过。
- 通过后状态为 `staged`，记下 `staged_ms`。
- **只收 agent 连接交来的暂存**，不收页面交来的。冒充的人想暂存，就得自己以 H 的身份登录 Hub。一个 id 只能留一条连接，所以他就得顶掉真 H。
- **只收这台 host 当前那条 agent 连接交来的暂存**：
  - 被顶替（4001）的连接在顶替的那一刻就同步标为死连接，之后它读到的帧一律丢掉：关闭发出之后，连接还可能交来几秒数据，不能指望它自己停。
  - Hub 暂存时核对：交来的连接必须是这台 host 此刻的当前 agent 连接。
  - 纵深防御：暂存的那一刻，这台 host 其它每条还开着的 agent 连接都欠一次确认，规则同窗口内的登录。
  - 否则 A 可以在已被顶替的旧连接上暂存，而真 H 一直连着、什么都不欠，T 一过就提交。

**窗口 T 的规则**（默认 120 秒，`DROPPEN_HUB_ROTATION_WINDOW_SECS`；诚实 Hub 执行）

- 窗口里每一次以 H 的旧钥登录 agent 角色：这条连接的 `agent_info` 一声明 `rotate/1`（features 在 `welcome` 之后才到），Hub 就发 `rotation_pending {fp, staged}`。没声明 `rotate/1` 的连接收不到它。
- 对方要在 `welcome` 之后 20 秒内回 `rotation_ack`：新钥对 `"rh/v1 rotate-ack\0" ‖ account ‖ host ‖ 证明体哈希 ‖ 本连接登录用的 nonce` 的签名。
- **分级的证据**：
  - 窗口内任何一次以旧钥登录、没有确认的，**都让暂存作废**。不做「不作废、再等一次」。
  - **`interrupted`**：
    - 适用于：对方在回答之前关了连接或超时断开，或者是 Hub 自己出错。
    - 处理：作废，但**不记**克隆证据，**不转** 30 天只收高保障。页面在每小时 6 次之内换新 nonce 自动重来，不要你输代码。
  - **升级为克隆证据**：
    - 适用于：
      - 回 `rotation_unknown`；
      - 确认答错；
      - 连接到期限时还开着却一声不吭，包括从没声明 `rotate/1` 的；
      - 出现 `conflict`；
      - 24 小时内第二次 `interrupted`。
    - 处理：作废，记争议证据，这台 host 30 天内只收 `assurance = 1`。
  - Hub 把原因如实交给页面（`interrupted` 与 `not_acked`、`conflict` 分开）。页面对 `interrupted` 不要求在设备上确认。
- **顶替**（§7 问题 10）：
  - 有一次开着的尝试（attempt）时，这台 host 的 agent 连接被顶替：这次尝试作废，原因 `replaced`，与 `interrupted` 同级，页面换新 nonce 重来。
  - 已暂存（staged）时被顶替：新登录照窗口规则必须确认，否则按上面的分级作废。
  - 两种都记日志，并向账户的设备推一条 `rotation {host, state, reason: "replaced"}` 提示。
  - 尝试之外的顶替不单独告警。
- 同一台 host 出现另一份不同的暂存：作废，原因 `conflict`。
- 24 小时没有提交：`expired`。

**为什么是 2 分钟**：agent 的重连退避封顶 30 秒（`S/agent/link.rs` `BACKOFF_MAX`）。被顶掉的真 H 在窗口内一定会重新登录、被要求确认。T 至少是它的 4 倍。

**提交**（Hub 收到含 `RotateHostKey` 的一批，`POST /v1/chain`）。必须同时满足：

- 状态为 `staged`；
- 条目里的钥、nonce、`staged_seq`/`staged_head` 与暂存一致；
- `now − staged_ms ≥ T`；
- 门槛满足（§5.6）。
- 否则回 409 `rotation_not_ready {reason, ready_ms?}`。
- 有克隆证据（§3.8）的 host，30 天内只收 `assurance = 1` 的换钥。这是纵深防御：页面本来也会这样做。

这些状态 Hub 都持久保存，重启不丢。

### 3.4 链条目 `RotateHostKey`（v3，20 号）

**编码**

```
20 RotateHostKey {
  host        str16
  sign_key    [32]     新 Ed25519
  dh_key      [32]     新 X25519
  staged_seq  u64      证明所对的链视图
  staged_head [32]
  nonce       [16]
  assurance   u8       0 自动；1 在那台设备上确认；其它值解码即拒
  old_sig     [64]
  new_sig     [64]
}
```

**规则**（`ChainState::apply`；Rust 的 `rules::*` 与 TS 的 `RULES.*` 用同一句话）

1. 只在 v3 条目里出现（`fixed_version() == 3`）；签名者是当前、活跃的 admin（聚合器文档 §3.2 规则 1）。
2. `host` 是当前、活跃的 host（`machine(host)`），不是待定，也没被移除。否则 `ROTATE_NOT_HOST`：「only a current device that runs AI renews its identity key」。
3. 新钥要规范、有效、不是小阶点。新钥（签名钥或 DH 钥）不能等于链上任何设备现在或以前用过的任何一把钥。否则 `ROTATE_KEY_REUSED`：「a renewed identity key must be one the chain never named」。这也挡住把 H 的身份撞到另一台设备的钥上。
4. `staged_seq < seq`，并且 `hash_at(staged_seq) == staged_head`。否则 `ROTATE_STAGED`：「the renewal was proved against another chain」。
5. `old_sig` 按 host **当前**的签名钥成立，`new_sig` 按新签名钥成立。否则 `ROTATE_PROOF`：「the renewal is not signed by both the old and the new identity key」。
6. 下一条必须是这台 host 新一轮 `MK` 的 `KeyEpochs`：复用 `host_key_due` 与 `HOST_KEY_NEXT`，同 `SetHost true`。Hub 拒收以这种欠账结尾的批。
7. 若这台 host 已经欠着一轮 `MK`（`host_key_due` 指着它），本条按今天的规则被 `HOST_KEY_NEXT` 拒绝。收窄与换钥分两批写，不放宽这条规则。
8. **退役钥不再回来**（不止本条）：任何加入设备的动作（`AddDevice*` 等），以及任何激活设备的动作（`ApproveDevice`、`PasskeyActivate`、`ActivateRecovered`），都拒绝链上已退役的钥（签名钥或 DH 钥，任何设备的）。否则持 `K0` 的人可以在换钥之前以 `K0` 发起一次待定加入，换钥之后再凭同步来的通行密钥自己激活。加入一侧与激活一侧都进两份验证者与互通向量，先于打开换钥。
9. **账户的换钥档位**：v3 新动作 `21 SetRenewalPolicy { always_assured u8 }`。
   - `always_assured` 只取 0、1，其它值解码即拒。只有当前、活跃的 admin 签；只在 v3 里出现。
   - 打开期间，`assurance = 0` 的 `RotateHostKey` 被拒：`ROTATE_NEEDS_ASSURANCE`「the account asks for every renewal to be confirmed on the device」。
   - Hub 只在换钥的门槛（每台当前 host 都声明了 `rotate/1`，且开关打开）满足时才收这一条，所以读得懂 20 号的 host 也读得懂 21 号。
   - 它记在链上，不是 Hub 上的状态。
10. **为换钥暂停控制（覆盖层）**：v3 新动作 `22 RenewalPause { op [16], phase u8, removals [(host str16, ids [str16])] }`，只有当前、活跃的 admin 签。
    - `phase` 只取 0（开始）、1（完成）、2（取消），其它值解码即拒。
    - **开始**：
      - `op` 链上从没用过。
      - `removals` 逐台列出 host 与要从它的放行里**暂时去掉**的设备或 host 的 id。host 是当前 host，不重复；每台至少一个 id；id 是链上有过的设备，不重复，不是这台 host 自己，也**不是当前的 admin**（D1：admin 的控制不靠名单，暂停它既不必要，也会漏出暴露计算）。
        - removals 必须是规范的：host 按字节序排列，每台的 id 也按字节序排列，否则拒绝。编码器从不截断数目。
        - **大小上限**：整条条目编码后的字节数，不超过每一种传输（握手 hello、`CHAIN` 帧）都装得下的上限，两份验证者用同一个数。超过就拒绝；TS 的编码器抛错，不截断。
    - **完成、取消**：`op` 是一个开着的暂停，`removals` 为空，每个暂停只结束一次。任何当前、活跃的 admin 都能签，不必是开始它的那一位。
    - **生效**：暂停开着期间，每一份验证者、每台 agent 的准入、每个页面，都按「`SetAccept` 定下的底子，减去所有开着的暂停去掉的边」来算有效的放行（`may_control`、`authorize_control` 都一样）。
      - 完成或取消，这一层就撤掉。
      - 不写任何 `SetAccept` 去收窄或恢复。手改的 `SetAccept` 永远只改底子，暂停从不碰它。
    - **开始它的 admin 后来被移除或降权**：暂停照样有效。它只会收窄，失败时安全。任何当前 admin 都能结束它，但页面**从不自动结束**这样的暂停，执行器也不碰它，一律要人确认。
    - **结束时补封钥**（D2）：暂停结束、某条边恢复时，页面把那台 host 已提交的各轮 `MK`（用途 5）补封给重新被放行的一方，让只是暂时被暂停的设备拿回较早的纪元。暂停期间照旧不封。
    - **查询**：开着的暂停（op、开始的序号、签名者、去掉的边），以及某台 host 此刻被暂停的边。
    - **agent**：在每条传输上照这一层准入；失去准入的已开通道会被关掉，同 `SetAccept`。
    - 与 21 号同在同一轮读者发版里，Hub 同样只在换钥门槛满足时才收。

**效果**

- 当前两把钥进 `DeviceRecord.retired: Vec<RetiredKeys{sign_key, dh_key, until_seq, by_assured}>`，再把 `info` 换成新钥，记 `rotated_seq = seq`。
- `by_assured` 记的是换掉它的那一条是不是 `assurance = 1`，§3.8 用。
- 接受策略、flags、`ran_ai`、`via_*` 都不变。

**新的查询**

- `retired_keys(id)`。
- `keys_at(id, seq)`：第 `seq` 条生效时这台设备的钥。验存下的流头（§5.4）和争议证据（§3.8）用。
- `ever_named(key)`。

**不变的**：`authorize_device`、`may_control`、`machine()`、`check_attestation` 都读 `info`，自然只认新钥。作证只有 admin 做，与 host 的钥无关。

**告警**（聚合器文档 §3.2 的表加一行）

- 每台设备显示一条「提示」级的变化：「X 更换了身份密钥 · 新指纹 …」。
- 每台 agent 照常 `note_change`，每台 host 每小时至多 4 条（N3）。
- 被换钥的 host 自己：若条目里的钥不是它暂存的，那就是**克隆证据**，发高级告警（§3.5）。
- 为什么不要求每台设备确认「是我做的」：这一条要旧钥签名，一台 admin 单独做不出来（§3.2）；而真正能发现冒名换钥的，是被换掉的那台 host 自己。

v2 没有这个动作。还在 v2 的账户照旧提示重新注册，先升级到 v3（D4）。

### 3.5 提交之后

**Hub（存条目的同时）**

- 把这台 host 登记的签名钥与 DH 钥换成新钥，条件是登记的还是条目里的旧钥；对不上就整批 409。它作为设备登记的那一份同样处理（那一份可能还不存在）。
- 旧钥进历史，记下 host、两把钥、退役的链序号与时间、是否由 `assurance = 1` 退役（`by_assured`）。
- 删掉收件人是 H 的全部信件。它们都封给了旧 DH 钥：两种角色、用途 2、4、5 都在内。
- 吊销设备 H 的全部设备会话。
- 暂存记为 `committed`，清掉「待换」。

**Hub（存条目之后）**

- 先把条目推给订阅者，H 自己的连接也会先收到。
- 再用 **4005** `rotated {fp}` 关掉 H 的 agent 与设备连接。这是新关闭码：「这台设备的身份钥已更换：请用新钥登录」。
- 此前签给 H 的中继票据一律吊销。

**H（agent）**

- **提升**：收到条目或 4005，并且新钥等于 `machine-key.next.json` 的钥时：
  1. 用新钥登录；
  2. 在 Hub 给的链上验到这一条；
  3. 把 `next` 原子改名到 `machine-key.json`，旧种子随之被替换；
  4. 进程内依次重启链接、中继连接、本机控制端与流的写方。本机 AI 会话、终端 shim 不受影响。
  5. 本机设置的「Droppen」一节写「已更换身份密钥 · 14:02 · 因为 Y 被移除」。
- **崩溃安全**：启动时若 `next` 在，先用它登录，再用旧钥。Hub 回 `denied`（还没提交）就退回旧钥。链上已经是新钥时就补做提升。提升只在链上验到条目之后发生，所以撒谎的 Hub 骗不走它的旧种子。
- **不拿旧钥误伤自己**：
  - 只要还留着 Hub 收下过的暂存种子，**每一次**登录都先试它们。只有每一把都被回 `denied`（说明都没提交），才退回旧钥。
  - 这对窗口内的重连、睡眠后醒来、链还没追上的情形都一样。否则错过提交的真 H 会以退役钥登录，自己把自己隔离掉。
  - 在登录结果确定当前钥之前，本机控制端不以设备角色换会话：待换期间 Hub 本来也暂停它的设备角色。
  - 没被 Hub 收下的暂存（超时、被拒）随即丢掉，不留着。
- **不是自己暂存的钥**（`next` 不在，或钥不同）：说明别处有人握着它的旧钥，并且抢先换掉了它的身份。
  - 记高级告警 `foreign_rotation`：在本机界面、日志、Bark 上提示，Tauri 应用还发系统通知。
  - 停掉链接，保留旧种子。它之后每一次以旧钥登录，都是 Hub 记下的争议证据（§3.8）。
  - 本机设置显示红字「这台设备的身份在别处被换掉了」，下一步是「在这台设备上确认」（§3.7）。

**其它设备与 agent**

- **关通道**：页面与本机控制端看到条目后，关掉响应方静态钥不等于链上新 DH 钥的通道，重新握手。握手失败时先同步一次链再重试：对方可能比自己先换了钥。
- **交新钥**：做这次换钥的 admin 用 `deliverMachineKey` 交出新一轮 `MK`，`reencrypt: true`。先走通道（对 `dh1`），再走信箱（封给 `dh1`）。
- **补封与作证**：再把放行 H 的 host 的已提交 `MK` 补封给 H 的设备角色（用途 5，§5.3），并为新链头签 `ATTEST`。
- **别的 host**：H 的 hello 带着这一条，它们自己补链。

### 3.6 抢答：持旧钥的人先回答怎么办

| # | 情形 | 结果 |
|---|---|---|
| 1 | A 被动，真 H 在线 | 成功。之后 A 的旧钥什么都做不了。A 若再试着登录，就成了争议证据（§3.8） |
| 2 | A 被动，真 H 离线 | 排队；H 上线后照情形 1 完成 |
| 3 | A 在中继上顶掉 H、抢答了 D 的请求，真 H 仍连着 Hub | A 要暂存，就得以旧钥登录 Hub，顶掉 H。H 在 30 秒内重连、顶回来，被要求用 A 的新钥确认，确认不了：`not_acked`，作废。页面告警「另一处握着 X 的身份钥」，这台 host 转高保障 |
| 4 | 真 H 已暂存，A 在窗口内以旧钥登录 | A 确认不了：`not_acked`，作废，转高保障。A 能逼你到电脑前确认一次，仅此而已；确认过的换钥不能再被争议（§3.8） |
| 5 | A 在线，真 H 离线（合盖、断网），Hub 诚实 | **A 赢**：H 的 id 绑到 A 的钥上。H 一上线，以旧钥登录被拒，Hub 记下证据推给每台设备，页面隔离 H。从 A 赢到 H 上线这段时间，A 冒充 H，与今天一样（今天 A 能一直冒充，直到你重新注册）。真 H 这时只剩退役钥，**原地恢复不了**：移除这个 id，真 H 生成新种子，以新 id 重新添加（§3.8「只剩退役钥时」） |
| 6 | A 与 Hub 串通 | Hub 能替 A 隐瞒确认、压下证据，**A 赢且可能不被设备看见**。剩下的信号：H 本机的告警与 Bark；H 写出的流全被读者拒收，看上去停在换钥那一刻。与架构文档 §7「被盗机器 + 恶意 Hub」同级。只有高保障档能防 |

**什么能把真 H 和 A 分开——老实说**

- **秘密**：分不开。A 复制了全部，包括 Bark、`state.json`、`streams.db`。这一步之后真 H 新产生的东西（新的 transcript、新的流记录），A 也能经 Hub 读到它的密文和流头。
- **预先承诺下一把钥（KERI 式的 pre-rotation）**：下一颗种子也在同一块盘上，A 会一起拷走。只有放在 A 读不到的地方才有用：以后 Tauri 应用的钥匙串或 Secure Enclave（§5.5）。现在不做。
- **请求 nonce + 新旧钥双签**：防得住 Hub 凭空塞钥、重放旧证明、一台 admin 单独改绑。A 自己也做得出来，所以防不住 A。
- **在线**：这是唯一能自动利用的差别。A 想赢，必须在窗口里是唯一以旧钥登录为 H 的一方。真 H 只要进程在跑、有网，每次重连都会被要求确认。所以在诚实 Hub 下，A 只能在真 H 离线时赢。
- **那台电脑本身**：只有它的屏幕是 A 碰不到的。高保障档就建在这上面。
- **Hub 的视角**：诚实 Hub 看到同一个 id 的两处登录（4001 顶替）、确认失败、退役钥的登录，都变成告警。恶意 Hub 可以什么都不说。

**失败时安全的方向**：任何一次抢答，要么让换钥作废（什么都没变，并且知道了有人握着旧钥），要么让赢家在真 H 回来时被隔离。最坏的结果是逼你到电脑前确认一次，不会悄悄把 id 永远交给别人（串通的 Hub 除外，见情形 6）。

### 3.7 高保障：在那台设备上确认

**什么时候用**

- 账户开了「更换身份密钥时总在设备上确认」（默认关，§7 问题 1）；
- 出现过克隆证据：`not_acked`、`conflict`、退役钥登录；
- 这台 host 已被隔离；
- 手动更换时你选了它。

**流程**

1. 请求带 `assurance: 1`，其余同 §3.2。
2. H 在本机显示代码 `SAS = base32(SHA-256("rh/v1 rotate-sas\0" ‖ 证明体)[..5])`，8 个字符，写作 `XXXX-XXXX`，10 分钟有效。显示在：
   - 本机网页设置的「Droppen」一节；
   - Tauri 应用的窗口与系统通知；
   - 无界面的服务器：`droppen agent status`（经 SSH）。
3. D 显示「在 X 上打开 Droppen，输入它显示的代码」，你把代码输进来。
4. D 用它收到的应答算同一个 SAS，两者一致才继续：照常暂存、窗口、提交，条目 `assurance = 1`。
5. 输不出来或对不上就放弃，并告警「X 没有显示代码，或代码不同：可能有别处在冒充它」。

**为什么成立**

- A 抢答时，真 H 根本没收到请求，屏幕上没有代码；A 也没法让真 H 的屏幕显示他的代码。
- A 看不见真屏幕，也就无从在自己的应答里凑同一串代码（40 位）。
- Hub 同样碰不到那块屏幕。
- 要求「输入」而不是「比对」：比对容易被随手点过。

**它仍然不管的**：后门（§2.3）。经 SSH 看代码，前提同样是那台机器干净。

### 3.8 旧钥再出现：争议与隔离

**证据：退役钥签的争议声明**

- **为什么不用登录当证据**：
  - 两个墙上时钟定不了先后。「登录时间晚于退役那一条加 5 分钟」挡不住时钟不一致时重放换钥之前的登录。
  - 它还会漏掉真 H：A 在 H 离线时赢了，H 五分钟内回来，它唯一那次退役钥登录过不了时间规则；同时 Hub 按「几秒之内只记录」也不隔离；之后再也不会有新证据。
- **争议声明**（`rh-proto`，Rust 与 TS 逐字节相同，进互通向量）：
  - 标签 `rh/v1 rotate-dispute\0`；
  - 证明体 `str16 account | str16 host | u64 seq | entry_hash 32 | new_sign 32`；
  - `seq` 是被争议的那条 `RotateHostKey`，`entry_hash` 是它的链哈希，`new_sign` 是它装上的新签名钥；
  - 由那一条退役的签名钥（`keys_at(host, seq − 1)`）签。
- **它为什么成立**：它绑着那一条的哈希，只有看到那一条之后才签得出来。所以不需要比较时间，Hub 也拿不出换钥之前的东西冒充。
- **谁来签**：判定「身份已在别处更换」（§3.8「只剩退役钥时」）的那台 H 的 agent，用它手里的退役钥签。
  - 它把声明存在本机，经 `POST /v1/rotations/{host}/disputes` 交给 Hub，一直重试到 Hub 确认收下。
  - 交声明不需要会话：退役钥的签名本身就是凭证。
- **Hub**：
  - 用自己的链验过声明，存下，向账户的设备推 `host_dispute`，每台 host 每小时至多 4 条。
  - 隔离只认声明（规则见下面「隔离」）。
- **以退役钥登录**：照旧拒绝（4401 `rotated`，并给出到退役那一条为止的链），也照旧记录。它**只是信息**，不再让任何一方隔离这台 host。
  - 握着退役钥的 A 本来就能签声明，逼你确认一次（见下面「隔离」）。所以不认登录不丢任何东西，只少了误报。
- **设备**：用自己的链验声明（那一条是给这台 host 的 `RotateHostKey`、哈希对得上、签名出自 `keys_at(host, seq − 1)`）。Hub 伪造不出来，只能压下不发。
- Hub 自己出错（例如数据库出错）时，不记任何证据。
- 窗口内的 `not_acked`、`conflict` 同样记为证据，那时还什么都没提交。

**隔离**（页面执行，状态存在 Hub，所以每台设备、每次加载都看得到）

- 不再向 H 开通道，不再给 H 封任何钥。
- 自动换钥对它关闭，只走高保障。
- 诚实 Hub 同时不再签发去它的票，也不签发它的票。
  - 唯一的例外是**在设备上确认**：这台 host 有一次 admin 开的、`assurance = 1` 的尝试（attempt 或 staged）时，Hub 才为那台 admin 设备路由去它的通道，并签相应的票。
  - 页面也只为 `/rh/rotate` 这一次调用开这条通道，不封钥、不做别的。
  - 应答方若是 A，真屏幕上没有代码，你输不对，什么都不提交（§3.7）。
- 解除：链上序号大于证据所争议那一条的 `assurance = 1` 的 `RotateHostKey`，或 H 被移除。比较的是链序号，不是时间。
  - 前者只在**真 H 握着当前钥**时走得通（A 拿的是退役钥）。真 H 若只剩退役钥，见下面「只剩退役钥时」：只能移除。
- 由 `assurance = 1` 退役的钥再出现时，只记录、提示，不隔离：那一次是在真电脑上确认过的。所以 A 拿退役钥捣乱，最多逼你确认一次。
- 同理：一把由 `assurance = 0` 退役的钥，只有在它退役之后这台 host 还**没有**过一次在设备上确认的换钥时，才会让它隔离。否则同一把旧钥能一次次把它隔离、一次次逼你确认。
- 隔离只看设备自己验过的争议声明；Hub 单方面说的「隔离」只当作没验过的提示，不触发「先移除」的引导（扣着钥不给仍然可以）。`GET /v1/rotations` 总要带上让它隔离的那条声明。
- 页面把验过的声明按账户存在本机，只增不减，跨标签页也一样：Hub 之后不再给、或回 404，都不解除。只有自己的链上一条序号大于它所争议那一条的、`assurance = 1` 的换钥，或者这台 host 被移除，才清掉它。开通道、封钥之前先按它判断。

**只剩退役钥时：以新身份重新添加**

- **情形**：真 H 手里只有退役钥 `K0`。一是 A 在真 H 离线时赢了抢答（§3.6 情形 5）；二是 H 从换钥之前的备份恢复，换钥之后的种子随之丢了。
- **原地恢复不了，这是设计使然**：
  - 规则 5 要当前钥的签名，而当前钥在 A 手里，或已经没人有；
  - 高保障的请求按链发到当前的 DH 钥，也就是 A，真屏幕上不会出代码；
  - 以 `K0` 重新加入，被「退役钥不再回来」挡住（§3.4 规则 8）。
- **不加**让退役钥签换钥的规则：持 `K0` 的 A 同样能用它把身份抢回去，换钥就白做了。
- **agent 只凭链上验过的证据判定**：
  - **判定条件**：链上有一条给自己这个 id 的 `RotateHostKey`，验过签名与链头的连续性，新钥既不是自己的种子，也不是自己暂存的。只有这时才进入「这台设备的身份已在别处更换」。
  - **Hub 的 `rotated` 拒绝本身不算证据**，只意味着「先同步链」。否则一个恶意 Hub 只要说一句 `rotated`，就能逼诚实的 host 重新注册，丢掉它的 id、接受策略和主设备地位。
  - **证据从哪来**：登录被拒的连接上拿不到链，所以 Hub 以 `rotated` 拒绝时，先不关连接，最多 10 秒：
    - 它只收一条 `chain_sub {from}`，回从 `from` 到退役那条 `RotateHostKey` 以及紧跟的 `KeyEpochs` 为止的条目，不多给；
    - 然后用 4401 关闭。
    - agent 从自己的链头接着验。验不到（Hub 不给、给的接不上或签名不对）就停在「登录被拒，等待同步」，照常退避重试，不重新注册。
  - **判定之后**：
    - 停掉链接，发 `foreign_rotation` 告警（§3.5）；
    - 本机设置的「Droppen」一节给出「以新身份重新添加这台设备」；
    - 你确认后，它生成一颗**新**种子，旧种子改名留档，再走现有的注册流程：输入新的注册码，得到新 id。
  - **任何注册路径都不复用退役的种子**。今天 `enroll`（`S/agent/control.rs`）沿用已有种子，只有断开（unenroll）才删。改为：当前种子在链上已退役（或已改名留档）时，注册前一律生成新种子。`load_or_create` 与崩溃恢复永远不加载留档的种子。
  - **页面批准加入时**：被 `KEY_RETIRED` 拒绝的，解释成「请以新身份添加那台电脑」。
- **文案不能吓人，也不能误导**：这一状态也会出现在你把这台电脑**自己**换钥之前的备份恢复回来之后。所以本机与页面都写成「这台设备的身份密钥已在别处更换（比如从更换之前的备份恢复，或另一处握有它的旧钥）。要在这里继续用它，请以新身份重新添加」，不直接说「被冒充」。
- **页面**：隔离的 host 行的第一步是「去看 {id} 上的 Droppen」。按它显示的，二选一作为主操作：
  - **显示「身份已在别处更换」**：主操作是移除这个 id，然后到那台电脑上点「以新身份重新添加」，输入新的注册码。
  - **显示一串代码**：主操作是「在设备上确认」（真电脑仍握着当前钥，A 拿的是退役钥）。
  - 两种情形里，「移除」都只差一次点击。在它被移除或确认之前，别的 host 的 agent 仍按接受策略把握着当前钥的一方当作这台 host，所以行上一直写着这一点。
- **代价**：同重新注册（§1）。旧 id 下的接受策略、主设备、名单要重新设。只在这一种情形里付这个代价。
- **远端分不出**「从备份回来的真电脑」和「握着旧钥的别人」，所以这条路要你到那台电脑前，与重新注册同等。

### 3.9 考虑过、没采用的

- **host 用旧钥自签换钥，不要 admin**：A 一样能签，谁快谁赢，也没有窗口和门槛。保留「只有 admin 签链」这一条规则，验证者更简单。
- **新 id 加「继任」链接**：等于换了皮的重新注册，每个按 id 记的地方都要认继任关系。
- **只靠 admin 签，不要 host 的旧钥签名**：一台被偷的 admin 就能改绑任何 host 的身份。
- **暂存由页面交给 Hub**：A 只要在中继上抢答就够了，不必碰 Hub。只收 agent 连接交来的暂存，A 就得顶掉真 H，窗口规则才咬得住。

## 4. 什么时候跑、界面

### 4.1 触发

`hostsToRotate(chain)` 取代 `hostsToReEnroll`，位置 `W/lib/hub/account.ts`。

**沿用今天的三种「失去」**（某台设备曾能控制这台 host，而后不能了）：

- 移除它（`RemoveDevice*`、`RemoveMachine`）；
- 把一台没在名单里的 admin 降权（`SetAdmin false`）；
- 收窄 host 的名单，把它移出去（`SetAccept`）。

**补上传递**

- 今天只看直接能控制的设备，这是漏洞：X 能控制 H、H 能控制 H2（H2 的名单放行 H）时，X 拿着 H 的种子就能以 H 的身份控制 H2，所以 H2 也可能被复制了。
- 规则：一台 host E 暴露（失去之后还没换钥）期间，**任何时候**放行 E 的 host 都随之暴露。E 的复制品就是它的通行证。
- 页面在 E 暴露期间**不让**把它加进别的 host 的名单，先换完钥再加（§7 问题 8，已定）。
- **换完之后什么会让它再暴露**（避免互相放行的两台 host 来回换个没完）：
  - H 换钥之后，只有这三样会让 H 再暴露：
    1. 晚于这次换钥的新「失去」；
    2. 晚于这次换钥、把一台暴露的 host 加进 H 的名单（页面本来就不让，旧页面可能写过）；
    3. H 放行着一台**换不了钥**的暴露 host E（旧 agent，或 v2 账户）。
  - 第 3 种不显示成「再换一次」，而是「它放行着一台换不了钥的暴露设备 E：请收窄名单，或把 E 重新添加」。这时再换多少次都没用。
  - H 换钥时，它放行的、**能换钥**的暴露 host E 还没换完，H **不算**再暴露。这一条只在下面「互相放行的一组」先收窄名单的前提下成立。
- **互相放行的一组：先收窄，再换，最后恢复**：
  - **为什么**：E 与 H 都暴露、互相放行。H 换完之后，E 还没换，A 手里 E 的旧种子仍是 E 当前、被放行的身份。
    - 一个恶意的中继可以把「E」接到 H 上：Hub 的暂停只在 Hub 上管用，H 的 agent 只按链准入。A 经主机控制就能读走 H 的新种子，窗口里连暂存的种子都读得到。
    - 在设备上确认也挡不住：代码证明的是应答来自真 H，不是没人能控制 H。
  - **次序先于收窄**：「H 放行 E」时，E 必须先于 H 换完（控制者先换）。这样 H 换钥时，E 的旧钥已经作废。
    - 没有环的部分只靠这个次序就够，不收窄任何名单。
    - 只有互相够得着的一圈（强连通、至少两台）排不出次序，才对这一圈收窄。
    - **覆盖层**：用一条 `RenewalPause` 开始（§3.4 规则 10），在 `removals` 里列出圈里每台 host 要暂时去掉的圈内边。
      - 底子（`SetAccept` 写下的名单）一字不动，手改永远只改底子。
  - **怎么做**（页面的自动执行器，只对一圈）：
    1. 写一条 `RenewalPause{op, 开始, removals}`：圈里每台 host 去掉它放行的圈内其它 host。
    2. 逐台换钥，次序不限。
    3. **结束之前**，按此刻自己的链重新算暴露，不管之前哪次换钥、也不管 Hub 报的能力。
       - 结束后会恢复的每一条边，只要两端有一台是暴露的或被 Hub 标记的，就不结束：那些边留着暂停，行上写清原因。
       - 否则写 `RenewalPause{op, 完成}`。
       - **发布之前再查一次**：签好的结束条目在发出去之前，再按此刻的链与刚学到的隔离核对一遍要恢复的边；有一条必须留着就放弃、重建。
    - **大的一圈**：一条暂停装不下时，执行器把这一圈拆成几条暂停，每条都在大小上限之内，并且一圈的所有边都暂停上之后才开始换钥。
  - **卡住的暂停**：行上有「结束暂停」，写 `RenewalPause{op, 取消}`。
    - 确认绑定**确切的**恢复的边：发出之前若这组边变了（409 之后发现别的暂停重叠结束了、底子放宽了），就再问一次。
    - 确认框逐条列出会恢复的控制边。底子是 `All` 的，要说明暂停期间新加的设备也会因此被放行。
    - 同样受上面的暴露检查约束。
  - **换不了钥的**：圈里有换不了钥的 host（旧 agent、v2 账户）时，涉及它的边就一直暂停着，同上面的第 3 种「它放行着一台换不了钥的暴露设备」。
  - **为什么这样就够**：
    - 暂停是链上、admin 签的条目，收方 agent 在每条传输上按「底子减暂停」执行：Hub、中继、直连都一样，失去准入的已开通道会因链变化而关掉（`S/agent/link.rs`）。
    - 不经 Hub 的中继也绕不过去。
    - H 也不可能在拿到暂停之前暂存：`/rh/rotate` 带着页面的链视图，不在 H 的链上就回 `not_on_chain`。
  - **界面**：
    - 底子名单与暂停的部分**分开**显示，放宽底子藏不到暂停后面。
    - 组里的行显示「这些设备之间的控制已暂停，正在为它们更换身份密钥」，结束之后消失。
  - **代价**：
    - 每组多两条链条目（开始、结束），各有一条变化提示；
    - 组内 host 之间的控制暂停到换完为止；
    - 若没有哪个 admin 页面把这一组做完，暂停会一直开着。这是安全的方向，行上看得见，也能「结束暂停」。
  - 次序（控制者先换）是正确性的前提，不只是优化。

**清除与其它来源**

- **清除**：这台 host 的一条 `RotateHostKey`，只清掉链序号不大于它的 `staged_seq` 的那些失去。
  - 在 `staged_seq` 之后才发生的失去（又移除了一台能控制它的设备、又降了一个 admin……），这次换钥不算补救：新种子是在那之前生成的。
  - 页面在提交之前看到这样的失去，就作废这次准备，换新 nonce、新种子重来。
- **手动**：admin 随时可以对任何 host「更换身份密钥」。
- **克隆信号**（§7 问题 10，已定）：只在换钥进行中才算。尝试中被顶替（4001）就作废，原因 `replaced`。24 小时内第二次 `replaced` 或 `interrupted` 升级为克隆证据（§3.3「分级的证据」）。尝试之外的 4001 只是信息，不告警。

**`controllers` 记录**（聚合器文档 D3）

- 自动换钥之后，按链上的暴露换，不再用记录来省掉，因为换钥便宜、而且保守。
- 记录仍用于旧 agent：它们换不了钥，只在真的握过手时提示重新注册。
- 不用它省掉任何自动换钥（§7 问题 3，已定）。

### 4.2 谁来跑、在线与离线、重试

**谁来跑**

- 每个 admin 页面都带一个自动执行器，与自动回复用途 4 的索钥同一处。
- 做移除的那个页面当场就跑。之后打开的任何 admin 页面，从 `GET /v1/rotations` 接手没做完的。
- 同一台 host 同时只有一次尝试，靠 Hub 的登记串行（§3.3）。

**在线与离线**

- 移除那一批写完后，每台暴露的 host 都先登记成「待换」。
- 在线的立即发请求。
- 离线的等在线态推送：它一上线，任一开着的 admin 页面就开始。没有 admin 页面开着，就等下次有人打开。

| 失败 | 怎么办 | 界面 |
|---|---|---|
| 离线 | 等上线 | 「上线后自动更换身份密钥」 |
| 旧 agent（404，或没声明 `rotate/1`） | 不重试；保留重新注册这条路 | 「Droppen 版本过旧：更新后自动更换」；「改为重新添加」 |
| 门槛不满足（别的 host 没声明 `rotate/1`） | 等它们更新 | 列出卡住的设备 |
| `stale`（作证还没到） | 先作证再重试，同 `STALE_GRACE_MS` | 无 |
| 通道失败、超时 | 1 分钟、5 分钟、30 分钟后重试；3 次之后要你处理 | 「换不成：……」 |
| `interrupted`、`replaced`（断开、超时、Hub 出错、尝试中被顶替） | 换新 nonce 自动重来（每小时 6 次之内）；24 小时内第二次才按下一行处理 | 无 |
| `not_acked`、`conflict` | 不再自动，转高保障；记克隆证据 | 红色告警 |
| `expired`、页面中途关掉 | 下一个 admin 页面重来 | 无 |

### 4.3 待换期间

- **Hub 暂停这台 host 的设备角色**：不发设备会话、不收订阅、不签设备票据，已有的会话吊销。agent 角色照常：它还要运行 AI，也要被换钥。
  - 理由：真 H 离线、A 握着它的种子时，A 可以以 H 的设备角色订阅别的 host 的流、收给 H 的用途 5 信件，也可以开通道去控制放行 H 的 host。暂停把这些都挡在 Hub 上。
  - 只暂停声明了 `rotate/1` 的 host：它们很快会换完，旧 agent 换不了，不能把它们关在外面。
- **admin 页面不再把别的 host 的钥封给它**：用途 5，以及对它的用途 4 回复。它自己的 `MK` 照今天的规则交付：防不住持种子的人，也没有坏处。
- **设备上**：它的格子、面板显示「待更换身份密钥」徽章。

### 4.4 界面

**「我的设备」那一行**

现在的红字块「请重新登记它：轮换钥匙挡不住复制了它身份的设备……先移除，再重新添加」换成以下状态：

| 状态 | 文案（zh-CN） | 操作 |
|---|---|---|
| 进行中 | 「正在更换身份密钥…（约 2 分钟）」 | 无 |
| 等它上线 | 「上线后自动更换身份密钥」 | 无 |
| 版本过旧 | 「Droppen 版本过旧：更新后自动更换身份密钥」 | 「更多 → 改为重新添加」 |
| 要在设备上确认 | 「需要在这台设备上确认」 | 「输入设备上显示的代码」 |
| 隔离 | 红色：「这台设备的旧身份密钥在别处被使用。确认之前不会再连它。」 | 「在设备上确认」「移除」 |
| 刚完成 | 指纹换成新的，小字「已更换身份密钥 · 14:02」，显示 24 小时 | 无 |

**其它地方**

- **账户提示条**：「请重新登记 {{ids}}……」改为「正在为 {{ids}} 更换身份密钥」；要你处理时改为「{{ids}} 需要在设备上确认身份密钥」。
- **移除的确认框**：多一句「它能控制的 N 台设备会自动更换身份密钥（在线的约 2 分钟）」。收窄名单、降权的确认框同理。
- **账户设置**：一个开关「更换身份密钥时总在设备上确认」，默认关。
  - 它是一条**链上的、admin 签的**条目（`SetRenewalPolicy`，§3.4），不是 Hub 的状态。
  - 每台设备都显示它的变化。打开期间，两份验证者都拒绝 `assurance = 0` 的换钥，与 Hub 串通也关不掉它。
  - **另有本机的一道保险**：admin 设备上可以单独设「这台设备只签在设备上确认的换钥」，存在本机，不论账户设置与 Hub 怎么说。
- **行上的手动操作**：「更换身份密钥」，admin 才有。
- **host 本机设置的「Droppen」一节**：最近一次更换、等待确认的代码、`foreign_rotation` 或隔离的红字。
- **翻译与守卫**：四种语言；新文案进 `web/test/ui-wording.test.ts` 的表。

## 5. 对各处的影响

### 5.1 运行中的会话与通道

- AI 会话是本机进程，与云端链接无关，**照常运行**。
- 通道在提交时全部断开：H 重启链接，设备也会关掉对旧钥的通道。设备随即对 `dh1` 重新握手，一次往返。
- 终端按 shim 偏移重新接上；在途的发送靠回执查询确认（架构文档 §5「断线时在途的发送」）；进行中的上传、下载失败，要重来。
- 直连路径随通道一起断，再按需重建。
- 窗口期间什么都不变，用户只在提交那一刻看到一次重连。

### 5.2 中继与票据

- 提交后吊销 H 的中继票据：此前签给 H 的 agent 票、设备票一律拒绝，H 的中继连接随之关闭。
- H 用新钥向 Hub 领新票。Hub 按登记的新钥签票，所以票据里的 `sign_key` 是新的。
- 设备票里的 `peers` 是 id，不受影响。

### 5.3 聚合器与 host 之间的控制（D1、S1-4）

- **同一个身份**：本机控制端用的就是 H 的身份（聚合器文档 §3.3），所以它和 agent 一起换钥、一起重启：
  - 用新钥换设备会话；
  - `aggregator/keys.json` 留着，旧轮次仍用来读旧密文；
  - 缺的新轮次由它发用途 4 索取，admin 把用途 5 封给 `dh1`；
  - `copies.db` 不动，存下的位置按 §5.4 验。
- **别的 host 怎么看它**：它们照常凭 id 放行 H（`SetAccept` 不变），按链上的新钥准入。H 的 hello 会把条目带过去。
- **D1 不受影响**：host 永远不是 admin，不能替别人签换钥条目。
- **传递**：见 §4.1。H 暴露期间，放行它的 host 也算暴露。

### 5.4 离线副本与按纪元命名的流

**写的一方**

- 换钥那一批带着 H 新一轮 `MK`，交付时 `reencrypt: true`。
- 索引、状态立刻用新名字，会话按 `naming.rs` 的迁移立即重建：manifest 与页都从 0 开始，由新钥签。旧名字确认被取代后才删。
- **合并迁移**：移除那一批刚给过一轮 `MK`，紧接着换钥又给一轮。迁移没跑完时，agent 直接改向最新的纪元；从没写过的那一轮名字直接跳过，不建空流。这样不会连做两遍。
- **窗口外的旧会话**：超出 `DROPPEN_AGENT_SYNC_DAYS`、不迁移、等保留期清掉的流，还挂着旧钥签的流头和 manifest。
  - 流头：心跳在几分钟内补上新钥签的（`HEARTBEAT_EVERY`）。
  - manifest：提升之后，agent 给它们各重签一遍，只重发 manifest，页不变（`CHECKPOINT`）。否则新读者读不出这些流。

**读的一方**（TS 的 `HubCopySource`、`MachineMirror`、`LogReader`；Rust 的 `rh-client` `follow::Follower`）

- **从网络上来的**流头与 manifest，只按读者自己的链上这台 host **当前**的签名钥验。
  - 验不过时先同步一次链再试：对方可能已经先换了钥。
  - 换钥之后旧钥签出的东西一律不认，所以 A 加恶意 Hub 也塞不进伪造的历史。
- **自己存下的位置**（IndexedDB 的 `streammeta/`、`copies.db` 的 `head` 列）按 `keys_at(host, …)` 验，也就是这台 host 用过的任何一把钥。
  - 这些位置是读者自己当年验过才存的，不是新的说法。
  - 所以离线副本不会因为换钥而消失，「截至」照旧。
  - 防不了本地存储被人篡改，这本来就不在模型里。
- **下限**（`follow::Floor`）不变：新钥的流头时间更晚，照常推进。

**其它**

- **钥环与通行密钥包**：`mk/<host>/<MK 轮>/…`、`pk/m/<host>/…` 按 id 和轮次命名，照常写新一轮，旧的不动。

### 5.5 桌面 App

- App 跑的是同一个 `remote-hand-server`（实例 `droppen-app`），种子同样在文件里。换钥全在 sidecar 里完成，App 不用改协议。
- App 要做的只是显示：
  - 高保障代码与 `foreign_rotation` 发成系统通知，点开就是本机设置的「Droppen」一节；
  - 菜单栏图标在「需要确认」时带标记。
- **以后**：种子进钥匙串之后（聚合器文档 §7.3），`SeedStore` 的暂存与提升都换成钥匙串条目。到那时，经通道控制它的人未必读得到种子。若再有一把 Secure Enclave 里、要用户在场才能用的「换钥授权钥」，高保障档就能变成自动的。现在不做。

### 5.6 旧 agent、旧页面与门槛

**为什么要门槛**：20 号动作在旧验证者那里是未知动作，整条链从这一条起验不过。

- 旧 agent 会报链告警、停止接受通道，同链 v3 的互通表。
- 旧页面验链失败，版本横幅强制刷新。

**门槛**（同聚合器文档 §3.5 的做法）

- agent 在 `agent_info.features` 与握手回复里声明 `rotate/1`。
- Hub 只在账户里**这一批生效之后**的每台当前 host 最近一次都声明过 `rotate/1`，并且 `DROPPEN_HUB_HOST_ROTATION=on` 时，才收含 `RotateHostKey` 的批。否则 409 `rotation_not_ready {waiting: [ids]}`。
- 被这一批移除的 host 不卡门槛，规则同 v3 门槛，否则落后的 host 永远移除不了。
- **暂停的结束不卡门槛，也不看开关**：22 号的 `Completed`、`Cancelled` 只结束链上已经开着的暂停（链本身拒绝结束没开着的，`PAUSE_NOT_OPEN`），读得到这条链的都已经认识 22 号，结束只是把控制交还。所以开关拨回 `off`（下表「只能向前修」）或中途加入一台不声明 `rotate/1` 的 host 之后，开着的暂停照样能结束；新的暂停、换钥、档位照旧被挡。

**字段命名**

- Hub 的 HTTP 与 websocket JSON 一律 snake_case，与现有的每一条 Hub 消息一致：`nonce_hash`、`ready_ms`、`staged_seq`、`staged_head`、`sign_key`、`dh_key`、`old_sig`、`new_sig`。
- agent 的 `/rh/*` 路由与 `GET /api/cloud` 保持今天的 camelCase：`/rh/rotate` 的 `{nonce, eph, chainSeq, chainHead, assurance}` 与应答 `{signKey, dhKey, oldSig, newSig, mac}`。

**线上兼容：谁都不收到会弄坏它的消息**

- **旧 Hub 收不到新消息**。Hub 对不认识的 agent→hub `t` 回 4400 并断开。所以：
  - 新 Hub 在 `welcome` 里加 `features: ["rotate/1"]`。这是新字段，旧 agent 不读。
  - agent 只在本连接的 `welcome` 带了 `rotate/1` 时，才发 `rotation_stage`、`rotation_ack`、`rotation_unknown`。
  - 没带时 `/rh/rotate` 回 409 `hub_not_ready`，不生成种子。页面本来就先 `PUT /v1/rotations`，旧 Hub 回 404，页面不往下走。
- **旧 agent 收不到会弄坏它的东西**。agent 的 features 在 `welcome` 之后才到（`agent_info`）：
  - Hub 只在这条连接声明了 `rotate/1` 之后才发 `rotation_pending`。旧 agent 本来也忽略不认识的 `t`，但不发给它。
  - 4005 只发给被换钥的 host 的连接，而能被换钥的 host 都声明过 `rotate/1`。
  - 退役钥的登录沿用 4401（`error` 的 code 为 `rotated`），旧 agent 当它是一次普通的拒绝，照常退避重试。关闭前最多 10 秒只收一条 `chain_sub`，回到退役那一条为止的链（§3.8）；旧 agent 不发它，10 秒后照样关闭。
- **旧页面**：`/v1/client` 的新推送 `rotation`、`host_dispute` 交给控制消息的监听者，不认识就忽略。

**兼容表**

| 组合 | 结果 |
|---|---|
| 被换钥的 host 是旧 agent | `/rh/rotate` 回 404 → 「版本过旧」，保留重新注册 |
| 账户里另有旧 agent | 门槛挡住，列出它们 |
| 旧 Hub | 不认识 20 号，追加回 409；所以 Hub 先发版 |
| 旧页面开着 | 验链失败 → 刷新。Service Worker 的预缓存随版本走 |
| agent 回滚到不认 20 号的版本 | 验链失败，停止接受通道，与 v3 一样**没有回头路**。只能向前修：把 `DROPPEN_HUB_HOST_ROTATION` 拨回 `off`，不再写新的；开着的暂停仍可结束（上文） |

**发版顺序**

1. 先发**能读**的 Hub、`rh-proto`、agent（含 `rh-client`）与网页。
2. 门槛要等每台 host 都升上来才会满足。
3. 再发**会写**的网页（R4）。

**打开的顺序**：开关打开之后，admin 要先明确选一次换钥档位（写一条 `SetRenewalPolicy`，开或关都行），页面的执行器才开始自动换钥。

- 链上还没有 `SetRenewalPolicy` 时，页面的执行器不自动换钥，提示 admin 先选。
- Hub 也拒绝开尝试：409 `rotation_not_ready {reason: "policy_unset"}`。
- 把档位从「总在设备上确认」改回自动，是一条要确认的提示，写之前先让 admin 确认。

### 5.7 两份链验证者与互通向量

Rust 在 `C/rh-proto/src/chain.rs`，TS 在 `W/lib/e2e/chain.ts`，必须逐字节、逐规则一致。

**新增的互通向量**（`C/rh-proto/vectors/rust.json` 与 `ts.json`，两边都要读对方产的）

- 20 号条目的编码与解码，`assurance` 取 0 和 1，以及非法值；
- 证明体的字节、`rotate-confirm` 的 MAC、`rotate-sas` 的代码、`rotate-ack` 的签名；
- 一条完整的链：加入 host → 移除一台能控制它的设备 → `RotateHostKey` → `KeyEpochs`，两边重放出相同的状态与链头；
- 每条拒绝规则一个反例，拒绝原因用同一句话：
  - `ROTATE_NOT_HOST`（浏览器、待定设备、已移除的 host）；
  - `ROTATE_KEY_REUSED`（当前钥、退役钥、别的设备的钥）；
  - `ROTATE_STAGED`（seq 超前、头不符）；
  - `ROTATE_PROOF`（缺旧签名、用退役钥签、新签名不对）；
  - 非 admin 签、v2 条目里出现 20 号、紧跟着的不是 `KeyEpochs`。
- `keys_at` 在换钥前后取到的钥。

**标签**：`sig::LABELS` 加 `rh/v1 host-rotate\0`、`rh/v1 rotate-ack\0`，现有的标签互不为前缀的测试照样覆盖。`rotate-confirm`、`rotate-sas` 是 HMAC 与哈希的标签。

**回归**

- 现有的每条向量、每条链，在新代码下重放结果不变。这一条只是加法：v2、v3 的旧链从没出现过 20 号。
- `v3_regressions.rs` 与 TS 测试里各加一组攻击回归：
  - 一台 admin 单独改绑（没有旧钥签名）；
  - Hub 重放旧证明（钥已用过）；
  - 把 host 的身份撞到另一台设备的钥上；
  - 窗口规则属于 Hub 一侧，见 R2。

### 5.8 Hub（登记的钥何时变）

> Hub 一侧的存储与更新做法（表结构、迁移、事务）是 Hub 的内部实现，不在公开仓库。外部看得到的是下面这些，接口、状态与错误码见 `docs/hub-api/`。

**换钥的整个过程里，Hub 登记的这台 host 的钥只在一个时刻变**：存 `RotateHostKey` 的那一刻，agent 角色与设备角色两处一起换成新钥（条件是登记的还是旧钥）。

- 暂存和窗口期间不变：旧钥照常登录，好让真 H 在窗口里能被要求确认。
- 设备角色那一份登记平时从不被替换，换钥是唯一的例外。

**登录**

- agent 与设备会话的验签都只按当前钥。
- 验不过时再查退役钥（按 host id 与钥一起查，不只按钥）：查到就是 `rotated` 加争议证据，并在关闭前给出到退役那一条为止的链（§3.8）；查不到照旧 `denied`。

**连接与信件**：4005 关闭码；暂停「待换」host 的设备角色（§4.3）；删给它的信；吊销中继票。

**接口**（见 `docs/hub-api/`）

- HTTP：`PUT`、`GET`、`DELETE /v1/rotations[/{host}]`。
- `/v1/agent` 上的消息：`rotation_stage`、`rotation_pending`、`rotation_ack`、`rotation_unknown`。
- `/v1/client` 上的推送：`rotation {host, state, reason}`、`host_dispute`。
- websocket 关闭码表里有 4005。
- `/v1/me` 有 `rotations` 摘要。

### 5.9 主设备、套餐、通行密钥

- id 不变，所以这些都不受影响：主设备（`/v1/main-device`）、屏幕里的 `machine`、接受策略、别的 host 的名单、`hosts.max`、`devices.max`、通行密钥槽。
- 不新增设备，不占名额。

- **R1（协议）**：Rust 与 TS 两份验证者里的 20 号动作、证明体、标签、规则与互通向量（§5.7）。只读，没有写方。

- **R3（agent）**：`/rh/rotate`，种子的暂存与提升（崩溃安全），在 Hub 连接上暂存与确认，提升后的进程内重启，`foreign_rotation` 告警，只剩退役钥时「以新身份重新添加」（§3.8），本机设置里的显示。
- **R4（网页）**：自动执行器与带传递的暴露判断（`hostsToRotate`），`renewIdentity`，隔离，高保障对话框，读者只认当前钥（存下的按 `keys_at`），§4.4 的界面与四种语言。
- **R5（端到端测试）**：真 agent 加拿复制种子的 devkit 扮 A：被动、在中继上抢答、H 离线 A 赢、高保障、真 H 握当前钥而 A 拿退役钥的隔离与恢复（§3.6）。

**仍要手动的**

- 高保障档的那串代码（要在那台设备前），包括隔离之后的恢复。
- 旧 agent 与 v2 账户：照旧重新注册（「更多」里）。
- 后门的排查与重装，以及那台电脑上别的凭据（Claude 登录、SSH 钥、云凭据）的更换。换钥碰不到它们。

## 7. 决定（2026-10-20）

原来的十个问题，都采用了建议的答案。没有给出建议的两条（4、10）照下面处理。

1. **默认档位**：自动换钥是默认。「更换身份密钥时总在设备上确认」是账户设置里的开关，**默认关**。它记在链上（`SetRenewalPolicy`，§3.4 规则 9），由两份验证者执行；admin 设备另有本机的一道保险。
2. **退役钥再出现时**：**隔离**这台设备，直到在那台设备上确认（失败时安全）。由一次 `assurance = 1` 的换钥退役的钥再出现，只记录、提示，不隔离（§3.8）。
3. **离线时被触发的 host**：上线后**照样自动换**，不强制到场。`controllers` 记录**不用来**省掉任何一次换钥；它只留给换不了钥的旧 agent，决定要不要提示重新注册（§4.1）。
4. **窗口 T**：沿用设计的默认 2 分钟（`DROPPEN_HUB_ROTATION_WINDOW_SECS` 可调）。这一条没有单独的建议，窗口长度以后再定。
5. **名字**：界面叫「更换身份密钥」/「更換身分金鑰」/「ID 鍵を更新」/ "renew identity key"。
6. **手动与定期**：行上给 admin 一个「更换身份密钥」。**不加**定期自动换。
7. **重新注册的入口**：「先移除，再重新添加」**保留**在「更多」里，作为旧 agent、v2 账户和用户不放心时的退路。
8. **传递**：经别的 host 间接够得着的也算暴露，一起换（§4.1）。一台 host 暴露期间，页面**不让**把它加进别的 host 的名单，要先换完钥。
9. **别的凭据**：换钥完成时如实提醒一句：被移除的设备可能读到过这台电脑上的 Claude 登录与 SSH 钥，请到对应的地方更换。
10. **克隆信号**：只在换钥进行中算。尝试或暂存开着时，host 的 agent 连接被顶替就让它作废（暂存时，除非新登录确认得出来）。同时记日志，并向设备推一条提示（§3.3「顶替」）。尝试之外的顶替不单独告警。
11. **窗口里断开的连接**：用分级的证据。断开、超时、Hub 自己出错算 `interrupted`：作废，不记证据，自动重来。答错、`rotation_unknown`、开着不答、`conflict`、24 小时内第二次 `interrupted` 才升级为克隆证据（§3.3）。

## 8. 安全评审清单（R6 的门槛）

每条都要有先失败、后通过的回归测试。

1. 20 号条目在 Rust 与 TS 里编码、规则、拒绝原因逐字节一致；现有向量与链重放不变。
2. 只有当前 admin 能签；没有当前身份钥的签名、或用退役钥签的，一律无效。
3. 新钥从没在链上出现过（任何设备、当前或退役）；`staged_seq/head` 必须在链上；退役钥不能再加入或激活任何设备（§3.4 规则 8）。
4. 换钥之后紧跟这台 host 新一轮 `MK`，而这一轮只封给新 DH 钥（信箱与通道都是）；给它的旧信在存条目的同时删光。
5. Hub：登记的钥（agent 角色与设备角色两处）在存条目的同时原子地换成新钥；旧钥的 agent 登录、设备会话、中继票全部失效；4005 关闭已有连接。
6. 窗口：只收这台 host 当前那条 agent 连接交来的暂存，被顶替的连接的帧一律丢掉；暂存时其它开着的连接也欠确认；窗口内每次以旧钥登录都必须用新钥确认，否则作废（分级证据）；不到 T 不能提交；24 小时过期。
7. host：只有链上验到条目、且钥与暂存一致才提升；每一步之间崩溃都安全；不是自己的钥时告警、不提升、保留旧种子。
8. 设备与 agent：握手只用链上当前的 DH 钥；钥变了就关掉旧通道。
9. 读者：网络上的流头与 manifest 只认当前钥；存下的位置按 `keys_at`；下限照旧。
10. 争议：退役钥的登录被拒，证据能被设备独立验证；隔离状态跨设备、跨加载可见；只有 `assurance = 1` 的换钥能解除。
11. 待换期间设备角色暂停，用途 5 不封给它。
12. 传递：X→H→H2 时 H2 也被换；暴露期间加进名单的 host 也算。
13. 门槛：不满足时 20 号条目回 409 并列出卡住的 host；被移除的 host 不卡门槛。
14. 高保障：代码只在 host 本机显示，页面要求输入（不是点「一致」）；不一致不提交。
