# remote-hand 云化设计初稿：端到端加密的公共 SaaS + 本机受控端

> 讨论稿，2026-10-14。代码依据 v0.2.94。除注明 `web/` 外，路径均相对 `server-rs/src/`。

## 0. 已定前提与结论

**已定前提**

- 面向公众、任何人可注册的多租户 SaaS。
- 云端**看不到、也解不开**任何与 AI 对话有关的内容，只存服务层数据，以及它解不开的端到端密文。
- 机器离线时 AI 不能运行，但可以从密文副本查看历史。
- 终端是核心功能，必须经中继、端到端加密，延迟是一等指标。
- 云端用 Rust 写，跑在普通的容器托管上。
- **不做任何密钥托管**：用户丢光所有设备、又没有恢复钥时，历史永久不可读，用户接受这一点。

**结论**

- **agent 就是今天的 server**，加一条只出站的连接。执行、transcript、凭据、PTY、文件都留在机器上。
- **hub 是盲路由器加密文仓库**，负责账号、计费、机器注册、转发和存储，没有任何能解密的钥。
- 产品只建在两个原语上：
  - **E2E 通道**：浏览器设备 ↔ agent 的 Noise 会话，用于命令、RPC 和终端。
  - **加密流**：agent 单写的追加日志，加上快照页，用于会话列表、会话正文，以及离线查看。
- 云端日志是**可重建的缓存**：真相在机器的 transcript 上，agent 随时可以用新密钥重写。

```
浏览器/手机（设备钥）──WSS──▶ hub（Rust）◀──WSS，只出站── 电脑上的 agent（今天的 server）
        ╚══════ Noise 端到端通道（hub 只转发密文帧）══════════════════╝
                     数据库：账号、设备链、机器、流头、小记录
                     对象存储：加密快照页、大文件
```

## 1. 密钥模型

> 2026-10-15 按安全评审（C1/C2/H1/M1–M5）修订；实现见 `server-rs/crates/rh-proto` 与 `web/src/lib/e2e`。

| 密钥 | 类型 | 谁持有 | 用途 | 轮换 |
|---|---|---|---|---|
| 账户根钥 `AK` | Ed25519 | **没人长期持有**：创建账户的设备签完创世条目就销毁私钥 | 只签创世条目；公钥指纹是账户的根身份，机器注册时钉住它 | 只在「全部丢失后重置」时换（新创世） |
| 恢复钥 `RK`（可选） | 客户端生成的 ≥128 bit 随机数，以词组形式展示 | **只在用户手里**，任何设备都不存 | 派生恢复签名钥 `RSK` 和恢复包裹钥；后者包裹各 epoch 的 `UK`，结果存云 | 用户可随时重新生成，由完整设备签 `SetRecoveryKey` 换上新 `RSK` |
| 恢复签名钥 `RSK` | Ed25519，`HKDF(RK)` 派生 | 不存储，用时由 `RK` 现算 | 只签 `RecoveryJoin` 和 `ActivateRecovered` 两种条目；公钥写在创世条目里 | 跟随 `RK` |
| 用户钥 `UK_e` | 对称 256 bit，带 epoch | 完整设备 | 加密 UI 文档，并包裹各台机器的 `MK` | 任何设备或机器被吊销时 epoch +1 |
| 设备钥 `DK` | Ed25519 + X25519 | 单个浏览器/手机：WebCrypto 生成，用时是不可导出的 `CryptoKey`；在 IndexedDB 里存成用本机 AES-GCM 钥封起来的 PKCS #8（WebKit 存不住不可导出的 X25519 钥），同源代码能解开读出（第 7 节「网页前端投递」） | 设备身份、签设备链条目和链证明、Noise 静态钥、收发被封装的钥 | 设备重装即生成新钥 |
| 机器身份钥 | Ed25519 + X25519，由一个随机 32 字节种子派生 | agent 实例目录（0600，`SeedStore` 抽象，见下） | 向 hub 签登录挑战；Noise 响应方静态钥；签流头和推送 | 重新注册时更换 |
| 机器钥 `MK_m,e` | 对称 | 该 agent（经 E2E 通道交付）；用户侧只以 `UK` 包裹的形式存在账户钥环里（`mk/<机器>/<MK epoch>/<UK epoch>`），浏览器本地不存明文 | 只作 HKDF 输入：按不同 salt 派生流 id 的 HMAC 钥、各流钥、已读文档钥 | 吊销时 epoch +1 |
| 流钥 `SK` | `HKDF(salt="rh/v1 stream-key", MK_e, stream_id)` | 不存储 | 加密日志记录和快照页 | 跟随 `MK` 的 epoch |
| 通道钥 | Noise 临时钥 | 内存 | 实时通道，前向保密 | 每小时或每 2^20 条消息 rekey |

**为什么不算托管**

- 云端只存「用设备公钥或恢复包裹钥包裹后的密文」，没有服务端主钥，也没有客服找回。
- `RK` 必须由客户端随机生成，不允许用户自定口令，否则云端可以离线爆破。
- 不做 passkey PRF 解锁。那等于把钥匙托管给 Apple/Google 的同步账号。

**谁能签什么（设备链规则）**

- `AK` 只签创世条目，之后没有任何权限。被移除的设备手里没有可以复用的账户级私钥——所以「吊销时轮换 `AK`」不需要，也没有意义。
- 普通条目（加/删设备、加/删机器、批准恢复设备、换恢复钥）只能由**当前有效的完整设备**用自己的 `DK` 签。
- `RSK` 只能签 `RecoveryJoin`（加入的设备处于**待定**状态）和 `ActivateRecovered`。待定设备既不能签条目，也不会被任何 agent 放行握手。
- 待定设备转正有两条路：任一有效完整设备签 `ApproveDevice`；或者 `RSK` 签 `ActivateRecovered`，且**验证者自己**最早看到那条 `RecoveryJoin` 已满 24 小时（用验证者本地的首次看到时间，hub 和设备都无法回填）。这 24 小时里所有设备和 agent 都要告警，任一完整设备可用 `RemoveDevice` 否决。
- id 永不复用；最后一台有效完整设备不能被移除；所有公钥必须是规范编码、在曲线上、且不是小阶点（两端规则一致）。
- 以上是链 v2 的说法。新账户从创世起就是链 v3（`Genesis3` 加 v3 的 `KeyEpochs`，`docs/local-aggregator.md` §3.5）：完整设备在 v3 里叫 admin，机器是「可运行 AI 的设备」，规则一一对应；链 v2 只留在此前建的账户里，它们在「我的设备」里确认一次升级后也写 v3。

**新设备如何拿到钥**

1. **扫码配对**：新设备显示二维码，里面有它的公钥和一次性秘密 `s`。已有设备扫码后：
   - 签一条「加入设备链」条目；
   - 把 `UK_*` **带发送方认证地**封装给新设备（见第 5 节「钥匙投递」），并用 `s` 对整个投递（账户指纹、发送设备 id 和公钥、封装结果）做 MAC；
   - 经 hub 的信箱投递。

   公钥和 `s` 走的是光学通道；新设备此时还不认识这个账户，靠 `s` 的 MAC 确认投递来自扫过它屏幕的那台设备，hub 冒充不了任何一方。
2. **口令配对**（设备没有摄像头时）：新设备显示 8 位数字，用户在已有设备上输入。双方经 hub 跑 PAKE（M2 实现为 CPace-X25519，见第 9 节），协商出共享钥后再交换公钥。尝试次数由**两端**强制：每次运行只用一个口令，失败即作废，hub 每次只有一次在线猜测机会。
3. **恢复钥**（M2 以 BIP-39 的 12 个英文词展示与输入）：输入 `RK` → 派生 `RSK` 和恢复包裹钥 → 下载并解开 `UK` → 用 `RSK` 签 `RecoveryJoin`。新设备先处于待定状态，所有设备收到告警；有其它完整设备在时由它批准，否则 24 小时后用 `RSK` 自行激活。

**全部设备丢失、又没有恢复钥时**

- 云端密文永久不可读，任何人都恢复不了。
- 邮箱可以找回**登录**，但只能换来一套新的 `AK`/`UK`（新创世），旧的流和 UI 文档会被删除。
- 机器钉住了旧 `AK` 的指纹，必须在机器本地执行 `agent re-enroll` 才接受新的信任根。所以邮箱被盗也接管不了机器。
- 重新注册后，agent 用本机 transcript 重建加密流，仍在磁盘上的会话历史会回来。真正永久丢失的是只存在云端的数据（待办、布局），以及已退役机器上的会话。

**吊销与轮换**

1. 任一完整设备签一条「移除」条目。hub 立即停止为被移除的设备路由，并作废它的登录会话（纵深防御）。
2. agent 订阅设备链，立刻断开该设备，并拒绝它之后的 Noise 握手。hub 若扣住这条移除不发给 agent，见第 5 节「冻结」。
3. `UK` 和所有 `MK` 的 epoch +1，新钥只封装给剩下的设备和各 agent。之后写入的记录，被吊销的设备读不到。被吊销设备手里旧 epoch 的流钥也伪造不了新记录：读者只放行机器签名流头覆盖的记录。
4. （M2 安全复审）每个新 epoch 先在链上提交（`KeyEpochs` 条目：`SHA-256("rh/v1 key-commit\0" ‖ 种类 ‖ 账户 ‖ 机器 ‖ epoch ‖ 钥)`，每次只能 +1），再包裹、发信、交付；设备和 agent 收到任何 `UK`/`MK` 都对照链上的提交，对不上一律拒绝——被吊销的设备（或 hub）塞不进自选的钥，也推不走 epoch。

被吊销设备已经缓存的旧历史无法收回。可以提供「吊销并重加密」：agent 用新 epoch 从本机 transcript 重建流，再删除旧密文（M2 已实现，见第 9 节）。流名也随 epoch 换（`streams/2`，`docs/relay-and-plans.md` §5；有设备在通道问候里声明能读之后才启用，此前的做法见第 9 节「轮换与重加密」）：每条流的名字由它创建或迁移时那个 epoch 的 `MK` 派生；轮换后索引流和状态流立刻换到新名字，会话流在 6 小时内的一个随机时刻迁到新名字（重加密时立刻迁），新流被 hub 确认之后才删旧流。所以重加密就是把流迁到新名字下，被吊销的设备没有新 epoch 的 `MK`，算不出之后的流名；hub 仍能凭时间和大小把新旧名字对上一部分，见第 7 节「轮换后的流名」。

设备链带单调递增的序号，设备和 agent 都缓存见过的最高（序号，哈希），拒绝回滚和分叉。

浏览器的这份记录（「已见记录」，每个账户一条：验到第几条、那条的哈希、最近 256 条的哈希、每条第一次见到的时间）和它钉住的创世哈希放在一起，由同一浏览器的所有页面共用：钉住的创世只设一次，记录只进不退。落后的页面不会把它改低，两个页面的链在重叠处不同就是分叉（告警，页面停下）。

- **存在 IndexedDB**（库 `rh-hub-seen`，每个账户一个值：钉住的创世和已见记录）。读、比、写在同一个 `readwrite` 事务里做完，钉哪个创世、在它之下收下什么，是一次决定的。比较是同步的，事务中途不等任何东西（WebKit 在页面让出事件循环、事务又没有待处理的请求时就提交）。同源各页面范围重叠的 `readwrite` 事务一个接一个执行，每个都看到前一个提交的结果，所以拿着过时视图的页面写不低记录，也钉不上另一个创世（#183）。原来两者都放在 `localStorage`：每个页面读的是自己的副本，浏览器事后才同步，Web Lock 只能让两个页面不同时写，挡不住按旧副本写低；写后 2 秒重读一次的做法现在不需要了。
- **写不进去就不算数**：事务没提交（磁盘满、连接断了），这次的视图就不装上，作为可重试的错误往上报（`SeenStoreError`）；读不出来也一样，从不当成「没有记录」，也从不当成分叉。
- **通知其它页面**：IndexedDB 没有变更事件，写了值的页面在 `BroadcastChannel`（`rh.hub.seen`）上说一声，开着的页面拿自己验过的链头再比一次（低了就写回并告警，冲突就是分叉）；页面回到前台时也比。
- **旧版本页面留在 `localStorage` 的**（`rh.hub.genesis.<账户>`、`rh.hub.seen.<账户>`）：每次读、写都一并看，从不删除（旧版本页面可能还在写）。
  - 它们钉的创世：IndexedDB 里没有时就用它，两边不同就是分叉。新版本页面钉住时也把它写回 `localStorage`，给旧版本页面看。
  - 它们的记录：只认和这个钉住的创世放在一起的。证明了和 IndexedDB 里的是同一条链（低的那个的链头就是高的那个在同一高度的哈希），就取高的；不一致就是分叉；证明不了（高的那个没留那么早的哈希），两个检查点都留着，之后每个视图都要同时对上两个，直到一条验过的链同时包含它们。所以旧版本页面写不低 IndexedDB 里的记录，也塞不进一条没证明过的延伸。
- **打不开 IndexedDB 时**（个别隐私模式：第一次打开就报 `InvalidStateError` / `SecurityError`，或者根本没有 IndexedDB），这个页面照旧把两者放在 `localStorage`、在 Web Lock 下读写，并在控制台说明；这时过时的副本仍可能把记录写低。这个浏览器以前用过 IndexedDB（`localStorage` 里有 `rh.hub.seen-in-idb`）就不这样退回，而是报可重试的错误：那里的副本比 IndexedDB 里的旧。
- **新账户的创世钉不进 IndexedDB 时**（重试一次仍失败），钉在 `localStorage`（下次读取时收进来），免得刚建的账户的第一个用户钥丢掉。
- **剩下的缺口**：在没有一个持更高视图的新版本页面开着时被写低的记录，下次加载照样被信任。能写低它的只剩两种：旧版本页面（在任何新版本页面把记录收进 IndexedDB 之前，它们之间照旧可能按过时副本写低），以及这个源里的代码——它不在这个威胁模型里（`docs/web-integrity.md`）。要发现这种写低，得有一份源里的代码改不了的状态，浏览器不提供。

**机器种子存哪里**

- 现在是实例目录里的 0600 文件（`SeedStore` 的文件实现），记录它属于哪个实例身份 uuid，拷到别的实例会被拒绝。
- 0600 防不住同一用户下的其它进程——包括本机运行的 AI CLI。读到种子的人可以冒充这台机器登录 hub、在别处接受握手，直到这台机器被移除或重新注册；但它**无法**冒充某台设备对本 agent 做任何改状态的操作（见第 5 节首包规则）。
- macOS 钥匙串能把读取者收窄到本程序的代码身份，但未签名的自升级每次都会触发授权弹窗，所以先只留接口，等发版签名稳定后再接。

## 2. 云端能看到什么

| 类别 | 云端可见（明文） | 加密，云端读不到 |
|---|---|---|
| 账号 | 邮箱、登录凭据（密码哈希或 passkey 公钥）、套餐与账单、访问 IP | — |
| 设备 | 随机 device id、公钥、已签名的设备链条目、最后在线时间、推送 endpoint 及其公开参数；浏览器和手机的类型与浏览器简称（如「iPhone · Chrome」，只取自固定词表，由设备自己请求的 User-Agent 得出，User-Agent 本身不保存） | 设备名 |
| 机器 | 随机 machine id、公钥、agent 版本、OS/架构（用于升级）、在线/离线、连接时间、IP、流量计数 | 主机名、显示名、路径、CLI 版本、账号与额度、能力详情 |
| 会话流 | 不透明的 `stream_id`（由 `HMAC(MK_e, source/id)` 派生，无法对应到 CLI 会话 id；每轮密钥换一套名字）、所属机器、seq、分桶填充后的记录大小、追加时间、总字节、epoch | 标题、cwd、仓库/分支、模型名、CLI 类型、状态、未读 Ledger、是否在问、消息、工具输出、草稿、图片 |
| 实时通道 | 哪台设备连哪台机器、开关时间、帧的大小与时序 | 终端输入输出、RPC、文件内容和文件名 |
| UI 数据 | 文档 revision、大小、更新时间；非敏感偏好（主题、字号、语言） | 布局（含叶子引用和路径）、待办、置顶/归档、已读时间 |
| 推送 | 目标订阅、密文大小、时间 | 通知标题和正文 |

流量分析无法消除：云端能看出你何时在工作、输出量有多大、终端的敲键节奏。可选的缓解措施是把记录填充到固定大小档位，并对终端输入加入干扰流量（OpenSSH 9.5 的做法）。另外，记录先压缩再加密，所以要逐条压缩并填充，避免压缩长度泄露内容。

## 3. 现有模块怎么落位

| `terminals/`、`pty_shim/` | shim 进程、环形缓冲、vt100，16 ms 合帧（`terminals/mod.rs:69`） | agent，走 E2E 通道 |

## 5. 协议

**传输层**

- agent 只出站，连 `wss://hub/v1/agent`，用机器钥签挑战。
- 浏览器每页一条连接，连 `wss://hub/v1/client`，用账号会话加设备钥签名。
- 三方都只出站连 hub；hub 按（设备，机器，`ch`）配对转发。所谓「端到端通道」是套在 hub 转发帧载荷里的一层 Noise 加密，不是一条独立的网络连接。**例外（已实现）**：设备和机器能直接互通时，同一条通道可以多一条 WebRTC 直连路径，信令在通道里、直连上再跑一次 Noise、hub 永远兜底，见第 9 节「直连通道」。
- hub 可见的帧格式为 `[type][ch][len][payload]`（单帧 ≤64 KB，u64 字段 ≤2^53−1），帧类型有：`OPEN/DATA/CLOSE/CREDIT/PING/PONG`，流相关的 `APPEND/ACK/CONFLICT/SUB/RECS/GONE/CHECKPOINT/EPHEMERAL/HEAD/PAGE`，另有 `CHAIN`、`ATTEST`、`PUSH_SEND`。
- `ch` 号单调递增、永不复用，沿用 `feed/mux.rs` 的 `sub` 规则。

**E2E 通道**

- 每对（设备，机器）一个 Noise IK 会话（`Noise_IK_25519_AESGCM_SHA256`，浏览器用 WebCrypto 原生实现，agent 用 `snow`）：发起方是浏览器，它从设备链里拿到 agent 的公钥。握手 1-RTT。
- prologue 只绑定 `rh/v1 | account | device | machine`，防止 hub 拼接会话。**不**绑定设备链序号——精确相等会让「hub 扣住移除条目」时，签了移除的诚实设备连不上、被移除的设备反而连得上。
- **首包不带请求**。IK 首包可被重放，且持有 agent 静态钥的人可以冒充任意设备伪造它（KCI）。所以首包只放 `HelloBody`：设备的链视图（序号、哈希）、最近 16 条链条目、客户端元数据；任何改状态的请求都等握手完成后的第一条传输消息（那需要设备自己的静态私钥）。
- agent 的检查顺序：解密首包 → 用首包里的条目补齐自己的链（与已有条目冲突即**分叉告警**）→ 若仍够不到设备的链视图，回复「从第 N 条起补发」并结束 → 用补齐后的链授权该设备 → 最后才查重放防护。回复里带 agent 自己的链视图，设备同样检查分叉。
- **冻结**：hub 扣住某条移除时，只要任一看到移除的设备连上，agent 就会补齐。在那之前，特权操作还要求链「新鲜」：另一台完整设备在 N 小时内对 agent 当前链头签过证明（`Attestation`，经 `ATTEST` 帧由 hub 转发；账户只剩一台完整设备时可用它自己的证明）。
- **重放防护**：首包带发送方时间戳；agent 按设备分配配额（只在授权之后），条目保留到时间戳本身过期（过去 10 分钟、未来 60 秒）；没有持久化状态的新进程拒绝它启动前一个未来窗口内的所有时间戳，有持久化则恢复快照。
- 通道内部复用多条子流：`rpc`、`mux`、`term`、`blob`；每条子流有信用窗口，并分优先级：控制 > 终端 > rpc/mux > 文件。
- 终端帧不做额外批量（只有 agent 侧的 16 ms 合帧），并设置 `TCP_NODELAY`。

**钥匙投递**

- **封装给某个密钥对**（`UK` 给新设备、信箱里的 `MK` 给 agent）：带发送方认证，仿 HPKE Auth 模式——`kek = HKDF(DH(e, R) ‖ DH(S, R), info = e ‖ S ‖ R ‖ 上下文)`。上下文写明用途、账户、发送方 id、接收方 id、epoch，同时作 AAD。接收方只接受「发给自己、本账户、发送方是当前有效完整设备」的投递，所以 hub 塞不进自己的 `MK` 或 `UK`。
- `MK` 交给 agent 首选走 E2E 通道（由已授权设备直接发）；封装只用于对方离线时的信箱。
- **对称包裹**（`UK` 包 `MK`、恢复包裹钥包 `UK`）：`HKDF(K, 上下文)` 加 AES-GCM，上下文同样带 epoch。

**签名**

所有 Ed25519 签名都是「固定的、以 NUL 结尾的标签 + 固定二进制结构」：`chain-entry`、`chain-attest`、`stream-head`、`stream-manifest`、`hub-login`、`push`。任何密钥都不对 hub 选的原始字节签名；hub 的登录挑战随机数只出现在 `HubLogin{角色, 账户, id, hub 源, 随机数, 时间}` 结构里。

**加密流（借鉴 Loro 的 streams，但不用 CRDT）**

- **记录**：`{seq, epoch, nonce, ct}`，AAD 为 `rh/v1 record ‖ stream ‖ seq ‖ epoch`，所以 hub 无法跨流挪用或重排记录。明文里带上一条的链接值 `link` 和格式号 `fmt`；`link_n = SHA-256(标签 ‖ stream ‖ link_{n-1} ‖ 记录_n)`。
- **来源与新鲜度**：流钥持有者（包括还握有旧 epoch 钥的被吊销设备）能封出合法密文，所以 agent 每次追加后、并定期作为心跳，用机器钥签**流头** `{stream, next_seq, epoch, link, time}`（`HEAD` 帧）。读者只放行被机器签名流头覆盖的记录：流头超出已收到的记录，说明 hub 在扣记录；链接值对不上，说明记录被伪造或替换；最新流头的时间就是视图的新鲜度。
- **流名**：`stream_id = HMAC(HKDF(MK_e, "rh/v1 stream-id"), source ‖ 0 ‖ id)`，`source`、`id` 不允许含 NUL；`e` 是这条流创建或迁移时的 `MK` epoch（第 9 节「轮换与重加密」）。
- **压缩**：由写方逐条决定，默认不压缩。只有不会把攻击者可影响的内容和秘密混在同一条里的记录才压缩，然后再按档位填充。
- **内容**：用今天 feed 的「从 `fromIndex` 起替换」语义（`{fromIndex, items, endIndex, fp}`），复用 agent 的 transcript 归一化，前端渲染不用改。
- **会话正文不进 Hub 的数据库**：数据库只放元数据——账号、设备链、机器、流头与 manifest、页目录、配额；记录与页的密文另外存放（Hub 内部，第 8 节）。索引流和状态流同样如此。
- **写入**：单写者 CAS——`APPEND{expect_seq}`，hub 原子地比对 `next`、写记录、推进 `next`、记账，之后才回 `ACK`；seq 不符就回 `CONFLICT`。agent 先把要发的记录预写进本地库，`ACK` 丢了就原样重发，hub 对逐字节相同的重发再回一次 `ACK`。尾部未被 manifest 覆盖的部分超过 256 条或 8 MiB 时拒绝追加（`stream_refused {code: "compact"}`），agent 立刻压缩后再写。Hub 崩溃时最多丢掉最后约 1 秒已确认的追加，可以自愈——agent 的下一次追加遇到 `CONFLICT`，从本机 transcript 变基重建；读者只放行签名流头覆盖的记录，丢失的记录不会被当成流的内容。
- **快照**：agent 定期把已封口的条目写成不可变页（内容寻址），经 hub 上传（`PAGE` 帧）由 hub 存放；manifest 就是一个机器签名的流头加页引用（两层签名：流头本身 + `stream-manifest`）；读者只能从签名流头起步（`LogReader::from_head`），页经 hub 代理读取（鉴权、流式、支持 `Range`）。存储的地址和凭据只在 hub 里，客户端拿不到任何指向存储的 URL。落后的读者会收到 `GONE`，从 manifest 重新起步。manifest 的链接值沿用记录链时是压缩，换成新的随机值时是**变基**（agent 用本机 transcript 重建流），持有旧记录的读者接不上、从 manifest 重来。细节见第 9 节「M2 第一部分」。
- **游标**：agent 收到 `ACK` 后，把「流 seq ↔ 本地 transcript 位置」写进实例库。前端把解密后的记录和 seq 写在**同一个** IndexedDB 事务里；前端的链状态和日志读取都是串行化的，并发调用不会合并分叉或重复收下同一条记录。

**重连、在线态、版本**

- **重连**：指数退避加抖动。重连后通道重新握手（很便宜）；各子流用已有的续传手段：feed 用 `since/fp`，终端用 shim 偏移，发送用 `clientMessageId`，流用 seq。
- **死连接**：页面每 10 s 向 hub 发一次 `ping`（hub 每个都回），25 s 收不到任何东西就当连接已死：关掉、通知其上的通道 `LINK_LOST`、重连——手机网络常把 TCP 连接悄悄掐掉（半开），否则页面要几分钟后才知道，期间经它的请求都石沉大海。页面的计时器被挂起过（后台标签、手机休眠）时，迟到的那一拍不算数，再给一个间隔。agent 一侧早有同样的检查（20 s 一次 `ping`，60 s 没动静就重连）。路径指示上的 hub 往返时间在探测没有回音时按最老那个未回探测的时长往上涨，不会停在最后一次的好数字上。
- **断线时在途的发送**：通道随连接一起断，在途请求立刻失败成「状态未知」。新通道一建好（`Transport.onReconnect`），发件箱立刻按 `clientMessageId` 去问服务端（`GET …/receipts`），收到的就显示为已送达；每次查询最多等 10 s，没结果就退避（1 s 起翻倍到 30 s）再问，不会卡在「正在确认」。通道暂时不能跨 hub 重连存活：hub 路径上发出的帧不留底（只有直连上的帧等确认、可重发），而且需要一个把已有 Noise 会话绑到新 `ch` 的续接握手，两端都要改。
- **在线态**：20 s 一次心跳；分在线、离线、未知三态，新鲜窗口 90 s；只在状态变化时发布。
- **版本**：
  - hub 可见的协议版本在路径里（`/v1/`）；
  - agent 的功能列表在通道内交换，hub 看不到；
  - 记录格式由 `fmt` 区分；
  - 云端托管的 SPA 要兼容 agent 的 N-2 个版本，agent 归一化逻辑升级后可以重建流。

**MVP 的 agent 侧桥接**

- 通道里的 `rpc/mux/term` 先转发到 agent 自己的回环监听：`/api/*`、`/api/events?v=2`、`/api/terminals/{id}/ws`。
- 回环请求带一个每次启动生成的内部凭据，`auth::guard`（`auth/mod.rs:282`）只接受来自回环的这种凭据。
- 这样现有 handler 一行不改。前端用 openapi-fetch 的 `fetch` 选项，以及 `feed-hub.ts` 已有的通道抽象，替换掉传输层。

## 6. 多租户认证、机器注册、防滥用

**登录与解密是两套秘密**

- 登录用邮箱加密码或 passkey，只决定能不能用服务、按什么计费。
- 解密靠设备钥和恢复钥。
- 忘记密码只影响登录；丢光设备的情况见第 1 节。
- 删除流、移除机器等破坏性操作，hub 要求带上设备链里某台设备的新鲜签名。这样只盗走登录也删不了数据。
- **不登录就能问的接口**（M2 复审二轮）：注册、登录、设备会话的挑战与兑换、管理员接口、两个 WebSocket 入口按客户端地址限速（每分钟 300 次、突发 60；部署在反向代理后面时取代理写入的 `X-Real-IP`，客户端伪造无效），id 至多 64 个可打印字符，请求体至多 8 KiB、10 秒内到齐（否则 `408`）；健康检查、安装脚本跳转、网页文件、Turnstile 页这些静态路由另有一个每地址的桶。设备会话按设备、passkey 登录按 passkey 另有份额，只有证明了身份才扣（细节见 `docs/relay-and-plans.md`「不登录就能问的接口收尾」）。设备会话的挑战是无状态的（时间 ‖ HMAC(账户, 设备, 时间)），申请挑战不在 hub 上存任何东西，灌不满、也挤不掉别人的挑战；只有带有效设备签名的回答会被记下（一次性）。铸造设备会话不需要登录，只需要设备自己的签名。
- **会话绑定设备**（M2 安全复审）：密码登录只得到 15 分钟的「登录会话」，只能注册设备、读链（只读）和登出；其余一切都要「设备会话」——设备用自己的钥匙签 hub 发的一次性挑战（`HubLogin`，角色 device-session）换来，链上移除这台设备即吊销。被盗的登录密码因此既读不到信件和钥环，也写不进任何东西。

**机器注册**

1. 在已有设备上点「添加机器」。设备生成 128 bit 秘密 `secret`，显示注册码 `RH1-<AK 指纹>-<secret>`（读的时候也接受 `DR1-` 开头），只向 hub 登记由它派生的 `token = HMAC(secret, "rh/v1 enroll-token")` 的前 16 字节（10 分钟有效）。
2. 在机器上运行 `remote-hand-server agent enroll <code>`。agent 生成机器身份钥，连上 hub，出示 token；hub 分配机器 id 后，agent 发出证明 `HMAC(secret, 标签 ‖ 账户 ‖ 机器 id ‖ 两把公钥 ‖ token)`。
3. 设备校验证明，通过后用**正是这两把公钥**签「加入机器」条目，再把 `MK` 交给 agent（首选经 E2E 通道）。hub 不知道 `secret`，伪造不出证明，所以注册不进自己的机器；不再需要比对短码，也就没有可以暴力碰撞的短码。
4. agent 钉住 `AK` 指纹，只信任创世公钥与之相符的设备链。

若将来保留短码作兜底（例如设备不方便显示长码），必须先承诺后揭示：agent 先承诺 `H(pub ‖ n_a)`，短码取 `H(pub ‖ fp ‖ n_a ‖ n_d)` 的 20 bit。PAKE 兜底由两端限次：每次运行一个口令，失败即作废。

**防滥用（内容不可见，只能按量和行为管）**

- 注册：邮箱验证、Turnstile、一次性邮箱黑名单。
- 每账号配额：机器数、设备数、存储 GB、每月中继流量、并发通道数、单条终端通道带宽。
- 每连接限制：令牌桶限速，单帧 ≤64 KB。
- 尝试次数限制：注册码、PAKE 和登录都限次（登录复用 `auth/lockout.rs`）。PAKE 的限次在两端（M2 已实现）：新设备的 8 位口令只回答一次运行，失败或用过即作废、换新口令；hub 的会合点只在内存、每账户至多 4 个、每个至多 8 条消息、10 分钟过期（见第 9 节 M2 第二部分）。
- 信箱与钥环：信箱只能由当前完整设备以自己的名义发、发给本账户的设备或机器、单条 ≤8 KiB；每个收件者至多 256 封、1 MiB，其中同一发件者至多 128 封、不带钥的信件（配对投递、索钥请求、未知用途）至多 32 封——其余留给钥匙信件；每个发件设备每分钟至多 120 封；只有收件者能取和确认，设备对不认识的用途也确认；设备被移除时它发出和收到的信件一并清掉；给 agent 的信件在登录时分页推送（每页 64 封，确认或释放完再推下一页）。钥环每账户至多 1000 条、每个写入者至多 500 条，名字 `<底名>/<写入者>[.<后缀>]` 只能由结尾那台当前完整设备写、只写一次，且只能写链上已提交的 epoch（恢复包只能对当前恢复钥）；移除设备或换恢复钥时在同一事务里清扫（见第 9 节「M2 复审二轮修复」）。
- 被当作通用隧道或免费网盘：用流量上限、异常持续吞吐检测、免费层保留期和服务条款来管。

**轮换后的流名（剩下的可链接性）**：流名每轮密钥换一套（第 9 节「轮换与重加密」，`docs/relay-and-plans.md` §5）。被移除的设备即使和 hub 合谋，也**算不出**轮换之后的流 id。但 hub 自己看得到迁移：一批流停写、一批新流出现，它可以按时间和填充后的大小把新旧名字对上。下面三条只能缩小这种关联，消除不了：

- 会话流在轮换后 6 小时内的一个随机时刻才迁（`naming::migrate_at`），时间上不紧贴轮换；重加密时立刻迁，不等。
- 同一批流打乱顺序重建（`migrate_round`），新名字出现的先后对不上旧名字停写的先后。
- 记录和页都填充到固定的大小档位（`rh-proto/src/record.rs`），大小只能对到档位。

所以结果是一个匿名集，不是消除：hub 能把一批新流和一批旧流对上，批内只能凭档位和之后的活跃程度猜哪条对哪条。一台机器的流越少、各流落在的档位越分散，这个集合就越小，只有一条会话流时等于没有。这和第 2 节的流量分析一样，是元数据层面的剩余风险，不影响内容的机密性。

因此「云端永远解不开」对静态数据和传输中的数据都成立，也包括被强制的情况。唯一的前提是当次下发的前端代码可信，这一点由上表第二行的缓解措施逐步消除。

### M1 第一部分（hub + agent 连接）实现说明

> 2026-10-15。浏览器界面与浏览器侧 hub 传输是第二部分。

- **crate**：hub（`rh-hub`，闭源，不在本仓库）；`crates/rh-devkit`（无头设备与回显 agent，测试与本地端到端用）；`rh-proto` 新增 `bridge`（回环桥接的线格式）、`flow`（hub 层信用窗口）、`driver`（feature `runtime`，tokio 上跑一条通道，agent 与无头设备共用）。
- **两种 WebSocket 消息**：二进制消息恰好是一个 `rh_proto::frame` 帧（数据面）；文本消息是一个以 `t` 标记的 JSON 控制消息（登录挑战、注册、在线态、信箱、错误），见 `docs/hub-api/websocket.md`。登录签名的 `hub` 字段用**签名方自己拨号的源**，hub 用自己配置的源校验。
- **HTTP**：`/v1/signup|login|logout|me|devices|chain|enrollments|mailbox`、`/healthz`（见 `docs/hub-api/http.md`）；运营方的路由（`/v1/admin/*`）与 Hub 一起记录，不在公开仓库。二进制字段一律小写 hex。
- **通道**：设备的 `ch` 单调递增、永不复用；hub 为 agent 一侧另行分配，同样永不复用。每个方向一个 512 KiB 信用窗口（`flow::INITIAL_CREDIT`），超发或超额授信即以 4408 关闭该通道。关闭码：4404 机器离线、4403 不在设备链里、4400 协议错误、4409 通道过多、4410 对端断开；连接级 1012 表示 hub 重启。
- **新鲜度门槛**：每条通道都要求有完整设备在 `FRESHNESS_MAX_AGE_MS`（12 小时）内为 agent 的链头签过证明；没有则回复新状态 `Stale`。设备连上后先发 `ATTEST` 帧（hub 存最新一条并转给 agent），再握手。只剩一台完整设备时它自己的证明有效（M3 复审）。
- **桥接**：`OPEN` 元数据是请求头（方法、路径、头部）；流内是 `[kind][len][payload]` 消息（text/binary/head/end）。rpc：请求体后跟 `end`，agent 回 `head` 和响应体再关流；mux/term：agent 回状态 101 的 `head` 即为 socket 打开。内部凭据 `x-rh-agent` 每次启动随机生成，`auth::guard` 只接受来自回环的；身份记为 `cloud:<设备 id>`。
- **agent 状态**：`<实例目录>/agent/state.json`（0600）存 hub、账户、机器 id、钉住的指纹与创世哈希、整条链（每次加载从创世重新验证）、首见时间、重放防护快照（握手回复发出前落盘，所以重启后无需拒绝窗口）、证明、`MK` epoch；`machine-keys.json` 存 `MK`。没有 `state.json` 的实例与今天完全相同。
- **本地端到端**（OrbStack 的 docker 起 Postgres；脚本在 Hub 一侧，不在公开仓库）。首次结果：金丝雀在数据库导出和 hub 的 trace 日志中命中 0（文本、hex、base64 三种拼写）；终端按键回显 p50 19.9 ms、p95 20.4 ms（主要是 agent 侧 16 ms 合帧）；hub 重启后 agent 235 ms 内重新上线。

### M1 第二部分（浏览器）实现说明

- **云模式判定**：hub 提供同一份 web 构建，缓存规则与 server 相同（带哈希的资源 immutable，壳 no-cache + ETag），并在壳的 `<head>` 写入 `<meta name="rh-hub" content="<源>">`、加 CSP（壳里的内联脚本按哈希放行）。页面据此进入云模式；由 server 提供的页面没有这个标签，行为与原来完全相同。

### M2 第一部分（加密流与离线历史）实现说明

> 2026-10-15。配对、`MK` 走通道并用 `UK` 包裹、恢复词、机器名加密、blob RPC 是第二部分。

**流的布局**（`rh-proto/src/stream.rs`）

| 流 | 名字 `(source, id)` | 记录格式 | 一条记录的正文（JSON） |
|---|---|---|---|
| 索引流（每台机器一条） | `("rh.index", "")` | `fmt 2` | `{"reset"?: true, "upserts": [SessionSummary…], "removed": ["source/id"…], "asOf"}` |
| 机器状态流（每台机器一条） | `("rh.status", "")` | `fmt 3` | `{"asOf", "settings", "accounts", "quota", "cli"}`，每条整体替换上一条；账号只留 id/label/kind/provider/email/usageEnabled，不含任何凭据 |
| 会话流（每个会话一条） | `("claude"/"codex", CLI 会话 id)` | `fmt 1` | `{"fromIndex", "items", "endIndex", "fp", "prefixFp"}`，从 `fromIndex` 起替换；`items` 就是 feed 的归一化条目 |
| 草稿（不落盘） | 同会话流 | `fmt 4` | feed 的 `draft` 帧，只作 `EPHEMERAL` 载荷 |

- 正文与今天 API 返回的同一份数据（列表行、feed 条目），前端渲染不改。单条正文 ≤60,000 字节；单个条目超过时把最长的字符串对半截断，标 `"truncated": true, "rhOfflineTruncated": true`（离线副本只为回看，原件在机器上）。默认不压缩。
- **快照页**：明文 `[flags][fmt u16][len u32][正文][零填充]`，填充到记录同一套档位，AAD 为 `"rh/v1 page\0" ‖ stream ‖ epoch`；编码 `epoch | nonce | ct_len | ct`，名字是编码的 SHA-256（内容寻址，hub 上传时校验，读者再校验一次）。页不绑定某个 manifest，下一次压缩会复用前缀没变的页。
- **manifest**：`签名流头 | fmt | 页数 | 页哈希… | 签名`，签名标签 `rh/v1 stream-manifest`，覆盖流头（流头自己也是机器签名的）和页表。最多 1024 页。读者从 `reader_from_manifest`（验两层签名后 `LogReader::from_head`）起步，按顺序把页的正文套到空状态上，再接 manifest 之后的记录。
- **压缩与变基**：manifest 的链接值沿用记录链 = 压缩，已经持有这些记录、链接一致的读者原样继续；链接值是新的随机值 = **变基**（agent 用本机 transcript 重建），读者必须从 manifest 重来。浏览器只有在某个签名流头已确认过它的副本时才会跳过一个 manifest（一个什么都没确认过的空副本不算「已一致」——这是验收时抓到的 bug：首次以页上传、落在 seq 0 的 manifest 曾沿用空流的全零链接，现在一律用新链接）。
- **草稿**：AAD `"rh/v1 ephemeral\0" ‖ stream ‖ epoch`，不签名（持流钥者可伪造），只显示为临时内容；hub 只转发给在线订阅者。
- 新帧 `PAGE = 0x19 {stream, hash, data}`（agent 上传页）。互通向量 `rust.json`/`ts.json` 覆盖流名、页、manifest、草稿。浏览器的 `LogReader` 与 Rust 逐条对齐（被拒时回滚到已确认处、心跳也校验链接值）。

**hub**

- Hub 每条流存归属、`next_seq`、最新签名流头与 manifest、记录与页的密文和字节数；存储布局属于 Hub 内部，不在公开仓库（第 8 节）。
- agent → hub：`APPEND {ch=请求号}` 在一个事务里锁行、比对 `expect_seq`、写记录、推进头、记账，提交后回 `ACK`；不符回 `CONFLICT`；与已存记录逐字节相同的重发再回 `ACK`。`HEAD` 用机器公钥验签、不超过已存记录、更新才保留。`PAGE` 校验哈希与结构后存入。`CHECKPOINT` 验两层签名、页齐全；`upto ≤ next_seq` 时移动指针（不后退）并安排宽限期后裁剪更早的记录，`upto > next_seq` 时变基（立刻删掉全部记录，从 `upto` 重新开始）。`EPHEMERAL` 只转发给本账户的在线订阅，不存、不记日志。非 CAS 的拒绝是文本 `stream_refused {ch, stream, code, retry_ms?}`（`quota`/`rate`/`forbidden`/`missing_pages`/`invalid`/`unavailable`）。hub 用 `stream_watched` 告诉 agent 哪些流有人在看（agent 只给这些流发草稿）。
- 设备：`SUB {ch, stream, from_seq}`（`ch` 与通道共用永不复用的计数器），之后按序收到：`GONE`（位置已被压缩掉）→ `CHECKPOINT`（全新读者或落后时）→ `RECS` → 最新 `HEAD` → 文本 `stream_synced {exists, next_seq}`；随后实时跟随。`stream_unsub` 退订。设备必须在设备链里且流属于本账户。页走 HTTP：`GET /v1/streams/{stream}/pages/{hash}`（会话 bearer，其他账户一律 404，`immutable` 缓存）。
- 每个订阅一个任务，从数据库读到流头为止；出站队列超过一半就等，不会因为补齐历史把连接挤断。
- 配额：每账户有存储上限和写入速率上限，超了回 `stream_refused` 的 `quota`/`rate`（数值见套餐，不在本文）。被 manifest 覆盖的记录过一段宽限期后裁剪；当前 manifest 不再引用的页同样在宽限期后删掉。
- 日志只写流 id 的前 4 字节、seq、条数和大小。

**对象存储与尺寸上限**

- 单页、单条记录的明文最大 61,440 B（加 16 B tag），一帧放得下；一个 manifest 最多 1024 页 ≈ 60 MiB 状态；一个会话副本最多保留最新的 20,000 个条目。
- 设备不直连存储：页一律经 hub 代理读取，见「会话正文移出 Hub 的数据库」。

**agent**（`server-rs/src/agent/streams/`）

- **范围**：本机自有会话、最近 30 天更新过的（`~/.claude` 里的外部会话不同步）。每 3 秒对比一次列表和 transcript 签名，有变化才发；多次变化合成一条增量，不会每次按键就追加。
- **预写 + 游标**：`<实例目录>/agent/streams.db`（SQLite，`synchronous=FULL`）每条流一行：确认过的位置（`next_seq`、`link`、`epoch`）和它对应的本地位置（会话：`{start, end, 最近 9 个 fingerprint, 文件签名}`；索引：`index_rows` 表；状态：上一条正文）。追加先写进 `pending`（逐字节的记录 + 发送后的位置和游标），再发 `APPEND`；`ACK` 到了才在**一个事务**里把位置、游标（索引则连同行表）一起提交。崩溃后原样重发，hub 认作同一次写入。`CONFLICT` → 丢掉 pending，用 transcript 重建（变基到 `max(hub 的头, 本地位置)`）。
- **增量**：从游标里最新一个仍与 transcript 一致的 fingerprint 位置起替换（就地改写的工具结果也会被重发）；都对不上（transcript 被改写、被 adopt）、或增量超过 4 MB → 变基。
- **首次注册回填**：按更新时间从新到旧，至多 4 个请求同时在途，字节预算 1 MB/s；超过 64 KB 的历史直接以快照页 + manifest 上传（一份数据只传一次）。
- **压缩**：尾部满 128 条、或尾部字节超过 max(512 KiB, 状态大小)，且距上次至少 60 秒；只在 transcript 到游标末尾仍一致时做，页复用上一个 manifest 未变的前缀。`MK` 换了 epoch 就以新 epoch 变基。
- **流头**：每次 `ACK` 后签一个；索引流和状态流每 60 秒一次心跳（离线副本的「截至时间」就是索引流最新流头的时间），会话流每次连上和每 30 分钟一次。
- **状态流**：每 60 秒经回环 API 取 `/api/settings`、`/api/accounts`、`/api/stats/quota`，CLI 版本每小时跑一次 `--version`（`RH_AGENT_STATUS_CLI=0` 关掉）；内容没变就不追加。
- 可调：`RH_AGENT_SYNC_DAYS`、`RH_AGENT_SYNC_EXTERNAL=1`、`RH_AGENT_COMPACT_RECORDS`、`RH_AGENT_COMPACT_EVERY_SECS`。

**浏览器**（`web/src/lib/hub/streams.ts`、`mirror.ts`、`web/src/features/cloud/offline-transport.ts`、`cloud-transport.ts`）

- `StreamClient` 按 `ch` 分发流帧，每条流的处理串行化；只交出被签名流头放行的记录、或按签名 manifest 校验过的页。出错按种类重订：`incomplete` 从已确认处，其他（断链、解不开、伪造、正文缺口）从 0。页最多 4 个并发，先取最后一页。
- `MachineMirror`：索引、状态始终跟随；会话副本保留最近打开的 20 个和最新的 5 个（这些在机器在线时也在后台跟随，「保持温热」）。每条流一条 IndexedDB 记录 `stream/<账户>/<机器>/<流>`，解密后的状态与**签名流头**（不是裸 seq）写在**同一个事务**里；重新加载时先验流头签名，再 `LogReader.fromHead` 续上。退出登录会清空并封存缓存。
- **离线传输层**：机器离线时，应用的请求由副本作答：会话列表、会话详情、往前翻页、设置、账号、额度、`/api/events?v=2` 的 mux（`hello`、`sessions:snapshot`、订阅快照与增量），全部只读；其他请求一律 503 `machine_offline`；终端 socket 直接关闭。
- **切换**：启动时先用副本秒开，通道一通就切到实时；通道断开超过 3 秒、或 hub 说机器离线，再切回副本。切换时关掉旧传输层的 socket、让查询失效、立即重连，会话 feed 按 `since/fp` 续传。
- **界面**：机器条下方一条提示「offline copy · as of <时间> · read-only: sending and terminals need the machine」（中/繁/日文案齐）；输入框禁用并说明机器离线（不做离线队列）；终端页显示需要机器在线；完全没有副本时才保留原来的整屏遮罩。

**云端能看到什么**：流的不透明 id（`HMAC(MK, …)`，对不上会话 id）和它属于哪台机器；seq、epoch、按档位填充后的记录与页大小、写入时间、条数和总字节；签名流头与 manifest（seq、时间、链接值、页哈希——都不含内容）；哪台设备订阅了哪条流、何时；草稿帧的大小和时序。看不到：标题、cwd、模型、状态、未读、正文、工具输出、主机名、账号、额度、CLI 版本——这些都在密文里。

### M2 第二部分（配对、恢复、吊销、机器名、blob）实现说明

> 2026-10-15。

**M0 复审的必修项**（`rh-proto/src/chain.rs`、`handshake.rs`；浏览器 `lib/e2e/` 同步）

- **移除设备清掉它设的恢复钥**：链状态记下 `recovery_set_by`（谁签的 `SetRecoveryKey`；创世里的算创世设备）。`RemoveDevice` 移除的若是它、或是经恢复加入的设备，`RSK` 一并作废——偷到 `RK` 再自己换上的恢复钥，不会在移除后继续有效。
- **握手回复带链后缀**：agent 的 `ReplyBody` 末尾附上发起方序号之后、自己链上的条目（至多 16 条）；设备在判定 `Stale`/`Open` 之前先并入（分叉即报错）。被 hub 扣住的移除条目因此一握手就能到达设备。
- ~~**新鲜度只认可信的证明**~~（已被 M2 安全复审取代，见下一小节 M1）：`freshness(请求方, 证明, now, max_age, clock)`——其它完整设备的证明有效，**除非**它是 24 小时内（按验证者自己的首见时间）经恢复**自行激活**（`ActivateRecovered`）的；被已有完整设备 `ApproveDevice` 批准的恢复设备与配对加入的设备一样立即可信（验收中发现：若批准的也不算，「原有设备 + 刚批准的恢复设备」这对组合里原有设备一整天找不到任何人为它作证）；请求方自己的证明只在它是唯一完整设备、且不是刚恢复的、也不是靠自己 24 小时内签的移除才变成唯一的时候有效。
- **证明真正分发**：设备在每次链变化（加/删设备、批准、轮换）后、以及每次连上 hub 时，给新链头签 `ATTEST`；hub 存每台设备最新一条并转给在线 agent。agent 每次开通道前要求「另一台可信完整设备」12 小时内为当前链头作证。
- ~~**体验上的代价**~~（M2 安全复审已去掉这条规则）：只剩一台设备、且它刚移除了别的设备时，24 小时内它自己的证明不作数，agent 会回 `Stale`——这是有意的（防「偷到设备 → 移除其它所有设备 → 独占」）。界面在这种情况下说明原因并给出时间。剩余风险：用户自己配对的「傀儡」第二设备（例如另一个浏览器配置文件）可以给同一个人作证；它防的是 hub 和偷到单台设备的人，不防持有两台设备的人。

**新原语**（Rust 与 TS 各一份，`vectors/rust.json`/`ts.json` 双向互通）

- `mnemonic`：BIP-39 编码 + 官方 2048 词英文表（SHA-256 `2f5eed53…dbda`），`RK` 默认 16 字节 = 12 词，带校验和；只借编码，不做 PBKDF2 种子。大小写、空白不敏感；错词、换位都能识别。
- `pake`：CPace-X25519（照 draft-irtf-cfrg-cpace 的形状）。生成元 `elligator2(SHA-512(DSI ‖ lv(口令) ‖ lv(ci) ‖ lv(sid))[..32])`，`ci = "rh/v1 pair-ci\0" ‖ 账户 ‖ 0 ‖ 新设备 id`，`sid` 16 字节由发起方选；`ISK = SHA-512("rh/v1 cpace isk\0" ‖ lv(sid) ‖ K ‖ Ya ‖ Yb)[..32]`，HKDF 展开成两把确认钥和一把配对秘密（即扫码里的 `s`）。浏览器侧 X25519 用 WebCrypto `deriveBits`，只有 Elligator 2 用 `BigInt` 手写。**Elligator 不是常数时间**（Rust 用 `num-bigint`）：输入来自一次性口令，侧信道观察者必须在它唯一一次使用内恢复出来——原型接受，正式版换常数时间实现。
- `pairing`：`Offer`（扫码内容：账户、新设备 id、两把公钥、`s`；文本形式 `RHP1-<base32>`，可粘贴；读的时候也接受 `DRP1-`）、`Hello{sid, Ya}`、`Answer{Yb, 新设备 id 与公钥, tag}`（tag 用响应方确认钥对整个转录做 HMAC，发起方验过才继续）、`Delivery`（账户指纹、发送设备 id 与两把公钥、各 epoch 的 `UK` 用发送方认证封装给新设备，整体用 `s` MAC）。新设备先验 MAC，再同步链、确认发送方是**链上当前的完整设备**、自己已被加入，才显示「已配对」。
- `wrap`：`seal_for_recovery`/`open_from_recovery`——各 epoch 的 `UK` 封装给恢复钥的 X25519 孪生钥（`RSK` 的 Montgomery 形式），发送方须是链上的完整设备。

**hub**

- **信箱**：`POST /v1/mailbox`（发给本账户某台设备，≤8 KiB）、`GET`（只取发给自己这台设备的）、`DELETE /v1/mailbox/{id}`（确认）。用途：1 = 一个 epoch 的 `UK`（发送方认证封装），2 = `MK`（机器离线时的兜底），3 = 配对投递。有新信时 hub 推一条 `mail` 控制消息。
- **钥环**：`GET /v1/keys`、`PUT /v1/keys/{name}`，名字 `[a-z0-9._/-]{1,128}`，每账户至多 1000 条（二轮复审起名字以写入者结尾：`<底名>/<写入者>`，见下文「M2 复审二轮修复」）。约定：`mk/<机器>/<MK epoch>/<UK epoch>` = 用 `UK` 包裹的 `MK`（`wrap_under`，上下文绑定账户、机器和两个 epoch）；`rk/<UK epoch>/<发送设备>` = 给恢复钥的 `UK` 封装。hub 只见名字和大小。
- **口令配对的会合点**（只在内存）：`POST /v1/pairings`（新设备开）、`GET`（本账户已有设备列出）、`POST|GET /v1/pairings/{id}/messages`、`DELETE`。每账户同时至多 4 个、每个至多 8 条消息、单条 ≤4 KiB、10 分钟过期。限次由**两端**负责：新设备一个口令只回答一次运行，之后作废并换新口令；已有设备每输入一次只跑一次；发起方读到回答后立即关掉会合点。hub 作为主动攻击者每次运行只有一次在线猜测。
- **移除即切断**：`RemoveDevice` 进链时 hub 关掉该设备的 socket，之后拒绝它登录 `/v1/client`（4403）。它的会话 token 仍能取页和钥环，但那些都是它没有钥的新 epoch 密文。

**agent**

- **`MK` 走通道**：通道里新增 agent 本地路由 `/rh/*`（不转发到回环）：`GET /rh/info`（机器 id、显示名、持有的 `MK` epoch）、`POST /rh/display-name`、`POST /rh/machine-key {epoch, key, reencrypt}`——只接受链上当前的**完整设备**，epoch 必须比已有的新（同 epoch 不同钥 → 409）。收到后落盘并通知同步任务。信箱里的 `MK` 只在机器离线时用，且必须是链上完整设备用发送方认证封装的。
- **轮换与重加密**：新记录、页和草稿都用**最新** epoch 封装。流名按 epoch 派生（`streams/2`，`docs/relay-and-plans.md` §5，`server-rs/src/agent/streams/naming.rs`）：`e` 是流创建或迁移时的 `MK` epoch，记在 `streams.db` 的 `name_epoch` 里。
  - 轮换时索引流和状态流立刻在新 epoch 的名字下重建；会话流在 6 小时内的一个随机时刻、按打乱的顺序，逐条在新名字下用本机 transcript 重建（manifest + 页，从 seq 0 开始），索引条目的 `se` 写明它的流名 epoch（没有 `se` 就是第一个 epoch）。旧流要等新流的检查点被确认、且已确认的索引指向新名字之后才删；列表里暂时没有的会话一律保留（见下文「M3 重加密不完整」）。
  - `reencrypt: true` 时不等随机时刻，立刻迁移：重加密就是这次迁移，旧 epoch 的密文随旧流一起从 hub 上消失。
  - 读者找索引流和状态流时先试最新的 epoch，找不到再往回试（机器离线、还没迁移）。
  - 只有在某台设备于通道问候里声明了 `streams/2` 之后（agent 记在 `streams.db` 里）才这样做。在那之前仍是原来的做法：所有流名都由第一个 epoch 的 `MK` 派生，`reencrypt: true` 时每条流用本机 transcript 在 `next_seq + 1` 变基重建，hub 收到变基立即删旧记录，并马上清扫不再被引用的页。
  - 来历：M2 验收中抓到最初流名用的是最新 epoch，轮换后 agent 开了一套新流、旧密文原封不动，于是先固定成第一个 epoch；按 epoch 改名、连同迁移和删旧流，是 M3a 补上的（下文「M5」）。
- **链变化即断开**：每次并入新条目后，agent 关掉不再是当前设备的通道（4403）；握手本来就只放行当前设备。
- **机器显示名**：默认主机名，可经 `/rh/display-name` 修改（≤64 字符、无控制字符，空 = 回到主机名），存 `state.json`，写在加密的状态流里（`displayName`）。hub 上仍只有 id。
- **blob 通道**：桥接的 `blob` 类只接 `/api/fs/download`、`/api/fs/upload`、`/api/media/github` 三个路由；与 rpc 同样的桥接格式，但在通道内多路复用（`rh-proto/src/mux.rs`，两端都按 control > term > rpc/mux > blob 排）里优先级最低、分小块发送，不挤占终端和 mux。

**浏览器**（`web/src/lib/hub/`、`features/cloud/`）

- **钥匙在本地怎么存**：每个浏览器有一把不可导出的 AES-GCM 本地包裹钥（`CryptoKey`，存 IndexedDB）；各 epoch 的 `UK` 只以它加密后的形式存（`uk/<账户>/<epoch>`，AAD 绑定账户和 epoch），用时直接解成不可导出的 HKDF 钥，只有封装给别的设备/恢复钥、或生成新 epoch 时短暂出现原始字节、用完清零。这防的是钥库里出现明文、内存里留着字节，防不住同源代码：它能像这里一样用本机包裹钥解出 `UK`（第 7 节「网页前端投递」）。`MK` 本地**不存**：只有钥环里用 `UK` 包裹的密文（可缓存）。M1 留下的明文 `MK` 在首次加载时包进 `UK` epoch 0 后删除。测试检查钥库里写过的每个值都不含原始 `UK`/`MK` 字节。
- **配对**：新浏览器登录后显示二维码 + 可复制的 `RHP1-…` 文本（默认）、「改用口令」（8 位数字）或「恢复词」三种方式；已有设备在「设备」页选「粘贴文本 / 扫码（`BarcodeDetector`，没有则 jsqr）/ 输入口令」，然后比对两边显示的设备指纹再确认。新设备只有在投递的 MAC、链校验、解封都通过后才显示「已配对」。加设备成功但投递失败时可重试（已在链上的设备改用用途 1 的信件重发 `UK`，不需要 `s`）；在链上却没有 `UK` 的设备会明确提示去另一台设备上「重发钥匙」。
- **恢复词**：12 个词只显示一次，随后随机抽 3 个让用户填回；输入时提示未知的词、缺几个词或校验和不对。恢复后设备进入「等待批准」，显示何时可以自行激活（提前点会被拒并给出时间）；其它所有设备在此期间显示「批准 / 移除」的告警条。账户没有恢复词时，设备页提供「生成新的恢复词」。
- **移除**：设备页每台其它设备有「移除」，可勾选「同时重加密历史」；完成后列出轮换结果（新 `UK` epoch 发给了几台设备、是否封装给恢复词、每台机器的新 `MK` 是经通道还是信箱送达）。通道暂时打不开（机器离线或链头还没被另一台设备确认）时 `MK` 走信箱，重加密请求记在本地，下次连上该机器时在通道里补发（agent 收到同一把钥匙且 `reencrypt: true` 即开始重加密）。被移除的浏览器删掉钥匙、钥环缓存、设备钥和离线副本，显示「此设备已被移出账户」。
- **跟随设备链**：每次连上 hub 都从自己的序号订阅链，合并推送来的条目（自己的条目若已被推送先到，只校验一致），每次链变化、每次连上、以及每 3 小时为链头签证明；收到 `mail` 通知就取信箱。`MK` 有新 epoch 时，离线副本和机器列表的读者都会补上新钥，并按新钥找流：索引流和状态流先试最新 epoch 的名字、找不到再往回试，会话流按索引条目的 `se`（上文「轮换与重加密」）。

- **blob**：云模式下图片（`HostImage`、灯箱、文件预览、markdown）、下载、上传、GitHub 私有图都经通道的 `blob` 管道，取回后成 `blob:` URL（卸载即撤销）；hub 源上没有任何内容请求。上限：图片 25 MB、下载 256 MB、上传 64 MB（隧道内另有 64 MiB 请求体硬上限）；按 `content-length` 和实际流量两次检查；图片 LRU 缓存 32 张 / 96 MB；进度与错误显示在机器条的传输列表里。
- **机器名**：机器列表与机器条从状态流解密显示名，id 作小字；读不出时只显示 id。在线时可改名。
- **离线搜索与首条未读**：`offline-search.ts` 逐条移植 `feed/search.rs` 与 `attention::first_unread`（复用 Rust 的测试用例），离线传输层用解密后的副本回答。

**验收**

- 本地端到端（扩展后）通过：机器名经状态流送达、300 KB 文件经 blob 流 101–123 ms 取回；无头设备扫码文本配对（拿到 `UK`、从钥环解出 `MK`、读到历史）；口令配对先输错一次——两端都拒绝并作废——再用对的口令配上；恢复词 12 个 → 从恢复包解出 `UK` → 待定 → 批准后激活；移除扫码设备并轮换：`MK` epoch 1 在通道里交付并重加密，被移除设备的 socket 被关、再登录被拒，新记录用新钥能读、用旧钥读不了，hub 上旧 epoch 的记录和页一条不剩，之后的新一轮仍能写进重加密后的流；数据库导出与 trace 日志里金丝雀命中 0。
- 本地真浏览器（`cloud-dev.sh`，三个源 `127.0.0.1`、`localhost`、`localhost.` 当三台独立浏览器，另加 `rh-device` 无头设备）：注册时显示 12 个恢复词并要求勾选/回填；机器列表与机器条显示主机名、改名后显示新名；会话里的主机图片经 blob 通道画出、下载按钮取回的文件与原件逐字节相同，页面对 hub 源除 `/v1/*` 和静态资源外没有任何请求；离线时会话内搜索命中副本；扫码文本配对（新浏览器显示二维码 + 文本 + 指纹，旧浏览器粘贴、比对指纹后加入，0.6 s 内显示「已配对」并能看历史）；浏览器输入口令配对无头设备（先输错：提示「口令已作废」）；恢复词（换位的词提示校验不过；待定时自行激活按钮不可用；另外两台显示批准/移除告警；批准后 0.3 s 激活并看到历史）；从浏览器移除设备并勾选重加密：`MK` 在通道里交付、agent 关掉被移除设备的通道、被移除的浏览器清空钥库并显示「此设备已被移出账户」、被移除的无头设备再登录被拒且只持有旧 epoch 而 hub 上只剩新 epoch 的密文；剩下的设备实时看到移除后写入的记录，停掉 agent 后离线副本也能读到（不刷新页面）；金丝雀、机器名、主机名、恢复词、会话标题在数据库导出与 hub 日志里命中 0。验收中抓到并修掉的问题：流名随 `MK` 轮换而变（当时改为第一个 epoch；后来改成每轮换名并迁移，见上文「轮换与重加密」）、hub 推送先于追加的应答导致「expected entry 3, got 2」、加设备成功但投递失败后无法补救、新注册机器的名字要刷新才出现、轮换后离线副本拿不到新 `MK`（钥环写入改到发信之前 + 缺钥时刷新钥环）、`MK` 只能走信箱时重加密请求丢失、批准的恢复设备不能作证导致原设备一天打不开通道。

**已知缺口**：两台设备同时轮换可能撞 epoch 号；签了移除条目后页面崩溃则不会自动补做轮换；钥环条目没有删除接口（旧恢复包留着，但旧词已不能加入）；摄像头扫码只做了单元测试（`BarcodeDetector`/jsqr 解码回读），没在真摄像头上试；Elligator 2 非常数时间；页仍在数据库里；流的删除与保留期未实现。

### M2 复审二轮修复

> 2026-10-17。复核的概念验证（PoC A/B/B2/C 等）都改写成了回归测试，修复前失败、修复后通过：`rh-proto/src/attack_regressions.rs` 的 `m2_verify` 模块、`agent/state.rs`/`link.rs`/`streams` 的单元测试、`web/test/cloud-m2-verify.test.ts`，以及 Hub 自己的测试。

**账号变更提醒和恢复否决**

- **合并不原子 → 生效的一律处理**：`ChainState::merge_partial`（TS `mergePrefix`/`verifyPrefix`）说明应用了几条、停在哪里；`merge` 写明不是原子的。agent 的 `absorb` 返回生效的新条目和错误，链接层对生效的每一条都告警、`drop_removed`、保存——来自 hub 的帧和来自设备 hello 的条目一样（按前后 seq 算，不看握手成败）。没有做成「整批要么全生效」：那样「加入 + 太早的激活」同批到达时加入永远不被记录，验证者既不会告警，也永远收不下激活。
- **`ActivateRecovered`（和 `ApproveDevice`）也告警**。
- **分叉告警送到所有设备**：分叉、回滚、创世或指纹不符记为告警（`state.json`，同一告警每小时至多一次），写进加密的状态流（`alarms`）和 `/rh/info`，并走 Web Push + Bark；机器列表在那台机器上显示「链告警」。hub 能扣住状态流的新记录，但伪造不了、改不了，签名流头会显示它落后。
- **谁和这台机器握过手**（链 v3 评审 D3 的后续）：agent 把每台握手被接受的设备记在 `state.json`（`controllers`，回复发出前保存；新设备存不下就拒绝握手，已在记录里的照样放行），写进加密状态流（`controllers: {from, fromMs, seq, devices}`，空也写）和 `/rh/info`；新设备或链前进都写一条新记录。「我的设备」的重新登记提示把它当证据逐台写明（连接过 / 自某时起没有记录 / 不知道），从不因它撤掉提示——握过手的设备能改这份记录。撤掉只能由人：「我确定它从没连接过」，确认后记在本浏览器、低调列出、可撤回。细节见 `docs/local-aggregator.md` 的 D3。
- **浏览器确认「被移除」**：`confirmRemoval` 与 `sync()` 走同一套校验（钉住的创世、上次见到的链头、自己的活时钟与保存的首次看到时间），不再把整条链当历史。hub 持恢复词让自己的设备立即自行激活再移除主人时，主人的浏览器停在加入之后，不确认移除、不清密钥。
- **错过加入和激活不再锁死**：链按本设备时钟能走多远就收多远并保存；太早的激活和其后的条目「压后」（`heldBack`），加入显示为待批准。批准＝以用户的话收下 hub 的链；移除＝在 hub 链头上签否决并收下；否则本设备首次看到加入满 24 小时后自动收下（agent 同理：压后，到期后重新订阅）。
- 剩余：压后期间本设备看不到其后的链条目，除批准/移除外的写操作会被拒绝并提示先处理。

**密钥轮换完整性**

- **只用链承诺的最新 `UK` 包裹**：`ensureUserKey` 只返回链上最新一轮且本设备持有的 epoch；缺了就是「缺少密钥」（`missingUserKey`）：先取信箱，再给其它完整设备发索钥请求（信件用途 4，只有 epoch，每 10 分钟至多一次），对方收到后把持有的全部 `UK` 封装发来；在此之前不包裹任何新 `MK`。设备页显示缺口，可「再次索取」或「再轮换一次」。
- **钥环名字绑定写入者**：`<底名>/<写入者>[.<后缀>]`，hub 只让结尾那台当前完整设备写、只收链上已提交的 epoch（`mk` 要求机器在链上、两个 epoch 都已提交；`rk` 要求发送者即写入者、对当前恢复钥），每写入者至多 500 条。遇 409（自己名下已有别的字节：另一个标签页，或 hub 篡改）换一个随机后缀重试，不再跳过。移除设备或换恢复钥时在同一事务里清扫：别的恢复钥或非当前发送者的恢复包删掉；被移除写入者的条目只留每个已提交 `MK` 包裹一份（保住历史可读），其余删掉。旧名字（无写入者）仍可读。
- **信箱额度**：每收件者 256 封中同一发件者至多 128 封，不带钥的信件至多 32 封；移除设备时它发出和收到的信件在同一事务里清掉；浏览器确认未知用途的信件。
- **重新注册**：`agent enroll` 删掉旧的 `machine-keys.json` 和 `streams.db`；写入方只装链上为本机提交过的 `MK`，按其中最新的封装。

**配对名额与低危**

- **配对名额**：不是链上完整设备的设备（新设备）同时只开一个配对（新开的替换旧的），且只在注册后 30 分钟内能开；任何当前完整设备都能关掉本账户的任何配对（配对列表里有「关闭」）。只靠密码仍能在每次注册后的 30 分钟里占一个名额——剩余风险，靠关闭按钮和登录限速。
- **吊销**：标记移除、删会话、清信件、清扫钥环与链条目在同一个事务里；hub 启动时按每个账户的链重建一遍。
- **早先没有绑定设备的会话**：截到创建后 15 分钟。
- **`stream_delete`** 只接受链上当前的机器。
- **agent 延迟信件**：按 id 去重、至多 64 封；被挤出的若 epoch 已过时就确认，否则发 `mail_release` 留在信箱里、下次登录再推（hub 照样推下一页）。
- **重加密待办**：只在 agent 回 200、或 409 说它已持有更新的 epoch 时清除；`uncommitted`（agent 的链落后，hub 可以故意扣住提交造成）和 `key_mismatch` 都保留、下次再问。

**复核修复（独立评审 N1–N5 与注册上限）**

- **测试缺口（账号变更提醒）**：新增链接层测试（hub 帧和设备 hello 两条路径），验证一批中途失败时，生效的每一条都告警、`drop_removed` 并保存；恢复旧的「出错就不处理」写法两个测试都会失败。
- **N1 否决只针对被压后的那台设备**：压后期间只允许移除那台自行激活的设备（其它移除被拒绝：那会在 hub 链头上签名、顺带收下激活并给它发新 `UK`）；否决同一批里移除它带进来的一切——由它或由它带进来的设备添加、批准、激活的设备，用恢复钥加入或激活的设备，以及它们添加的机器；已被本设备信任的设备在这段里签的条目保留。待处理横幅列出压后的条目（批准会收下的内容），压后期间其它「移除」按钮不可用。**注意**：面对持有恢复词的恶意 hub，任何否决都无法排在激活之前——hub 决定链的顺序，否决只能是激活之后的一条移除；补救是否决 + 换恢复词，若怀疑 hub 本身，在机器上 `agent re-enroll`。
- **N2 钥环挤占**：被移除写入者的 `MK` 包裹只在没有当前写入者（或旧名字）持有同一底名时保留一份；账户上限只计当前完整设备和旧名字的条目。单独提交的 `KeyEpochs`（不属于移除后的轮换或机器注册）在设备和机器上都告警。轮换写钥环遇到 507 时仍把新 `MK` 交给机器，并在报告里用红字说明「未写入钥环」。
- **N3 告警刷屏**：hello 的分叉只在发送方静态钥与链上该设备一致时才算告警，否则只是拒绝；agent 另有全局上限：每小时至多 4 条告警。
- **N4 移除时的竞态**：发信和写钥环在自己的事务里、在移除也会取的行锁下再查一次发件者（和设备收件者）/写入者仍在账户里。
- **N5 索钥回复**：先发对方索取的那一轮，再从新到旧发其余的，避免被每分钟 120 封的限速截断。
- **注册上限**：只凭密码注册设备，当时临时定为每账户每小时至多 6 台、链外待加入（30 分钟窗口内）至多 4 台。M3a-4 起：每账户每天至多 10 台（按数据库计数，重启不忘），链外待加入同时至多 3 台，24 小时未进链即删除；进链之后才计入套餐的 `devices.max`（`docs/relay-and-plans.md` §4.3）。链 v3 下，关掉别人开的配对（一并吊销开它的链外设备）和签移除都只有可管理账号的设备能做。

### 会话正文移出 Hub 的数据库 实现说明

> 本节是 Hub 的内部实现与运维记录（键名、对象键、迁移、部署与验收），不在公开仓库。

对客户端可见的部分：

- 页经 `GET /v1/streams/{stream}/pages/{hash}` 读：设备会话鉴权、只限本账户（其他账户 404），支持单个 `Range`（见 `docs/hub-api/`）。客户端拿不到任何指向存储的地址。
- Hub 崩溃时最多丢最后约 1 秒已确认的追加（第 5 节）：agent 的下一次追加遇到 `CONFLICT`，从本机 transcript 变基重建；读者只放行机器签名流头覆盖的记录，丢掉或变短的尾巴不会被当成流的内容。
- **agent**：`stream_refused {code: "compact"}` 时丢掉这次 pending（hub 没存）、立刻压缩，再重发增量。新的压缩触发：尾部 5 分钟没有新追加（`RH_AGENT_COMPACT_IDLE_SECS`），或最老的未覆盖记录满 30 分钟（`RH_AGENT_COMPACT_OLDEST_SECS`；`streams.db` 新增 `tail_since_ms`），原来的条数/字节阈值保留。所以 Hub 上未压缩的尾部一般只有最近几分钟、几十条。

### 直连通道（已实现）

> 2026-10-16（由测量探针而来）。代码：`rh-proto/src/{path,channel,driver,rtc,direct}.rs`、`server-rs/src/agent/direct.rs`、`web/src/lib/{e2e/path.ts,e2e/driver.ts,transport/p2p.ts}`。

**为什么做**：经 hub 中转、离 hub 较远时，按键回显 p50 ≈ 176–190 ms；两端能直接互通时（同一台机器、同一个局域网、两边都有 IPv6，或 NAT 打得通）可以降到局域网或公网直线的时延。探针在真实网络里测过（见下方「测量记录」），值得做。**hub 永远是兜底**：每条通道都先经 hub 建好，直连只是同一条通道的第二条路，不另设 TURN。

**一条通道，两条路**

- 握手时协商：设备的 `HelloBody.client` 带 `paths/1`，agent 回复的 `features` 里有 `paths/1`（以及直连开着时的 `direct/1`）才启用；旧版两端照旧走原来的帧格式。启用后，通道里**每一个** mux 帧（两条路上都一样）都包在一个带序号的信封里，hub 看到的只是 `DATA` 帧稍大了 17 字节。
- 信封（Noise 明文里，hub 看不到）：

  | 种类 | 内容 | 走哪条路 |
  |---|---|---|
  | `DATA` 1 | `seq u64, ack u64, mux 帧` | 任一条 |
  | `ACK` 2 | `ack u64` | 任一条 |
  | `PROBE` 3 / `PROBE_ACK` 4 | `nonce u64` | 原路应答 |
  | `DOWN` 5 | `原因 u8` | 只走 hub：「我不再用直连了」 |

  `seq` 每个方向从 1 起数，`ack` 是「到此为止一条不缺」的最大序号。
- **切换**：直连握手完成即切（先建后拆）：新帧走直连；在直连上发出的帧留着直到对方确认；接收方按序号交给 mux——从快路先到、而前面还在 hub 上的帧先扣住，等缺口补上再一起交出（扣住的上限 16 MiB，超了视为协议错误）。
- **回退**：直连的 DataChannel 关了、对端连接失败、一条消息解不开、1 秒一次的探测 3.5 s 没有任何回音，或者**有经直连发出的帧在等确认，而直连 1.5 s（或十个往返，取大者）没有任何进展**——就放弃直连：先在 hub 上发 `DOWN`，再把所有未确认的帧按原序号经 hub 重发，接收方丢掉已经收过的。对方收到 `DOWN` 也同样退回并重发自己未确认的。所以无论每一帧走了哪条路，mux 看到的都是不丢、不重、不乱序（终端照旧还有 shim 偏移这一层）。「进展」指对方的数据经直连到达，或者一个确认释放了经直连发出的帧；探测不算（它只说明对方还在，不说明这边发的到了）。从最老那一帧发出算起的旧规则会把正常但慢的直连判死：手机网络上 DataChannel 的缓冲（最多 1 MiB）要好几秒才排空，对方的确认又排在对方自己的积压后面，于是两端轮流放弃一条好好的直连，经 hub 重发全部积压，几秒到几十秒后再重连——和 2026-10 手机（4G）上直连每 20–60 s 断一次、两端都有发起的样子吻合。代价是：一条在自己的大上传后面排队的按键，现在要等直连的发送缓冲排空（最多 `DIRECT_BUDGET`，1 MiB）才发出，而不是 1.5 s 后退回 hub 重发——直连还在一点点送，退回 hub 也得先把同样的积压重发一遍。
- **确认**：直连上收到的帧 15 ms 内确认（攒满 16 帧立即），能捎带就捎带；回答探测时顺带把欠的确认发出去——页面在后台、定时器被浏览器节流时，对方的探测仍会把确认带回来。
- **探测与指示**：直连每秒探测一次（兼作保活），设备另外每 5 s 探测一次 hub 路径，所以界面能同时显示两条路的往返时间。
- **流量控制**：hub 路径的信用窗口不变；直连上「已交给 WebRTC、还没上线」的字节超过 1 MiB 就不再往直连上放（浏览器看 `bufferedAmount`），未确认超过 4 MiB 也停，等确认。mux 的子流窗口照旧，blob 也一样自动走当前路径。

**信令在端到端通道里**

- 设备在已有通道里开一条 `mux` 子流 `GET /rh/direct`；agent 像 websocket 一样回 101（直连关着时回 403）；之后每条消息是一条二进制的 `Signal`：`OFFER {id, 设备 DTLS 指纹, SDP}`、`ANSWER {id, agent 指纹, nonce, SDP}`、`CANDIDATE {id, 候选行 | 空=收集完}`、`BYE {id, 原因, 说明}`。
- 这些都是 Noise 通道里的密文，hub 看不到 SDP、候选（双方 IP）和证书指纹。探针用过的 hub 明文信令房间只给探针用，正式功能不碰。

**DataChannel 上再跑一次 Noise（选择与理由）**

- 做法：DataChannel 打开后，设备在上面发起一次**新的** `Noise_IK_25519_AESGCM_SHA256` 握手，用与 hub 通道相同的静态钥，prologue 是 `"rh/v1 direct\0" | 账户 | 设备 | 机器 | hub 通道的握手哈希 | agent 这次给的 nonce | 设备 DTLS 指纹 | agent DTLS 指纹`。首包照旧只带链视图（`HelloBody`），不带请求。
- 没有选「把现有通道的传输钥带过去、换新 nonce」，理由：
  1. Noise 的传输钥配的是隐式递增 nonce，同一把钥在两条路上用就得自己管 nonce 空间，一旦算错就是 AES-GCM nonce 重用；`snow` 也不把传输钥交出来。两条路各有自己的钥和 nonce，从根上排除了重用。
  2. 隐式 nonce 要求严格顺序，一条消息丢了或乱序整条会话就作废；两条路共用一个会话就做不到「直连死了、hub 照常」。各自一个会话，各自在自己有序可靠的管道里。
  3. 重新握手就是重新**准入**：agent 用 `handshake::accept_direct`，与 hub 通道完全相同的规则——补链、设备必须是链上当前设备、链头 12 小时内有完整设备作证（新鲜度）、重放防护。被移除或视图过期的设备拿不到直连，就像拿不到 hub 通道一样。
  4. 新的临时钥给直连会话独立的前向保密；它不依赖浏览器 WebRTC 栈的 DTLS 是否可靠——两条路的保护强度相同。
- 代价：多一个往返（同一台机器上不到 1 ms，手机流量上一个直连往返），换来上面四条。

**DTLS 指纹的绑定**

- 每一方在信令里**写明**自己证书的 SHA-256（`OFFER.fp`、`ANSWER.fp`），收方要求 SDP 里的 `a=fingerprint` 正是这一个，否则回 `BYE BadFingerprint`（`path::check_fingerprint`）。信令在端到端通道里，hub、STUN 服务商或网络上的人改不了；浏览器和 str0m 的 DTLS 都只接受与 SDP 指纹相符的证书。所以 DTLS 这一层也没人能插在中间。
- 两边的指纹又写进了直连 Noise 的 prologue：双方看到的证书哪怕差一个字节，直连握手就解不开。测试覆盖：SDP 指纹被换、写明的指纹被换、两个指纹互换、nonce 或 hub 握手哈希不同，都被拒绝（`path` 与 `handshake` 的单元测试，`direct` 的进程内测试里 agent 对篡改的 offer 回 `BadFingerprint`）。

**新鲜度：被移除或过期的设备失去直连，与失去 hub 通道完全一样**

- 直连属于它所在的通道：通道的驱动持有直连的管道，通道一结束（hub 断开、agent 因移除关掉通道 `drop_removed`、协议错误）管道就被丢掉，WebRTC 连接随之拆掉、UDP 套接字关闭，对端看到 DataChannel 关闭就退回 hub（而它的通道也已被关）。
- 每次（重新）建立直连都重新准入：移除后、或链头没人作证超过 7 天，直连请求被拒（`Refused`）。已开着的通道也会过期：最近一条算数的证明满 7 天（认这个链头的证明，以及 agent 越过更早链头之前对它签的证明），agent 就关掉这条通道（`4412`），直连随之拆掉——hub 通道和中继通道都一样，到点、链变化、每开一条子流都会再查（`docs/local-aggregator.md` §3.4）。
- 测试：`driver::closing_a_channel_closes_its_direct_path`、`handshake::a_removed_or_stale_device_gets_no_direct_path`、`direct::a_removed_devices_direct_path_closes_with_its_channel_and_cannot_return`、`link::an_open_channel_closes_once_no_admin_vouched_for_this_view_in_seven_days`；e2e 里被移除的无头设备的直连随移除一起关闭。

**agent**

- `RH_AGENT_DIRECT=0` 关掉直连：不回答信令（403）、不绑定任何 UDP、`features` 里没有 `direct/1`（`paths/1` 照旧，它不花什么，还让设备显示 hub 往返时间）。`RH_AGENT_DIRECT_STUN` 可替换 STUN 列表（逗号分隔，空 = 只用 host 候选）。
- UDP 套接字按次绑定、随直连关闭；只有已注册、正在运行 hub 连接的实例才会绑定，没注册的实例什么都不绑。同时至多 16 个直连（所有通道合计）。
- 候选：本机默认路由上的 IPv4 和 IPv6 地址作 host 候选（不提供回环和链路本地地址），Cloudflare、Google 的 STUN 给出 srflx 候选，浏览器的连通性检查到达后成为 prflx 候选——IPv4、IPv6 一样。浏览器把自己的局域网地址藏在 mDNS 名字后面，str0m 解析不了就跳过，靠 prflx 配对（同一台机器、同一个局域网都是这样连上的）。同一台机器不需要回环地址：浏览器连的是本机的默认路由地址（测试 `rtc::the_same_machine_connects_over_its_default_route_address`）。
- 直连握手的准入与 hub 通道共用状态：链、时钟、重放防护（回复发出前落盘）、证明；直连首包里带来的新链条目照常触发「关掉被移除设备的通道、告警、重试信件」。

**浏览器**

- `lib/transport/p2p.ts`：只有页面自己的那条通道尝试直连（改名、交钥匙这类临时通道不尝试）。`RTCPeerConnection`（STUN：Cloudflare、Google，无 TURN）+ 一条有序可靠的 DataChannel `rh`；有 `getRemoteCertificates` 的浏览器（Chrome）还会核对 DTLS 对端证书的 SHA-256 就是 answer 里写明的那个；一次尝试 15 s 内没完成直连握手就作废（`BYE Failed`），然后按 2 s、4 s、8 s……最多 5 分钟加抖动重试，每次都是新的 `RTCPeerConnection`（相当于 ICE restart）；直连撑过 60 s 后退避归零；网络变化（`online`、`navigator.connection` 的 `change`）和页面重新可见时立刻重试——但连续 3 条直连都是接上之后不到 60 s 就断（`SHORT_LIVED_LIMIT`），之后就只按退避走：网络变化、页面重新可见、新开的通道都不再立刻重试，直到某条直连撑过 60 s，或者用户把直连关掉再打开。退避和这个计数按机器保留在页面的 `MachineChannel` 里（`DirectHistory`），hub 重连后的新通道接着原来的退避，不再从 2 s 开始。每条通道同时只有一个尝试；多台设备各自有各自的直连。
- 设备设置「只走 hub」：存在本机（`localStorage` 的 `rh.hub.hubOnly`），打开时立刻关掉直连、不再尝试；关掉后开始尝试，不用重连。
- 路径指示：机器条上「端到端加密」旁边显示「直连 · 1 ms」或「经 hub · 180 ms」（当前路径最近一次探测的往返时间），悬停显示两条路的往返时间。

**存储不变**

- agent 照旧把每一条索引流、状态流、会话流的记录写到 hub，与走哪条路无关。直连只加速**实时视图**：页面经通道拿到的 feed（`/api/events?v=2` 的 mux）、RPC、终端、blob 都在当前路径上，这些和走 hub 时是同一份数据。
- 加密流的记录**不**走直连：浏览器的离线副本只从 hub 读密封记录（同样的 seq、epoch、机器签名的流头），所以副本与 hub 上的完全一致、可验证，新设备和离线阅读照旧从 hub 来。以后如果为了让副本更新得更快而在直连上推记录，推的必须是发给 hub 的**同一批**密封记录和签名流头，浏览器按 seq 去重——两条来源不能有两份不同的数据。

**各方能知道什么**

| 谁 | 能知道 | 不能知道 |
|---|---|---|
| hub | 某条通道上有一些信令大小的密文帧（何时在尝试直连）；直连接上后这条通道在 hub 上的流量变少、直连断了又变多；回退时重发的帧的大小与时间 | SDP、候选（双方的 IP）、DTLS 指纹、直连是否成功（只能从流量推测）、直连上的任何内容 |
| STUN 服务商（Cloudflare、Google） | 每次尝试时两端各自的公网 IP 和端口、时间（设备和机器各自去问） | 两次查询属于同一对、连上没有、任何内容（STUN 请求不带身份） |
| 网络上的人（含运营商、局域网） | 双方 IP、UDP 流量的大小与时序（DTLS 外层） | 内容：DTLS 里面还有 Noise |
| 你自己的设备与机器 | 彼此的 IP：agent 看到设备的公网地址（srflx/prflx）以及设备给出的候选（浏览器的局域网地址是 mDNS 名字，不暴露），设备看到机器的默认路由地址（含局域网 IPv4 和公网 IPv6）和 srflx 地址；agent 的日志里有直连选中的地址对 | — |

所以「只走 hub」是给不想让自己的设备和 STUN 服务商知道 IP 的人用的；默认允许直连。

**测试**

- Rust 新增 34 个：`path`（信封、信令、DataChannel 消息编解码，指纹解析与篡改被拒，prologue 的每一部分都参与绑定，乱序、重复、直连中途丢失的 200 种交错下都按序交付）、`channel`（切到直连再回退不丢不重不乱序、已交付的重发被丢弃、探测与保活、未确认帧超时、解不开的直连消息只断直连、没有余地时不为确认唤醒）、`handshake`（直连与 hub 通道一样准入且密钥不共用、指纹或 nonce 或通道哈希不符即失败、被移除或过期的设备拿不到直连）、`driver`（打字途中静默断网与 DataChannel 关闭都不丢键、关掉通道直连随之关闭）、`rtc`（回环与同一台机器的默认路由地址都能连、UDP 被挡时连不上、STUN 解析）、`direct`（进程内的真 str0m：打字途中断网不丢键、UDP 被挡时 hub 照常且之后重试成功、篡改指纹的 offer 被拒、被移除设备的直连随通道关闭），agent 的开关与选项 3 个。互通向量 `rust.json` 新增 `path` 一节。
- 浏览器新增 39 个：与 `rust.json` 逐字节互通（信封、信令、直连 prologue 与握手、封好的信封）、`Lanes` 交错性质测试、两端驱动背靠背的切换与断网、`p2p.ts` 的完整流程、坏指纹、只走 hub、超时与退避、网络变化立即重试、403、被拒后重试、路径指示在三种语言下的渲染。

**测量记录**

- 探针（2026-10-16，hub 在新加坡）的结论：同一台机器总能直连（host ↔ host），直连 p50 不到 1 ms，经 hub 150–190 ms；手机 4G 上 IPv6 直连 p50 60–70 ms，经 hub 约 220 ms；两边 IPv4 都是对称 NAT、IPv6 又配不上时打不通，只能走 hub（这正是最需要就近中继的情形）。测过的网络里大约三分之二能直连。
- 正式功能，本地端到端的直连段（无头设备用 str0m，与 agent 在同一台 Mac 上；按键间隔 30 ms，即打字的节奏；最后一次运行）：
  - 本地 hub：直连 106 ms 打通，UDP/IPv6，探测往返直连 0.26 ms、hub 2.0 ms；按键回显经 hub p50 2.5 ms，经直连 p50 1.4 ms / p95 4.4 ms；断网测试 1255 次按键（往 `cat` 里打 30 行，第 10 行起 UDP 全断）1.5 s 后退回 hub（未确认帧超时），每一行完整、按序到达，重发 304 帧、丢掉 1 个重复帧；重试 52 ms 回到直连；即将被移除的设备的直连在签下移除后 41 ms 内随通道关闭；数据库导出与 hub 日志里金丝雀（含经直连打的那一个）命中 0。
- 真浏览器（一台 Mac 上的 headless Chrome，用应用自己的传输层开终端、按键间隔 50 ms；机器是独立的试用实例）：
  - 本地 hub（`cloud-dev.sh`）：通道打开后 0.2 s 内直连接上，探测往返直连 0.3–0.4 ms；按键回显经直连 p50 1.9 ms / p95 3.7 ms；打开「只走 hub」后直连立刻断开（重发 1 帧），机器条从「direct · 1 ms」变为「via hub · 1 ms」。
  - 终端输出原来固定攒 16 ms 再发，一次按键的回显至少等 16 ms；现在改为节流：安静一段时间后的输出立刻发，紧随其后的才攒到下一帧（`terminals/mod.rs`）。更早的测量（hub p50 约 20 ms 本地 / 176–190 ms 经新加坡的 hub）是连续按键、并包含那 16 ms。

**已知限制**

- 直连依附于 hub 通道：hub 重启（每次部署）或 hub 连接断开仍会结束整条通道，直连随之结束；页面照旧约 1 s 重连，再用一个尝试回到直连。让直连在 hub 断开时撑住通道是以后的事。
- 不做 TURN：两边 IPv4 都是对称 NAT、IPv6 又不通时（探针里打不通的那种情况）连不上，走 hub；这些用户需要的是就近的中继（`docs/relay-and-plans.md` §2）。
- agent 只在默认路由的那个 IPv4 和那个 IPv6 地址上提供 host 候选：多网卡、不同网段时只有默认路由那一侧；同网段的设备仍能经 prflx 连上。
- 加密流的记录不走直连（见「存储不变」）。

## 10. 考虑过但没采用的方案

- **不加密的薄中继**：云端能读到一切，与前提冲突。
- **Loro 式 CRDT 文档**：transcript 天然是单写的追加文件，用不上 CRDT。只借鉴它的加密追加日志、快照加尾部和游标纪律。
- **Cloudflare Workers/DO**：已选常规容器托管 + Rust。DO 能解决的「就近」和连接扇出问题，记为以后多区域时的参考。
- **每台机器各跑 cloudflared + Access**：做不了多租户，也没有端到端加密。
- ~~**浏览器直连电脑 / WebRTC 点对点**：暂不采用~~——探针的测量（大约三分之二的测试网络能直连，同一台机器 p50 不到 1 ms、手机流量 60–70 ms 对 hub 的 150–230 ms）改变了结论：已作为 hub 之外的**可选路径**实现，hub 永远兜底，不做 TURN（见第 9 节「直连通道」）。仍然不采用的是「只靠直连、没有 hub」。
- **服务端托管或 passkey PRF 解锁**：与「不托管」冲突。
- **云端密文搜索索引**：超出范围，搜索在 agent 或前端做。
